## D-129 — The front page is about what the ministry's paths produce, and it reads them from a public endpoint

**Decision (TAM-150):** §4.0's explorer stops explaining the product's four stages and shows **one tab per active training path**, each panel answering the question a manager actually arrives with — what will my people be able to do. The four stages survive as four lines beneath the tabs («كيف يُطابَق الموظف بمساره»), which is the weight process deserves on a page whose subject is capability. The hero, FAQ and footer keep their structure and change angle only: skills vocabulary, and a FAQ set re-chosen for a manager (how an employee is matched · what the path certificate attests · can a path be changed · who may register · where courses are studied · how a certificate is verified).

**Content is data, not copy.** A path now carries `skill_outcomes` (`text[]`, empty by default) beside its description, edited in §4C.4 next to the description because the two are written together and read together. Three to five capability nouns, bounded in the DTO — the public page renders the list as-is, so a hundred outcomes would be a wall of text on the ministry's front door, and a sentence with a full stop in it is prose that belongs in the description. **The lower bound is deliberately not enforced on save:** a path may legitimately have none yet, and refusing to save a half-written list is how an editor loses work. The seed carries placeholder descriptions and outcomes for all twelve paths, written from each path's real course list; **TAM-150 is not closed until الإدارة العامة للتدريب has signed them off**, the same rule the landing copy already lives under.

**`text[]` rather than a child table.** The list is short, always read whole with its path, and never queried across paths. A join table would buy ordering guarantees the array already gives and cost a second read on the public explorer's one query.

**A public endpoint, and it is treated as an exposure.** `GET /api/public/paths` is the second unauthenticated read in the product after certificate verification, and it carries the same disciplines: `@Public()` as the single greppable line, a throttle well below the default, and — new here — a **five-minute in-process cache with concurrent misses coalesced**, so that however many visitors arrive the database is asked at most once per window. It `select`s its columns rather than filtering a loaded row, because a `select` cannot leak a field added to the model later. It lives in a module of its own rather than on `PathsModule`, which is `@Roles('EMPLOYEE')` at class level: a public route among guarded ones is one refactor away from inheriting a guard it should not have, or losing one it should. What is deliberately absent and must stay absent: anything about people, the course titles themselves, and the path keys.

**Two deviations from the ticket, both deliberate:**

1. **The fetch is client-side, not server-side.** The ticket calls the landing page a server component; it is not — `LandingView` is `'use client'`, and it is mounted in two places: `/landing`, a server route, and `/`, where `PortalProvider` renders it from the client after a 401. A server fetch would serve one of those and not the other, and one page behaving two ways is worse than one honest fetch. What the instruction was protecting — "a static page must not hit the database per visit" — is solved where it actually belongs, in the endpoint's cache.
2. **Ordering is career type, then `displayOrder`.** `displayOrder` is curated *within* a letter (six paths share the value 1), so ordering by it alone interleaves the types and puts the two paths of one kind at opposite ends of a twelve-tab strip. The enum's declaration order is the canonical R-I-A-S-E-C (D-031), so this is the sequence the product already uses rather than a second opinion about it.

**The fallback is the rule, not a nicety.** A failed or empty read renders the matching strip alone above one Arabic line saying the paths will appear shortly — never a `DataView` error card. This is the ministry's front door: a visitor must still learn what the platform does and still be able to register when the API is down.

**Known and bounded:** an administrator's edit to a path takes up to five minutes to reach the front page, and the cache is per process, so invalidating it from §4C.4 would be best-effort in a multi-instance deployment and is deliberately not wired — the bound governs either way.

**Rejected:** keeping the stage explorer and adding paths beside it (two explorers on one page, and the stages were never the subject); a card grid of twelve paths (twelve descriptions at once is a wall, and the tablist is already the page's one interaction); showing the RIASEC letter (D-126 — «R» names nothing to a visitor); a `MINISTRY_HEADCOUNT`-style count of enrolled employees on the page (people are not public information); enforcing a minimum of three outcomes on save (loses an editor's half-written work).

## D-128 — «الأثر» is the first tab of §4C.8, and every figure on it carries the period it is about

**Decision (TAM-149):** §4C.8 becomes three views on the shared tablist (TAM-118) — «الأثر» · «التقارير» · «سجل العمليات» — and opens on the first. The reports beside it are unchanged; what they could not answer is the question management actually asks, because they have no time axis and no department axis: how many of our people took part this quarter, in which directorates, what did they complete, and is it growing. One endpoint, `GET /api/admin/impact?from&to&department`, one service, `admin-impact.service.ts`; every column it reads exists already, so it adds aggregation and nothing else.

**Four rulings inside it, each of which a plausible implementation would have got quietly wrong:**

1. **The comparison is a window of equal length, not the previous calendar period.** Q2 has ninety-one days and Q3 ninety-two; a calendar-to-calendar delta would report about a per cent of growth that is nothing but the length of the months. Equal-length shifting also keeps the contract at `from`/`to`: which preset the screen was showing never becomes a vocabulary the API has to branch on. For the default period — a calendar month — the shift lands exactly on the previous month, which is the case that matters.
2. **The participation rate is cumulative, and the tile says what its denominator is.** «Confirmed this quarter ÷ registered this quarter» can exceed one hundred per cent — someone who registered last year and committed this one is in the numerator and not the denominator — so it is not a rate. Both halves are counted to the end of the period. The denominator is **accounts, not the ministry's headcount**, which the platform has no way of knowing; the screen states that rather than letting a figure be quoted upward as workforce participation. A `MINISTRY_HEADCOUNT` setting could replace it later — noted, not built.
3. **A pass with no LMS timestamp is dated by when we recorded it.** `completions.completed_at` is what Moodle reported and is the right date, but it is legitimately null on a course whose completion criteria carry no timestamps (D-038). Filtering on it alone would put such a pass in no period at all — invisible in every impact report while still counting in the reports tab's running total, which is the worst of both.
4. **Counts are people, de-duplicated, and employees only.** Every participation figure is read through `user` with a relation filter rather than by counting rows in the child table, so a retake is one assessed employee (D-033) and six passed courses are one active learner. An administrator's or an entity contact's account is not the ministry's workforce taking part in training, so `role: EMPLOYEE` is the population everywhere — including the rate's denominator.

**Two things are said out loud rather than left to be inferred:** a pass whose course has no `duration_minutes` (D-035) contributes no hours, and the count of such passes travels with the total so the screen can state it — a silently short figure is worse than a stated gap. And the language-level block renders «لم يُفعَّل اختبار المستوى بعد» rather than an empty list, because "not enabled" and "nobody took it" are different findings; `cefr` is `null` in the contract until TAM-148 ships, which is what makes the distinction expressible.

**Paths completed are read from the path certificate**, not from `user_paths`: issuance is idempotent and happens the moment the last course is passed (§5.5), so the certificate row is the only durable record of *when* a path was finished — `user_paths` carries a status and an `updated_at` that any later write moves.

**Export and print.** The CSV is rendered in the browser over the shared `toCsv`, for D-112's reason: every column of it is Arabic copy, and that lives in the message catalogue. Printing is a stylesheet — `@page` A4, the frame's navigation, user menu and skip link marked `data-print="chrome"` and dropped, the owner's lockup and the classification kept, because a sheet that leaves a government office has to say whose it is. No second renderer: the Puppeteer path stays where the typography has to be exact, on certificates and the CV.

**Rejected:** sending the preset to the API (a second vocabulary for something the two dates already say); a charting dependency for the trend (the repo takes none for a bar, and every bar here is paired with its number so the row survives a printer that drops backgrounds — WCAG 1.4.1); reusing `AdminLetterShare` whole for the period's career types (its `activePaths` is a fact about now, and every other figure on the tab is a fact about the period); a fifth «مسارات مكتملة» tile beside the path-certificate count (§3 — the same number twice); per-department queries for the table (it is tallied from the same rows the tiles are counted from, which is the only way the columns cannot disagree with the totals above them).
## D-127 — Make the invalid state unreachable in the editor; keep the guard in the gate

**Decision (E.3):** §4C.9's editor is shaped so that two of `assessEnglishBank`'s blockers cannot be produced through it. Marking an option correct **clears the question's other options in the same transaction** (radio semantics, server-side), so `MULTIPLE_CORRECT_OPTIONS` is unreachable. The band editor exposes **five ceilings, not twelve bounds** — A1 starts at 0, each band starts one above the previous ceiling, C2 is pinned to the attainable total — so `BANDS_NOT_CONTIGUOUS` and `BANDS_DO_NOT_COVER_RANGE` are unreachable. **Both blockers stay in the publish gate regardless.**

**Why not delete the now-unreachable guards:** because "unreachable" is a statement about *this screen*, and rows arrive by other routes — the E.4 seed, a future import, a hand-run SQL fix during an incident. A blocker that no UI can trigger is exactly the one worth keeping: nothing else would catch the case, and it costs one branch in a pure function. The inverse — trusting the UI and dropping the check — is how a data fix made at 2am becomes a learner placed at the wrong level with nothing reporting it.

**Why not the other way round (free-form fields, refuse afterwards):** an editor that lets somebody type a gap and then refuses them for it is an editor that teaches its own rules by rejection. Deriving the lower bounds means the administrator is *only ever* choosing the thing they actually have an opinion about — where B1 ends — and the structure holds itself together.

**A convenience that is not a policy:** «توزيع متساوٍ» fills the five boundaries evenly. Growing a bank from twenty items to thirty makes every boundary stale at once, and retyping five numbers to get back to "roughly even" is work the screen can do; the administrator then moves the ones they care about. It is a starting point, never applied automatically — the band table is a ministry judgement, and a screen that silently rebalanced it would be making that judgement.

**Rejected:** a checkbox per option with a "only one may be correct" validator (the state is reachable, so it must be explained, so the screen grows an error nobody needs to see); twelve band fields with live validation (same); auto-rescaling the bands when `maxScore` changes (the editor would be deciding what B2 means).

## D-126 — The CEFR code is shown; the RIASEC letter is not

**Decision (E.2):** `CefrLevelBadge` renders «B2 · فوق المتوسط» — the Latin level code beside its Arabic name — where `HollandCodeChips` renders «الاجتماعي» and never the letter S.

**Why the two differ rather than one of them being wrong:** a RIASEC letter is a *storage key*. "S" is an index into a framework an employee has no reason to know, and «الاجتماعي» is the whole of the result; showing the letter would be showing them our database. A CEFR level is the opposite — "B2" **is** the internationally recognised name of the thing. It is what a training officer screens on, what a course prerequisite is written in, and what an employee would put on the English CV §4.11 exports (D-050). Hiding it would withhold the half that travels, and leave «فوق المتوسط» to be translated back by whoever needed it.

**Consequence for the message catalogue:** the code is rendered from the data — the `level` field — and never from `ar.json`, so the catalogue stays free of Latin letters and bare digits and `messages.test.ts` needs no exemption for it. The Arabic name carries the meaning; the code carries the currency. `dir="ltr"` is set on the code span alone, because an isolated Latin token in an RTL run throws its neighbouring punctuation to the wrong end.

**Rejected:** hiding the code for consistency with Holland (consistency with a rule whose reason does not apply here); showing the code alone (an Arabic-first product must not make a level readable only to people who already know the framework); putting the codes in `ar.json` (would need a third `LITERAL_VALUE_PATHS` exemption, for data that is not copy).

## D-125 — The CEFR bands live on the assessment version, and they are what the balance rule is not

**Decision (E.1):** the six CEFR bands are rows on the `english_assessments` version that owns them (`english_assessment_bands`), copied by copy-on-write with everything else, **not** entries in the `settings` table. Publishing an English version is gated by `assessEnglishBank`, whose central rule is that the band table must **partition `0 … maxScore` exactly**: all six levels present once, no inverted range, no gap, no overlap, starting at zero and ending at the highest attainable total. `isBalancedBank` and `assessBank` are not imported, not called and not modified.

**Why on the version rather than in settings:** a band table is not a knob beside the sync interval — it is the part of the instrument that turns a raw total into the level a person is told they are. In `settings` it would be a global mutable, and an administrator moving the B2 boundary would silently re-interpret every result ever issued: the stored `level` would say one thing and the live table another, with no way to say which was in force when. That is exactly the gap D-072 exists to close, and the fix is the same one — the bands travel with the version, so "38 out of 60 meant B2" stays true after the boundary moves. D-075's rule is unbroken: settings hold what an administrator must change *without a deploy*, and this is changed without a deploy too, through §4C.9's draft-then-publish.

**Why the partition rule replaces balance rather than joining it:** D-032's balance protects a comparison *across* dimensions — Holland ranks six raw scores against each other, so unequal attainable maxima make the code an artefact of authoring. English has one scale and nothing to compare across; an item worth four marks is difficulty weighting doing its job, not a skew. Applying the guard here would refuse correct instruments for a reason that does not exist in this model. The partition rule is the English analogue in the sense that matters: it is the one property whose violation produces an instrument that is *silently* wrong — a gap and a scoring learner cannot be placed at all, an overlap and the level they are told depends on which row was read first.

**Both bounds are inclusive**, because an administrator types "45 to 56" and a half-open editor would put an off-by-one between what they entered and what a learner was told. The floor on the bank is expressed over **attainable marks, not question count** (`MIN_ENGLISH_ATTAINABLE_MARKS = 5`), the same choice D-074 made and for the same reason: six levels need six distinct integers, and a count-based rule has no opinion about a bank whose items are worth different amounts.

**One warning, not a blocker:** a CEFR level with no question targeting it. It is a real quality problem — a bank with no C1 item systematically under-places strong candidates — but it is a content judgement, and refusing it would make the legal destination unreachable while a bank is being grown one level at a time. Same severity reasoning as D-074's adjacency rule.

**Rejected:** bands in `settings` (see above); sorting the table by `minScore` before validating it (a table where B1 sits below A2 is wrong, not "sorted differently", and sorting first would silently accept it); reporting contiguity and coverage over an incomplete table (three faults named for one mistake); defaulting an uncovered score to the nearest band (telling somebody they are A1 because a table was malformed is worse than refusing to score them — hence `ENGLISH_ASSESSMENT_NO_BAND`).

## D-124 — The English test gets sibling tables, not a discriminator on `assessments`

**Decision (E.1):** the English placement test is six new tables — `english_assessments`, `_questions`, `_options`, `_bands`, `_results`, `_responses` — mirroring the Holland instrument's *shape* and its copy-on-write versioning, and sharing no table, no type and no function with it. `AssessmentStatus` is the one thing reused, because DRAFT/ACTIVE/RETIRED is a lifecycle rather than a RIASEC fact. Not one line of the Holland schema, service, editor or test changes.

**Why, decisively:** the service layer is not key-aware. `AssessmentService.getActive` and `AdminAssessmentService.createDraft`/`requireDraft` all ask `findFirst({ where: { status: 'ACTIVE' } })` — or `'DRAFT'` — **with no filter on `key`**, and `overview()` reads the whole table. The partial unique indexes are per-key, so the *database* would happily hold a second ACTIVE instrument; the *code* would then serve whichever row Postgres returned first as the learner's Holland assessment. Making those queries key-aware means editing the live RIASEC path, which is precisely what this work is forbidden to do. Separate tables make "Holland is unchanged" a property of the diff rather than a claim about care.

**Two supporting reasons.** `AssessmentResult` is irreducibly RIASEC — six score columns and a `VarChar(3)` code — so English needed its own result table regardless; folding the banks together would have left the results split anyway. And the two models differ in kind, not degree: `AssessmentOptionWeight` (an option contributes points to one or more dimensions) has no English meaning, while `options.is_correct` and `questions.marks` have no Holland meaning. A shared table would carry both as nullable columns nothing enforces.

**What English adds that Holland lacks:** `is_correct` on the option and `marks` on the question. Marks sit on the *question*, not the option, because exactly one option scores and the rest score nothing — putting the value on the option would invite a bank where two options are worth different amounts of "correct". "Exactly one correct option" is checked at **publish**, not by a database constraint, on D-073's reasoning: a draft must be free to sit in an invalid state while somebody edits it.

**Rejected:** a `kind` discriminator on `assessments` (breaks the three unfiltered `findFirst` calls above; every future query must remember the filter); making the Holland queries key-aware first (edits the live path this work must not touch); a shared abstract "assessment engine" (its only two instances disagree about what scoring *is*, and it would put a correct RIASEC tally at risk for reuse nobody asked for).

## D-123 — The English test is independent, optional, and taken once

**Decision (at the user's direction, 2026-08-30):** the English (CEFR) placement test is an **independent** instrument. It is takeable at any time from a dashboard card, in every dashboard state; it produces a standalone CEFR level shown on the dashboard and Profile; and it **does not gate path selection** — Holland alone drives recommendation. It is **taken once and never retaken**: `english_assessment_results.user_id` is unique, and `EnglishAssessmentResultView.canRetake` is always `false`.

**Why this shape costs the existing journey nothing:** `DashboardState` gains no fourth member, `navForState` gains no branch, `JourneyStateService` gains no fact, and path confirmation gains no gate. The entry point is a secondary card, so §4.2's "one primary action per state" survives — the pre-assessment dashboard's single primary action is still «ابدأ التقييم» for Holland. The only change to an existing shared contract is one nullable field on `DashboardView`. It is not a learner nav item either: §4's steady-state six stands, and the English test is a flow page reached from its card, exactly as `/assessment` and `/results` are.

**Why "once" is a constraint rather than a check:** §4.13 says the test is taken once; a service-layer guard loses the race between two concurrent submissions and a unique index does not. Same shape as `user_paths.user_id`, and the D-035 reasoning applies unchanged.

**Why not mirror Holland's retake lock literally.** D-015 permits a Holland retake until a path is confirmed and refuses it after. Applied here, that gate would refuse the **first** attempt too for anyone who had already confirmed a path — so a learner with an active path could never take the optional English test at all. The rule that carries over is the one D-015 is actually protecting: a result, once taken, is frozen and not revisited.

**Consequence worth knowing:** there is deliberately no administrative "clear this person's English result" endpoint. If the ministry later wants a re-sit policy, that is a change to this decision and to the unique index, not a setting.

**Rejected:** English as a required second onboarding step before path selection (a new `DashboardState`, a new server-side gate on path confirm, and a change to the Holland journey e2e — a large blast radius for an instrument nothing downstream consumes); English retakeable at will (the user's direction); offering it only after Holland (couples two independent instruments for no product reason).

## D-121 — The learner's course is framed too; the handoff becomes the fallback for everyone

**Decision (at the user's direction, 2026-08-25):** §4.8's course player renders the Moodle course **inside the page**, the same way the entity's editor is framed (D-101). The plugin gains `embed=learner` (chrome hidden as for authors, **plus the course tabs** — a learner has no business in Settings, Participants or Grades; the course index stays; no editing) and posts `tamkeen:quiz-finished` when the quiz review page renders. The launch endpoint takes `{ embed: true }` and answers `mode: 'embed' | 'handoff'`; the frame component is now one, portal-agnostic `components/moodle-embed.tsx` fed the two launches and its words. D-045's "the player is a handoff page" is superseded: the handoff is the **fallback** — when the frame never reports ready, and always as the quiet «افتح في منصة التعلّم» beneath it. Its other rules stand unchanged: launch is a POST per visit, never prefetched, enrolment on demand, refusals indistinguishable, no `courseUrl` in the API.

**The outcome comes back in seconds, not at the next run.** On `quiz-finished` the page calls `POST /api/courses/:id/sync`, which runs the scheduled completion sync's own `syncUser` for this learner only — same code, same idempotency, same threshold reading — behind a 10-second per-learner cooldown so a burst of messages is one LMS read; then it refetches the player view. The scheduled sync remains the safety net, and certificate issuance still happens inside the sync.

**Why now:** the entity side proved the mechanism (same-site cookies, `frame-ancestors`, ready/fallback) and the user's test showed the learner's leave-for-Moodle as the last seam. **Rejected:** a separate learner frame component (one seam, one discipline); polling the player view after launch (the plugin already knows when the quiz was submitted); a course-scoped sync (Moodle's progress read is per user anyway).

**Verified:** as `demo-student`, `/courses/<id>/player` frames Moodle course 85 with `tamkeen:ready` received, `body.editing` false, navbar and course tabs hidden, course index present, all eight demo activities listed. Web 519, API unit 209, journey + entity e2e 105 green.

## D-120 — The authoring guide is one Markdown file, rendered in the portal by a forty-line converter of our own

**Decision (TAM-143):** the entity authoring guide lives once, in Arabic, at `docs/entity-authoring-guide.md`, and the portal renders it at `/entity/courses/guide` through `lib/simple-markdown.ts` — a converter for exactly the subset the guide uses (three heading levels with `{#anchor}` ids, paragraphs, one-level lists, bold, inline code, links to `#`, relative or http(s) targets). The source is HTML-escaped before any tag is written, so the only markup in the output is the converter's own. Blockers whose fix is in Moodle or in بيانات الدورة carry a «كيف؟» link straight to the section; the create card and the Content page link to the guide; it is not a nav destination (§4B keeps the entity nav to four) and it sits under `/entity/courses/…` so TAM-140's longest-match rule lights «دوراتي».

**Why not a Markdown library:** a general renderer is a new dependency to review for a government repository, would still need our own escaping and link policy, and would bring a hundred features the guide does not use. Forty tested lines that we can read are cheaper to own than a dependency we cannot. **Why not `ar.json`:** two copies of a long document drift; the file is the one source and the page reads it at render time (two candidate paths, because `process.cwd()` differs between the workspace and the repo root).

**Also here:** the Content page and Manage Course now show the course's **description** under its title — the text learners read in the catalogue, visible where the entity edits the course so the two never drift unnoticed.

**Owed:** screenshots of the framed editor in the guide once the Arabic language pack is installed on the target Moodle (the local one has none — download pending); the upload ceiling per environment (Phase 7).

**Amended 2026-08-27 (merge with `main`):** the guide shipped to `main` independently at `/entity/guide`, rendered by `apps/web/src/lib/markdown.ts`; this branch’s `/entity/courses/guide` route and `lib/simple-markdown.ts` were dropped when the two met. The decision’s substance — one Arabic Markdown file in `docs/`, an in-repo converter, links from the create card / Content page / publish blockers, not a nav destination — stands in that implementation.

## D-119 — A course belongs to at most three paths, within two RIASEC letters; membership is a proposal; «عامة» is the admin's word for "everywhere"

**Decision (TAM-141, at the user's direction 2026-08-25):** four rules for which paths a course may belong to.

1. **Cap of 3** (`COURSE_MAX_PATHS`, a setting). 2. **Coherence:** those paths may span at most **2** distinct RIASEC letters (`COURSE_MAX_RIASEC_LETTERS`). 3. **Approval:** what an entity saves is a proposal — `path_courses.status PENDING | APPROVED`; only APPROVED rows reach the learner catalogue, path build, the derived letters (D-066) and the publish gate. Auto-approved while `PATH_MEMBERSHIP_APPROVAL=off`, which is the state until Phase 5's Path Management queue exists; the schema (`status`, `decidedById`, `decidedAt`) is in place so switching it on is a setting, not a migration. 4. **«عامة»:** an admin-only `courses.isGeneral` — such a course reaches every path's build list without memberships, carries no letters, and is exempt from rules 1–2; entities see it read-only.

**Why each rule:** a course in every path carries every letter — no Holland signal (D-066 derives letters from paths); every path's 5–10 build list then holds the same generic course, so paths stop being curated tracks; and path membership is *path* content the admin owns (§4C.4), yet one entity ticking twelve boxes has edited every path. The cap alone does not protect the signal — three paths from R, S and C still smear it — hence coherence. «عامة» exists so a genuinely cross-cutting course (أساسيات أمن المعلومات) has an honest route that is an admin's decision, not the "all paths" hole under a nicer name.

**Grandfathering:** a course already outside the rules (seeded before them, or the limits lowered) keeps its memberships — learners may hold it in confirmed paths and D-002/D-040 forbid pulling it. It may remove memberships but not add until it is back within the rules (`PATH_MEMBERSHIP_FROZEN`, and the form says «يمكنك إزالة مسارات فقط»). No migration rewrites `path_courses`.

**Where the rules live:** one pure module, `path-membership-rules.ts` (`checkPathMembership`), used by `replacePathMembership`; the form applies the same three checks per checkbox from `pathRules` on the course payload, so the numbers live in the settings and nowhere else. Every learner-facing reader of `path_courses` filters `status: 'APPROVED'` (`courses.service`, `paths.service`, the entity dashboard count); the entity's own views show pending rows with their status. ## D-118 — The authoring loop is one page, and the publish gate is one component offered on two

## D-117 — The catalogue opens where the reader is, and groups the rest by the path that explains it

**Decision (TAM-127):** the courses catalogue stays **global for everyone** (§4.6 unchanged) and changes only where it *starts*. A learner with a **confirmed path** lands with that path preselected in the path filter — «كل المسارات» is one selection away, and their later choice wins. A learner still deciding lands on the whole catalogue **grouped by path**, one `<section>` per path in the API's order (recommended first, in the user's letter rank), each heading carrying the path name, the «موصى به» badge when it applies, and the group's course count. **Any search text or filter collapses the grouping into the flat grid** and clearing it restores the grouping. Courses in the learner's own path carry **exactly one status chip** — «مكتملة» / «قيد التنفيذ» / «في مسارك» — and courses outside it carry none. Path membership renders as quiet neutral tags instead of a comma-joined sentence, and the three filters are rebuilt on the shared `Field` + `Input` + `Select` primitives. **§4.6's "category" filter is satisfied by the path filter** — that is the reading recorded here.

**Why the default:** the product already does not treat these two readers alike. `assertCoursesSelectable` refuses to add any course outside the confirmed path, so a committed learner browsing forty-eight courses was looking at roughly forty they can never act on, with nothing marking the eight that are theirs. For the *un*committed learner the catalogue is the opposite tool — it is how "what does this path actually teach?" gets answered — and a flat grid of forty-eight cards answers it for nobody. One page, two starting positions, both a click from the other.

**Why grouping collapses under a filter:** a filtered result is an answer to a question, not a tour. Keeping the sections would spread three matches across three headings and make the answer harder to read than the question.

**Why the chip and not colour, and why absence:** the chip's word carries the meaning (WCAG 1.4.1) and it is neutral, never the primary accent — the accent means *recommended* (D-069), and a chip in it would recommend a course the learner has already committed to. A "not in your path" chip on forty cards would be noise on every card that is not the answer; absence is the signal (§3). The resolution is **one component** (`CourseStatusChip`) shared with the course page (TAM-128), reading a `courseStatus` namespace of its own — three screens share those three words, and a namespace named after one of them would make the other two look like borrowers.

**No API change.** The chips come from `myPathApi.get()`, fetched once alongside the list and only when a path is confirmed; its failure is deliberately **not** wired into the `DataView`, because blocking the catalogue on a decoration trades the page for a badge. The grouping comes from `pathsApi.list()`, which already carries `recommendationRank` — nothing is re-sorted in the browser (D-113's rule holds here too). A course in two paths appears in both groups: the grouping is a lens, not a partition. A course belonging to no listed path falls into a final «دورات خارج المسارات» section rather than vanishing from a view whose own count line still counts it.

**Rejected:** *restricting* a committed learner to their path (that is a gate, and §4.6 says browse is global); adding per-user status to the courses list response as well as fetching my-path (two sources for one fact); a RIASEC-type filter beside the path filter (two filters narrowing the same dimension compete, and users think in paths); pagination (the grouped default and the filters keep screens short at seed scale — it becomes its own ticket when real ministry data lands); deep-linking a card straight to the player (the chip informs, the detail page acts — §4.7 owns the single action).

## D-115 — Per-course resync is the immediate path; the scheduled sync is only the net

**Decision (TAM-133):** a rename, summary edit or visibility change made in the frame's own Settings tab now fires the same `tamkeen:content-changed` message a content edit does (`\core\event\course_updated` added to `db/events.php`, one message type for both). The portal answers it, and the entity's own manual «تحديث», with `POST /api/entity/courses/:id/resync` — a **synchronous, single-course** re-read of the LMS (`core_course_get_courses_by_field` by id), applied through the exact mapping the scheduled catalogue sync uses (`CatalogSyncService.upsertLmsCourse`, extracted so `sync()`'s loop and the new `syncOne(moodleCourseId)` can never map a field differently). The scheduled sync (`COMPLETION_SYNC_INTERVAL_MINUTES`) is kept, unchanged, as the safety net for a course edited some other way — directly against the LMS's own admin, or by a job — that never passes through this portal's frame at all.

**Why:** title, summary and visibility were a cached copy refreshed only on that schedule, so a rename at 13:31 stayed wrong everywhere in the portal — the Content page header, Manage Course, «دوراتي», the learner catalogue — until 13:35 (observed 2026-08-25). A five-minute lag on structure was already covered by the frame's existing message; the same lag on the course's own name was not, for no product reason — an entity watching the Content page after a rename should not need to know which kind of edit propagates immediately and which does not. Extracting the shared upsert rather than writing a second mapping is what keeps `sync()` and `syncOne` from silently disagreeing about what a given LMS course means, the same reasoning D-059 already applies to `status`.

**Coalesced, not merely rate-limited:** the frame can post its signal several times in one burst (an activity edit and a settings save land within the same couple of seconds), and each is a separate call into `resync`. `CatalogSyncService` holds one in-flight promise per `moodleCourseId`; a second caller for the same course during that window is handed the first's result rather than triggering its own LMS read. The `@Throttle` ceiling (30/min per user) is a second, cheaper backstop against a caller retrying faster than the LMS can answer — the two are independent, not alternatives to each other.

**Courses created directly in Moodle stay unclaimed.** An entity in the framed editor cannot reach "create course" — the primary nav is hidden — and D-060 already makes the portal the only place a course shell is created, so a course born in Moodle has no owner. This ticket does not change that or auto-claim such a course for whichever entity happened to resync it; it remains Phase 5's Course Oversight matter, shown there as unclaimed exactly as it is today. Noted here so a future convenience does not quietly attach ownership to whoever's frame first noticed the course.

**Rejected:** shortening the scheduled interval instead (fixes every course's lag at the cost of load, when only the course an entity is actively looking at needs to be fast); polling the single course from the Content page instead of the frame signalling (reintroduces the polling this event-based design was written to avoid, TAM-129); writing a second, resync-specific mapping function (the exact drift risk D-059 exists to close off — the two-harness unit test that feeds `sync()` and `syncOne` the same LMS course and asserts identical rows is what keeps this true rather than merely intended).

## D-107 — A password change is not the cheaper way to guess, and it sends no email (for now)
**Decision (TAM-110):** `POST /api/auth/change-password` feeds the **same** failure counter and lockout as sign-in (`AUTH_MAX_FAILED_ATTEMPTS` / `AUTH_LOCKOUT_MINUTES`); a locked account is refused there with the same `ACCOUNT_LOCKED` code; a successful change clears the counter as a successful sign-in does. **Why:** the endpoint verifies a password. The confirmation is a typo guard for the person, and a client that skipped it would store a password typed once and never repeatable; the server is the last line. The email is standard security hygiene, but §2's notification list is short and locked, and every other session is revoked on change — the owner already learns of a change they did not make by being signed out. Raised with the product owner as a §2 amendment; add it in a follow-up if approved, not silently.

**Rejected:** a separate counter for the change endpoint (two thresholds to explain, and the weaker one wins); counting a confirmation mismatch as an attempt (punishes the typo the field exists to catch); sending the email anyway (widens a locked list by one line without the decision that locks it).

Two rewrites happen on the way in: the XML prolog is stripped, because `<?xml …?>` part-way through an HTML body is markup the parser has nowhere to put, and the exported `.st0` class is dissolved into a `fill` attribute per path, because an inline `<svg>` shares the document's stylesheet and a global rule named after nothing is one collision away from repainting the certificate.

**The rule was furniture.** A signature line is drawn for somebody to sign *on*; this block prints a name the ministry has already configured (D-073), so the line implied a hand-signed document that the PDF is not.

**Still owed, and unchanged:** the ministry **seal** and the signatory's actual signature (D-051). The emblem closes half that blocker, not all of it.

**Rejected:** a data-URI `<img>` (rasterises at print size, and costs base64 for no gain over inline vector); reading the web app's copy at runtime (the container path problem above); recolouring the emblem to the certificate's primary green (it is the ministry's artwork, not a themed mark).

## D-104 — A setting's editor is derived from the schema that validates it
**Decision:** `AdminSetting` carries `editor` (`text` / `number` / `select`) and `options`, computed on the server by inspecting the Zod field in `envSchema` that the value is parsed against: a `ZodEnum` is a dropdown whose options are the enum's members, a `ZodNumber` is a digits-only field, everything else is text. `SETTING_KEYS` moved from `apps/api/src/settings/settings.schema.ts` into `packages/types` so the web message catalogue can be asserted against it.

**Why:** the ministry was typing `restricted` and `admin-only` into free-text boxes from memory, and the sync interval accepted letters until the save came back refused. Both are the same defect — the screen not knowing what the server accepts. Deriving the shape from the validating schema means the two cannot drift: a hand-written option list is a second source of truth for the allowed values, and the day they disagree the screen offers something the server refuses. The key list moved for a defect of the same family: the screen renders one row per key and looks its Arabic label up by key, so the three certificate keys added by D-073 reached the ministry as the raw `admin.setting.CERT_SIGNATORY_NAME` — and no test on either side could enumerate the keys to catch it. With the list shared, the catalogue is asserted against it and the next such key fails CI. The three labels and hints are now written, and the registration and digits hints stopped teaching the literal values now that a dropdown holds them.

**Also, at the ministry's direction:** Settings moves to the **last** position in the admin sidebar — the items above it are the day-to-day work, and configuration is a destination you go to deliberately.

**Rejected:** declaring the editor kinds in a table beside the keys (the second source of truth above); `type="number"` for the numeric field (it still accepts `e`, `+` and `-`, then reports the value empty rather than refusing the character — stripping on change is what actually enforces digits); translating the enum values themselves (they are stored and validated as written; only the *labels* are Arabic).

## D-103 — The pass threshold is deployment configuration, not a screen
**Decision:** `PASS_THRESHOLD` leaves `SETTING_KEYS`, so §4C.6 has no field for it and no endpoint can write or reset it. Completion sync and the course player read it from the validated environment through `AppConfigService`. A migration **deletes any stored override**. D-007 is unchanged — it is still a product setting, evaluated against Moodle's grade and never hardcoded into Moodle; it is now set where the deployment is configured.

**Why:** the ministry asked for the field to go (2026-08-25). Removing the screen without removing the row would have been the dangerous half: a stored override would keep governing every pass/fail verdict, invisibly, with no screen to show it and no endpoint to clear it — a number nobody could see deciding whether an employee earned a certificate. Deleting it makes the deployment's value the only answer, which is what the removal means. The property that made the knob safe to move survives untouched: `completions.passThresholdUsed` still records the threshold each verdict was decided under (D-042), so a certificate remains explicable.

**Rejected:** hiding the field but keeping the endpoint (a writable knob with no screen is worse than either); keeping it read-only in the "fixed rules" section (§2's floors are there because they are product *rules*; this is deployment config, and listing it would invite the question the removal answers).

## D-102 — Two course states, an availability period that applies itself, and a real delete
**Decision:** §4C.5 shows **two** words — «متاحة» / «مخفية» — with the reason a course is hidden (draft, withdrawn, expired period, gone from the LMS) printed under the badge; the four-state derivation is untouched and still decides, and the filter resolves through the same mapping so it cannot return rows the badge contradicts. Courses gain `available_from` / `available_until`, set as calendar days in ministry time and stored as the first and last instant of those days; the window is one more input to `effectiveCourseStatus`, never a status of its own. `DELETE /api/admin/courses/:id` removes the course from Moodle and then from the catalogue, refused for anything a learner holds, a certificate names or a completion records, reported in advance as `canDelete` and audited both ways.

**Why:** the oversight screen asks one question — can an employee choose this course — and four words answered a question nobody was asking; but collapsing the vocabulary must not collapse the *explanation*, which is why the reason still prints. The dates are ministry-local because reading them as UTC would open a course at 03:00 local. An ended period yields `HIDDEN_BUT_COMPLETABLE` and never `RETIRED`: it is a date somebody can retype, and a learner mid-course keeps it (§2, D-015). A new sync-cycle stage restates anything whose period opened or closed, and saving the dates recomputes immediately, because the case an administrator watches is the one they just typed. `LmsPort` gained `deleteCourse` because our row is a mirror — deleting only our side would have the next catalogue sync re-enter the course as an unowned draft minutes later.

**Rejected:** an `EXPIRED` status of its own (a fifth state for what is already derivable, and one that would then have to be un-set by hand); deleting our row only (the sync re-entry above); a soft-delete flag (retirement already is one — D-098's reasoning).

## D-101 — Moodle is framed by the entity portal, and the plugin — not a theme — dresses it for the frame

**Decision:** the entity authors course content in Moodle's own editor rendered **inside an iframe within the portal shell** (TAM-129/TAM-134, epic `moodle-embed`). D-046 (Model 1) stands: Moodle is still the authoring tool; only its frame around the editor disappears. Four things make it safe and workable, all in `local_tamkeensso`:

1. **Same credential as the handoff.** The frame's first URL is the single-use, HMAC-signed login (D-044) that `author-launch` already mints. `embed=author` rides beside the token as a plain parameter, **not inside the signed payload** — being framed grants nothing (Moodle still checks every capability), so a forged flag on a real token only changes how the page is dressed. Rejected: signing the flag (no security value, one more claim to keep in step between two codebases).
2. **Framing is allowed from the portal and nothing else.** `allowframembedding=1` only removes Moodle's own `X-Frame-Options: sameorigin`; alone it lets *any* site frame a Moodle login page — a clickjacking hole. So the plugin also sends `Content-Security-Policy: frame-ancestors 'self' <APP_URL>` on **every** page (the pages a hostile site would frame are precisely the ones not opened through the handoff), from a plugin setting the setup script fills from `APP_URL`. Verified: a frame from `127.0.0.1:3000` — a different origin from `localhost:3000` — stays blank and receives nothing.
3. **Chrome hiding is the plugin's, via the 4.3+ hook API, not a theme.** A body class and CSS injected from `before_standard_head_html_generation` hide the navbar (site logo, the primary entries that lead *out* of the course, the user menu), the footer and the breadcrumb, and **keep** the secondary course navigation and the course index — the quiz editor, question bank and activity settings are reached through them and the editor is unusable without them. A theme would be a second custom artefact to get approved under D-044's open question; the plugin already exists and is hook-capable. The edit-mode switch sits in the hidden navbar, so `login.php` turns editing on for the session (`$USER->editing`) — what the switch would do, and still capability-checked.
4. **Two messages cross the boundary, and only to the configured origin.** `tamkeen:ready` on every framed render (the portal shows loading until it arrives, and falls back to the full-page handoff if it never does — TAM-134), and `tamkeen:content-changed` on the render after a course-module/section/completion event (observers set a session flag; the head hook consumes it — one change, one message). Target origin is the configured ancestor, never `*`. No grades, no learner data.

**The premise this rests on, recorded so nobody discovers it in production:** Moodle must live on a **subdomain of the app's site** (confirmed as the deployment intent 2026-08-25). The framed session is a cookie; on a different registrable domain browsers drop it as third-party and the frame shows a login page. Locally `localhost:3000`/`localhost:8080` are one site (ports do not partition cookies). Production needs HTTPS on both hosts.

**D-045 amended for the entity page (TAM-134 will implement):** "the launch URL is never rendered into the page" becomes "never rendered *before the launch resolves*, and afterwards present only as the frame `src`" — by then the plugin has spent the nonce, so the DOM holds a used token that logs nobody in. The launch is still a POST per visit, never prefetched.

**D-044 follow-up, with more weight now:** if the ministry refuses custom PHP and the handoff moves to OAuth2, the chrome hiding and the `frame-ancestors` header must move into a Moodle theme. Also two operational lessons from installing this: Moodle CLI scripts must run as the web-server user (`docker exec -u daemon`) — run as root they leave cache directories the web server cannot write and every page dies with a permissions error; and `docker cp` of a directory into an existing target *nests* it, so `setup.mjs` now copies contents (`/.`). The setup script's `core_role_set_assign_allowed` call is now guarded — it inserted unconditionally and broke the script's "safe to re-run" promise.

**Not decided here:** framing the *learner's* course player. D-045's handoff stands for learners; this foundation makes it a small later ticket.
## D-100 — The admin dialog is centred, capped and form-free
**Decision:** `AdminDialog` carries `m-auto` (centring), a `max-h` with the body as the only scrolling region, a live backdrop token, a per-instance title id — and **no `<form>` wrapper**. The learner portal's confirm dialog already had the first of these with the reason written beside it.

**Why:** four separate defects, all invisible to a test that only reads text. Tailwind's preflight zeroes the `margin: auto` the UA stylesheet centres a modal `<dialog>` with, so every admin modal opened pinned to the block-start inline-start corner — **the top right of an RTL page**, which is exactly what the ministry reported. `backdrop:bg-navy/40` outlived the token D-069 retired, so the backdrop was fully transparent. A path panel with a dozen courses grew past the viewport and took its own cancel button off-screen. And `<form method="dialog">` plus `Button`'s missing default `type` meant save, retire and activate submitted the form and **closed the panel behind the request they had just fired**, while Enter in a create field abandoned the entry. Nothing in these dialogs needs form semantics: every action is an `onClick`, and Escape belongs to the element.

**Rejected:** giving `Button` a default `type="button"` (fixes this at the cost of silently changing every real form in the product); `type="button"` on each control in each panel (leaves the next control someone adds broken); a hand-rolled overlay instead of `<dialog>` (loses focus trapping, inertness and Escape — the WCAG failure the element exists to prevent).

## D-099 — The admin dashboard reads career types, not Holland codes, and only counts what an administrator can act on

## D-098 — A path has two removals: hide, and delete only what nobody ever chose
**Decision:** retirement (`isActive: false`) stays the reversible operation that takes a path out of new selections and touches nobody holding it. `DELETE /api/admin/paths/:id` removes a path permanently and is **refused for any path with a `user_paths` row or a certificate against it**, reported in advance as `canDelete` on the detail. The two live in separate sections of §4C.4 with different words and different button weights; deletion asks again, naming the path and offering the reversible alternative. The manage form also loses the estimated-duration field and the add-course button.

**Why:** the only removal was retirement, so a path created with the wrong letter or key could be hidden but never cleared away — it stayed in the management list as a permanent question about what it was for. Deletion is safe in exactly one case and that case is common: the mistake, made minutes ago, that nobody has seen. Everything else is refused because `user_paths.path_id` is `Restrict` and a path certificate names the path on a credential somebody holds — deleting it would falsify a document. The count-then-delete race is caught as P2003 and returned as the same refusal, so a learner choosing the path mid-decision produces a sentence rather than a 500; the audit entry carries the key, name and letter, because afterwards no row remains for the id to resolve against.

**On the two removed fields** (at the user's direction): the duration was maintained by hand, in minutes, for a path whose real length is whichever five to ten courses a learner picks — no single figure was right for two people. It is **still shown on the learner's path card** and is now settable only through the API; deriving it from the path's courses is the fix and is recorded as owed. Adding a course is the course's own act, done where its product metadata is set (§4B.3); detaching, reordering and the refusals stay here.

**Rejected:** a soft-delete flag (a third state to reason about, when retirement already is one); allowing deletion with a cascade through `user_paths` (falsifies certificates — the exact thing the schema was written to prevent); disabling the delete button for a held path (a disabled control teaches nothing; the sentence in its place names the operation that works).

## D-096 — One exit for every role: the header's user menu; the sidebar footer only names

## D-095 — The dashboard carries context, not just the one action: tracker, identity, the decision, what is next, what happened
**Decision:** every dashboard state shows a journey tracker (التقييم → المسار → الدورات → الشهادة, done/current/upcoming, derived from the server-decided state) and a personal header (name, department, employee id from the session). The assessed-no-path state previews the **top three recommended paths** in rank order, each opening its path page, beside one "عرض كل المسارات" link. The active state adds the next courses in order with their status, the latest certificate (or the locked slot and how it unlocks), and every state shows the last three things that happened (assessment completed, path confirmed, course passed, certificate issued). All of it arrives in the one dashboard payload; the activity feed is read from the product tables, not the audit log, because those rows carry titles a person recognises.

**Why:** §4.2's "near-empty" was obeyed literally and produced a page that read as unfinished — one card and a greeting. "Near-empty" was protecting against *empty widgets* (a zero-of-zero progress bar) and competing actions, not against information. Each addition answers a question the user has on arrival: where am I, is this mine, what should I decide, what comes next, what just happened. None is a second primary action: the recommendation cards are the decision itself brought forward; the course and certificate links are navigation to content that exists; the tracker and feed are not interactive.

**Reverses** the TAM-108 discussion's "no path previews on the dashboard" — that was the right call for a page whose only content was the card; with the tracker and feed in place, the preview is the most meaningful thing the choosing state can hold, and Results still owns the full ranking, the explanation and the retake.

**Rejected:** quick-link tiles in every state (duplicates the sidebar); a count-only nudge ("لديك 6 مسارات موصى بها" — says less than three names); the audit log as the activity source (minimal by design, no titles); a separate activity endpoint (one payload is the dashboard's contract).

**Numbering note:** authored as D-074 on its feature branch, in parallel with Phase 5, whose merge claimed the number first; renumbered D-095 at rebase (as D-093's note explains).

## D-094 — The assessment keeps the sidebar, and a session draft makes leaving free
**Decision:** the assessment page renders inside the normal shell, with the two-item pre-assessment nav (D-071); results and path build stay bare. Answers and the current question are written through to `sessionStorage` on every change, keyed to the assessment id and its question ids; the draft is restored on return within the browser session, discarded if the bank has changed, and cleared on submit so a retake (D-015) starts clean.

**Why:** the original rule hid the rail on every flow page because a rail beside a step-by-step flow invites abandoning it. That holds for results and path build, which end in a decision. The assessment is different: its audience is the user with a two-item nav and a legitimate reason to check their profile mid-way, and thirty statements is long enough that being trapped is the worse experience. Letting them leave only works if leaving costs nothing — hence the draft. sessionStorage rather than the server: per tab, gone when the tab closes, holding option ids only (no text a person typed, no PII), and no new endpoint.

**Rejected:** a leave-confirmation dialog (nags instead of solving); losing answers silently; a server-side draft (survives devices, but a new endpoint and table for a convenience the session already covers); showing the rail on results and path build too (those should end in a decision, not a wander).

**Numbering note:** authored as D-073 on its feature branch, in parallel with Phase 5, whose merge claimed the number first; renumbered D-094 at rebase (as D-093's note explains).

## D-093 — One navigation loader for the whole app: a top progress bar, started at the click, completed by the route change
**Decision:** `NavigationProgress`, mounted once in the root layout, is the loader for moving between pages: a 3px primary bar along the top edge that starts the instant a navigation starts and completes when the route has changed. It starts from a capture-phase click listener (every internal link, `next/link` or not, same-origin, not a new window, not a hash, not a modified click), from `popstate`, and from `startNavigation()`, which `useAppRouter()` — the only router hook pages use — calls on `push`/`replace`. It completes on the pathname/search change, the App Router's only honest "the new page is in" signal. One polite "جارٍ الانتقال…" per navigation for assistive technology; the bar itself is `aria-hidden`. In-page data loading keeps `LoadingState`; the bar never speaks for a fetch.

**Why:** with client-side data fetching, a navigation often shows nothing for several hundred milliseconds — the old page is gone, the new page's `LoadingState` has not rendered yet — and a user clicks twice. A per-page solution would be inconsistent by construction; a per-link one (`useLinkStatus`) misses programmatic navigations, which are a third of ours. The bar is the pattern government portals and the web at large use for exactly this, and it costs no dependency.

**Numbering note:** this decision was authored as D-072 on its feature branch, in parallel with Phase 5, whose merge claimed D-072–D-092 first; renumbered D-093 at rebase. Commit messages referencing D-072 for the loader mean this entry.

**Rejected:** `loading.tsx` route files (they cover server-rendered segments, but these pages fetch on the client — the fallback would flash for a moment and then hand over to `LoadingState`, two loaders for one wait); a full-page overlay (blocks the page for a transition that usually takes under a second); a third-party progress library (this is 80 lines); wrapping `Link` (misses plain anchors and programmatic routes).

## D-092 — A provider never unmounts the page it is providing to

**Decision:** the three portal providers gate their loading state on `isInitialLoad`, not `isLoading`, and `PreferenceProvider` always renders `FormatProvider` — resolving "no preference" to the *inherited* context rather than returning `children` bare.

**Why:** both shapes destroyed the page underneath on a perfectly ordinary event. Gating on `isLoading` meant any refetch — `refreshSession` after saving a preference, for instance — swapped the whole portal for a spinner and unmounted everything below it. And returning `children` unwrapped when the preference was null changed the element type at that position, so the *first* time anybody saved a preference React tore down and rebuilt the entire subtree. Either way the confirmation the person had just earned vanished, along with any half-filled form, open dialog or scroll position: a successful save looked like nothing had happened.

**How it was found, which is the part worth keeping:** a browser test asserted `getByRole('status')` after saving. It passed — against the *loading* state, which carries that role too. The bug and the test that should have caught it were hiding each other. The assertions now name the confirmation's actual words, and the loose ones elsewhere were tightened with it.

**Also:** the null fallback is the inherited context, not `DEFAULT_FORMAT_CONTEXT`. The root layout resolves `NUMBER_FORMAT` from the environment, so a deployment can ship Arabic-Indic as its default; substituting a fresh default here would silently override that for everybody who never expressed a preference — the opposite of what null means.

**Rejected:** keying the subtree to force a controlled remount (same loss, deliberately); moving the confirmation into a toast outside the provider (hides a structural bug behind a different rendering path, and every other piece of page state would still be destroyed).

## D-091 — Changing an email is a request, then a confirmation, and the pending address lives on the token

**Decision:** `POST /auth/change-email` verifies the current password, applies the ministry-domain gate, and writes the new address onto an `EMAIL_CHANGE` token which is mailed to that address. `users.email` moves only when `POST /auth/confirm-email-change` redeems the token — at which point every session for that user is revoked.

**Why each part:**
- **On the token, not the user.** A `pending_email` column would open a window in which the account row points at an address nobody has proved they can read, and an abandoned request would leave that sitting there. On the token, an abandoned request expires into nothing and a second request supersedes the first through the same invalidation the verification flow already does.
- **The current password is required**, and for a sharper reason than the password change: whoever can move the address can then use "forgot password" and own the account outright, with the real employee locked out and receiving no notice at all.
- **The ministry-domain gate applies** (`checkEmailDomain`, extracted from the registration policy so the two cannot drift). Without it an employee could walk a ministry account to a personal inbox one profile edit at a time — D-017 defeated through the back door. The *rest* of the registration gate deliberately does not carry over: `admin-only` governs who may create an account, not whether an employee who has one may correct a typo, and the employee number is not being changed.
- **A taken address is answered exactly like a free one.** The caller is authenticated, but replying "that address already has an account" would turn the profile form into the address oracle the registration endpoint refuses to be. The audit entry carries the real reason.
- **Every session is revoked on completion, including the caller's.** The identifier the person signs in with has just changed, so being asked to sign in again with it is the honest next step — and if the request was not theirs, it ends the attacker's session too. It also cannot be "all except the current one": the link is usually opened in whichever browser the new mailbox is signed into, which is not the one that asked.
- **Its own redemption route,** not a branch inside `/verify-email`. The two tokens do different things to an account, and a single route that had to branch on token type is how a link meant for one ends up doing the other.

**Known gap, carried to Phase 6:** the *old* address is not warned that a change was requested. §2 keeps the notification list short and locked, and the current-password requirement means an attacker already holds the password before this endpoint is any use to them — so this is defence in depth rather than the primary control. It belongs in the security review, and it is on the deferred list rather than silently absent.

**Rejected:** changing the address immediately and sending a "confirm or we will revert" mail (leaves the account on an unproven address, and the revert never arrives if the mail bounces); skipping the domain gate as "it is only an edit" (that is exactly how the policy erodes); keeping the caller's session alive (leaves it authenticated against an address that no longer exists).

## D-090 — The digits options carry literal digits, and the guard makes room for exactly those
**Decision:** the two format options read "أرقام عربية (0123)" and "أرقام هندية (٠١٢٣)". `LITERAL_VALUE_PATHS` in the Arabic-catalogue guard grows a third pattern, `/^profile\.digits(Western|Arabic)$/`, alongside the two it already carried for setting hints and setting-validation errors.
**Why:** the guard exists because a digit typed into Arabic copy is a number that will not follow D-018 when the preference changes. These two are the exception that proves it: they are *specimens of the glyph set the reader is choosing between*, and the whole point is that both appear regardless of the current setting. Routing them through the formatting layer would render both options in the same digits and make the choice meaningless.
**Rejected:** a general "digits are fine in `profile`" exemption (the namespace has ordinary copy in it too); rendering the samples through `format.number` (produces two identical labels); naming the sets in words only (the names are ambiguous — each set is called "Arabic numerals" by somebody).

## D-089 — The digits preference is per-user and nullable; the language switch is deferred
**Decision:** §4.12 ships a digits preference (Western `0-9` ⇄ Arabic-Indic `٠-٩`) written through D-018's single switch point, stored on `users.number_format` as a **nullable** column, and no language selector. Null means "follow whatever §4C.6 has set" and is a real third option in the control, not a blank.
**Why:** §4.12 asks for a language control, but the interface is Arabic-only — a selector offering English would be a control that does nothing, which is worse than an absent one. What genuinely differs between readers is which digits they read, and D-018 already built the switch point. Nullable rather than defaulted so the ministry can change the system-wide default without overwriting anybody's expressed choice: "no preference" and "prefers Western" have to stay distinguishable.
**Deferred, not dropped:** the language switch returns when an English UI exists. Recorded here so a later reader finds a decision rather than a gap.
**Rejected:** a language selector with one option (a promise the product cannot keep); a non-null column defaulted to the system value (freezes every existing user to whatever the default was the day they registered).

## D-088 — Changing a password ends the other sessions, and requires the current one
**Decision:** `/auth/change-password` verifies the current password before doing anything, refuses a new password identical to the old one, and on success revokes every session for the user *except* the one making the request.
**Why:** a session cookie is enough to *be* the user, so without the current-password check anyone reaching an unlocked machine could take the account permanently and the owner would find out at their next sign-in. And the usual reason to change a password is that it may be known elsewhere — a change that leaves those sessions alive does not address the thing it was done for. Keeping the acting session is the other half: being signed out of the page you are standing on reads as a failure and invites a second change.
**Refused rather than accepted:** re-submitting the same password returns `PASSWORD_UNCHANGED`. Somebody who believes they have rotated a compromised password and has not is worse off than somebody told they did not.
**Rejected:** trusting the session alone (turns an unlocked screen into a permanent takeover); revoking every session including the caller (looks like the change failed); accepting an unchanged password as a no-op (silently false reassurance).

## D-087 — A message namespace is never also a label, and tests hold the line
**Decision:** `admin.auditAction` stays a namespace of action labels; the column heading that shares its meaning is `admin.auditActionLabel`. A test block asserts that every dynamically-keyed namespace — `auditAction`, `riasec`, `courseStatus`, `coursePublication`, `versionStatus`, `setting` — is an object of strings with no numeric keys.
**Why:** assigning `auditAction: 'الإجراء'` into the same object overwrote the namespace with a seven-character string, and `Object.assign` onto a string yields `{0..6}` — so every lookup returned undefined and next-intl's fallback rendered the raw code. The screen still worked, every test passed, and the output looked like a deliberate design. That is the failure mode worth a permanent test: a namespace collapsed into a string is invisible unless something asserts the shape.
**Rejected:** relying on the type checker (the catalogue is JSON, and the keys are dynamic by design); relying on review (the diff looked like one more label being added).

## D-086 — Catalogue sync tolerates a row that vanished under it
**Decision:** `withdrawVanished` uses `updateMany` and skips the counter and the audit entry when it matches nothing, instead of `update`, which throws.
**Why:** the list of vanished courses is gathered in one query and walked one row at a time. A reconciliation job that crashes because the thing it was about to reconcile is gone is reconciling badly — and the throw abandons every course after it in the list, so one missing row silently stops the run half way. There is nothing to withdraw from a row that is not there, and skipping the audit keeps the trail from claiming a course was withdrawn when no course was.
**Where it bit:** nothing in the product deletes a course (D-040 forbids it), so in production this is defensive. In the integration suites it is not: several create and remove courses of their own, and a sync running while one of them cleaned up failed a *different* suite roughly one run in five, with a Prisma error naming a line that had nothing wrong with it.
**Rejected:** serialising every course-touching suite behind the shared lock (a two-minute CI tax to work around a job that should not be brittle); leaving it and re-running CI (a flake that fails an unrelated suite is worse than a red build, because it teaches people to re-run).

## D-085 — Retiring a path removes it from new selections and strands nobody
**Decision:** `paths.is_active` governs *offering*, not access. A retired path stays fully usable to anyone who has already chosen it: My Path and certificates never consulted the flag, and `getDetail` — the build page — now resolves a retired path for the learner whose `user_paths` row points at it. `confirm` continues not to check the flag, so someone part way through choosing may still commit. A path is never deleted.
**Why:** §4C.4 has to let the ministry stop offering a path, and D-002 makes an existing choice permanent. Those two were already reconciled for the *confirmed* learner and not for the one still building: a plain `isActive: true` filter turned a retirement into a 404 on their build page, while `confirm` never checked the flag at all — so they could still commit to a path they could no longer see. That is the §2/D-015 stranding rule wearing different clothes, and it gets the same answer courses got: hidden from new selections, untouched for whoever holds it.
**Why commitment is still allowed:** refusing at the gate would strand somebody who had already picked five courses, for a decision taken after they picked them. Retirement means "not offered to anyone who has not already chosen it" — bounded, and it drains as those learners finish.
**Also decided:** no delete endpoint. `user_paths.path_id` is `Restrict` and a path certificate names the path on a document somebody holds, so removing a path anyone ever chose would falsify a credential.
**Made visible:** the detail screen prints how many learners are *building* against how many have committed, because the building count is the only group a retirement inconveniences and the decision should be made knowing it. The retirement audit entry records that number.
**Rejected:** refusing retirement while anyone is building (one indecisive learner blocks the ministry indefinitely); cascading a retirement into those learners' selections (destroys work they did under the old rules).

## D-084 — An active path always offers at least five selectable courses
**Decision:** activating a path is refused when fewer than `PATH_MIN_COURSES` of its courses are selectable, and so is any detach that would drop an active path below that floor. Creation always produces an inactive path.
**Why:** §2 requires five to ten courses to confirm, so a path offering four is one nobody can ever complete — and that is invisible from every screen. The learner reaches the build page, selects everything there is, and the confirm button stays disabled with nothing to act on. Nothing logs it and nothing alerts; the path just sits in the catalogue looking like a choice. The only place to catch it is where the path becomes offerable.
**Why "selectable" means AVAILABLE only:** `HIDDEN_BUT_COMPLETABLE` is the D-015 state — still completable by whoever holds it, gone from new selections — so counting it would report a path as offerable on the strength of courses nobody new can choose, which is the exact trap the count exists to avoid.
**Why the ceiling is not checked:** ten is the most a learner may *select*, not the most a path may *offer*. A path of thirty from which five are chosen is what §4.5 describes.
**Rejected:** warning instead of refusing (the cost falls on a learner who cannot tell what went wrong); checking only at activation (the floor would then hold for one instant and never again).

## D-083 — The seed bootstraps the assessment; it does not maintain it
**Decision:** `seedAssessment` writes version 1 only while version 1 is the *only* version of the instrument. Once an administrator has published an edit through §4C.3, the seed reports that the content is the ministry's and leaves every row alone.
**Why:** the seed upserted the bank by key on every run, which was right while the code owned the wording. After D-072 (copy-on-write) it would overwrite a published ministry version with whatever draft text shipped in the repository — on `npm run db:seed`, in a deployment script, in CI against a real database. That is data loss dressed as a convenience, and the loss is a career instrument the ministry authored.
**Also decided:** it says so on standing back rather than skipping quietly. A seed that appears to run and changes nothing is how somebody spends an afternoon wondering why their edit did not take.
**Consequence:** revising the seeded Arabic in `seed-data/assessment.ts` stops having any effect on an instance that has been edited. That is correct — after the first publish there are two authors and only one of them is authoritative — and it is what D-032 meant by "seeded data precisely so Phase 5 can edit it without a deploy".
**Rejected:** upserting unconditionally (overwrites published content); refusing to seed at all once any assessment exists (breaks `db:reset && db:seed` in development, which is the seed's main job); a `--force` flag (a flag that exists to overwrite ministry content will eventually be used to overwrite ministry content).

## D-082 — Two integration suites share one assessment, and an advisory lock serialises them
**Decision:** `journey.e2e-spec.ts` and `admin-assessment.e2e-spec.ts` each hold a Postgres advisory lock for their duration, so they never overlap. Every other integration suite continues to run in parallel.
**Why:** every suite namespaces its rows by a per-run id and they share one database happily. The assessment cannot be namespaced — §4.3 has one instrument, `getActive` finds the one ACTIVE row, and the partial unique index means there is deliberately no second one to hand a test. So publishing a version mid-run made the journey suite's submissions fail with `ASSESSMENT_NOT_FOUND`.
**Why the failure was not a bug to fix:** that refusal is the product working. A taker whose instrument was replaced part way through must be refused rather than scored against a bank they never saw, which is exactly what `submit`'s `status: 'ACTIVE'` filter is for. Weakening either suite to make them coexist would have deleted a real assertion to accommodate a scheduling artefact.
**Why an advisory lock rather than `--runInBand`:** running the whole integration suite serially costs about eight minutes of CI against a hundred seconds today. The lock costs four seconds, because only two suites contend and the rest keep running alongside them.
**Why on its own connection:** the lock is session-scoped, and Prisma's pool would hand the unlock to a different connection than the one holding it. Its other property is what makes it safe: the server releases it when the connection dies, so a crashed worker cannot leave a lock that fails every future run — which a lock *table* would.
**Rejected:** `--runInBand` (eight minutes for a two-suite problem); a lock table (a stuck row breaks every later run); retrying the journey submission (hides the real behaviour); giving the test its own assessment key (there is one instrument by construction, and inventing a second would make `getActive` ambiguous in production to make a test convenient).

## D-081 — Two lockouts are guarded, and converting a learner is refused
**Decision:** `account-changes.ts` refuses three administrative changes, as pure functions over facts the service gathers: an administrator changing **their own** status or role; any change that would leave **no active SUPER_ADMIN**; and converting an **EMPLOYEE who holds a result, a path or a certificate** to another role.
**Why they are three rules and not one:** self-modification and last-admin look alike and are not. Self-modification protects an individual from ending their own session with the screen that would undo it — a mistake one careful person avoids. Last-admin protects the ministry from losing the portal, and no amount of individual care prevents it: two administrators can each demote the other, one after the other, and neither has done anything wrong. The third is not a lockout at all but an orphaning: a converted learner's record survives (`user_paths.pathId` is `Restrict`, certificates are immutable), yet every screen that reads it is `@Roles('EMPLOYEE')`, so the person could not reach their own training history while their certificate stayed publicly verifiable in their name. The ministry case it resembles — an employee seconded to run a supplier account — is properly served by a second account.
**Why pure functions:** every rule here prevents a lockout or an orphaned record, which are precisely the cases an integration test can reach only by arranging the disaster first. Over plain objects they are enumerable exhaustively. Same shape as `checkRegistrationPolicy` (D-017) and `publishBlockers` (D-061), and for the same reason: the rules must hold for any caller, so they cannot live in a controller.
**Also decided:** suspending or changing a role **revokes every session**. For suspension this is not what makes it take effect — `SessionService.resolve` already refuses a suspended owner — it is what stops *reactivation* silently restoring every session that was live at suspension, including whichever one may have caused it. For a role change it is the point: a demotion would otherwise keep resolving against the old role until the session expired.
**Rejected:** enforcing these in the controller (a second caller bypasses them); allowing self-demotion with a confirmation dialog (a dialog is not a guard, and the failure is unrecoverable without database access); allowing the conversion and hiding the orphaned rows (the certificate stays publicly verifiable regardless).

## D-080 — An administrator provisions accounts by invitation and never sees a password
**Decision:** §4C.2 creates an account with a hash of 32 random bytes that nothing retains, then emails an **invitation** — a single-use `PASSWORD_RESET` token, redeemed on the existing `/reset-password` page — so the person chooses their own password. No endpoint returns a password and no screen displays one. As a necessary part of this, **redeeming a reset token now marks the email verified when it is not already** (`??`, never overwriting the original timestamp).
**Why not "generate one and show it once", as `prisma/seed.ts` does:** that produces a credential two people know, which then travels over whatever channel the administrator uses to pass it on — in a ministry, a chat message. The seed does it that way because a terminal has no mailbox to send to; a web portal does. The tests assert the *absence* against the whole serialised response and the whole rendered page rather than against named fields, because a later refactor adding `temporaryPassword` would satisfy every field-specific assertion.
**Why a `PASSWORD_RESET` token rather than a third token type:** it does exactly the same job — let somebody set a password the server has never seen — and is redeemed by the same endpoint and the same page. Only the email copy differs, and it has to: "someone requested a password reset; ignore this if it wasn't you" arriving at an address that has never had an account here reads as phishing.
**Why the reset now verifies the address:** redeeming a token that was emailed to an address proves control of that address, which is precisely what verification asserts. This also closes a dead end that already existed: `requestPasswordReset` accepts an unverified account, so it was possible to register, skip verification, reset the password, and still be refused at sign-in with `EMAIL_NOT_VERIFIED` — having just proved the mailbox was yours.
**Also decided:** administrative provisioning **bypasses the D-017 registration policy**. That gate governs *self*-registration, and `admin-only` mode exists precisely so an administrator can be the gate. It also has to: an entity contact is by definition not at a ministry address and could never be provisioned otherwise. Email and employee-id uniqueness are still enforced, by the database.
**Rejected:** an admin-typed password (two people know it); a generated password shown once (same, plus a relay channel); a third `INVITATION` token type (identical mechanics, one more state to keep correct); requiring an invited account to verify its email *and* set a password in two separate emails (two links, two chances to strand someone, for a fact one link already proves).

## D-079 — Report exports are CSV with a UTF-8 BOM
**Decision:** §4C.8's exports are CSV, written with a leading UTF-8 byte-order mark, served as `text/csv; charset=utf-8`.
**Why:** No new dependency, and the ministry opens these in Excel. Excel does not sniff UTF-8 without a BOM — it reads BOM-less UTF-8 as the system codepage and renders every Arabic name as mojibake. Three bytes are the difference between a usable report and an unreadable one, and every other consumer (LibreOffice, `csv` in Python, pandas) skips them.
**Rejected:** XLSX (a dependency, a binary format, and a writer to keep correct for one screen); JSON (not what a ministry analyst opens); BOM-less UTF-8 (mojibake in the one program that matters here).

## D-078 — Super-admin keeps unscoped API access to entity data, but has its own screens
**Decision:** `EntityController` stays `@Roles('ENTITY', 'SUPER_ADMIN')` and `EntityScopeService` continues to return `{entityId: null}` for an admin. But an admin's *browser* is routed to `/admin`, and §4C.5's course oversight is built as its own admin screens rather than by pointing an admin at the entity portal's UI.
**Why:** The scope resolver was written for exactly this — its own comment says so — and duplicating the read paths would give the two portals two chances to disagree about what a course's status is. The UI is a different matter. The entity screens are shaped around *one* organisation: "my courses", "my learners". An admin's questions are global ones those screens have no place to ask — which entity owns this course, which courses have no owner at all, which entity's catalogue is failing its learners. Reusing them would mean bending every entity screen around a caller it was not designed for.
**Rejected:** Giving the admin a second entity account scoped to nothing (a fiction, and it would need a fake `entities` row); dropping `SUPER_ADMIN` from the entity guard and writing parallel admin queries (two readers of the same rows, free to drift).

## D-077 — The 5–10 bounds stay hardcoded, and Settings shows them read-only
**Decision:** `PATH_MIN_COURSES` / `PATH_MAX_COURSES` remain constants in `packages/types`. §4C.6 displays them, labelled as fixed, and offers no control that changes them.
**Why:** §2 lists 5–10 among the non-negotiable product rules, beside one-path-no-switching. A knob is an invitation, and the failure mode is not an admin typing 4 by accident — it is an admin lowering the floor to 3 under pressure to make the product look easier, after which every path certificate issued means something different from every one issued before it. Showing the numbers read-only answers the question an admin actually has ("what are the limits?") without offering to change the answer.
**Rejected:** Database-backed bounds (turns a product rule into a setting); hiding them from Settings entirely (an admin asked to explain a rejected path build has nowhere to look).

## D-076 — Certificate template settings are text-only for now; the seal stays a placeholder
**Decision:** §4C.7 edits the signatory name, the signatory title and the issuing-body line, stored as settings and rendered into future certificates. The ministry seal remains the neutral placeholder mark from D-051. No file upload is built in Phase 5.
**Why:** The real artwork does not exist yet — it has been the first open blocker since Phase 3 — so an upload control would be a form with nothing to put in it, and building it now means designing storage, MIME validation, size limits and a rendering path against an asset nobody has seen. The three text fields are the parts that can be filled in today, and D-052's immutable rendered bytes mean the template can gain the seal later without disturbing anything already issued.
**Deferred to:** Phase 6/7, together with the artwork itself (still open blocker #1).
**Rejected:** Building the upload against a placeholder image (speculative work against an unknown asset); leaving the signature block hardcoded (the ministry cannot name its own signatory without a deploy).

## D-075 — Which settings move to the database, and which stay in the environment
**Decision:** A `settings` table holds the product knobs an administrator must change without a deploy: pass threshold, completion-sync interval, registration mode, allowed email domains, employee-ID pattern, number format, the notification toggles, and the Moodle base URL. Each falls back to its existing environment variable when no row is present, so the environment stays the source of the *default* and an unseeded database still boots. Secrets do not move: the Moodle web-services token, the database URL and the SMTP credentials stay environment-only and are never readable through the API.
**Why:** §4C.6 is only real if changing the pass threshold does not require a release — a ministry cannot redeploy to adjust a grade boundary. But "database-backed" must not become "two sources of truth": every consumer reads through one `SettingsService`, which is what makes the pass threshold's four call sites (completion sync, the course player, the entity course view, the verdict evaluator) agree by construction rather than by inspection.
**What this forces:** the sync interval is read once at boot to register a BullMQ repeatable job, so changing it must re-register that scheduler — `upsertJobScheduler` on the same job id is idempotent, which is what makes that safe rather than a way to double the polling rate. And a historical verdict must stay explicable: `completions.passThresholdUsed` already records the threshold each verdict was decided under (D-042), so lowering the threshold changes new verdicts while leaving old ones both unchanged and still explained.
**Why the token stays out:** a setting readable by the screen that edits it is a setting that appears in a network response. §5.1 and §2A say the token is server-side only. The base URL is not a secret; the token is.
**Rejected:** Moving everything including secrets (puts a credential behind an HTTP endpoint); leaving everything in the environment (§4C.6 becomes a read-only page and the ministry redeploys to change a threshold); caching settings inside each consumer (the divergence this decision exists to prevent).

## D-074 — The balance guard refuses; the interleaving rule only warns
**Decision:** Publishing an assessment version whose six dimensions do not share the same attainable maximum is **refused**, with Arabic copy naming the dimensions that differ. A version that places two consecutive questions on the same dimension is **published with a warning** the admin may proceed past.
**Why the difference is not arbitrary:** the two rules protect different things. Balance protects *correctness* — ranking compares raw scores across dimensions (D-032), so an unbalanced bank makes the Holland Code an artefact of how many items each dimension happened to get, and every downstream recommendation inherits the skew silently. Adjacency protects *presentation* — five consecutive questions on one dimension read as a labelled section and invite block answering, which is a real effect on data quality but a weaker one, and an admin may have a defensible reason to accept it. Refusing both would make the editor obstructive in the way that teaches people to route around it; warning on both would let a skewed instrument ship.
**Where the guard runs:** over the *proposed* bank, server-side, at publish. `isBalancedBank` already expresses the property over attainable maxima rather than item counts, so it catches an unbalancing weight edit as well as an unbalancing question add — the same function CI already asserts over the seed constant.
**Rejected:** Refusing an unbalanced *save* (an admin cannot get from a balanced five-per-dimension bank to a balanced six-per-dimension one without passing through illegal intermediate states); auto-rebalancing (the editor would be inventing assessment content); switching ranking to normalised percentages instead (D-032 offers it as the alternative to balance, but it changes scoring, which D-048 forbids an admin-facing feature from doing).

## D-073 — An assessment edit is drafted, then published; the guard fires at publish
**Decision:** Editing the assessment produces a **draft version** — a full working copy of the bank that an admin may leave temporarily inconsistent — and a separate, deliberate **publish** step that validates it and makes it the active assessment. Balance is checked at publish, not on each save.
**Why:** Going from a balanced thirty-item bank to a balanced thirty-six-item bank means passing through six unbalanced states. A guard on every save would make the legal destination unreachable except by an ordering trick, which is the kind of rule people learn to defeat rather than obey. It also gives the admin somewhere to work: an assessment revision is a content task done over an afternoon, not one atomic edit. D-072's copy-on-write already gives the draft a natural home — it is simply the next version before it becomes active.
**Consequence:** at most one draft version exists at a time, and the active version is never the one being edited. A learner mid-assessment is unaffected by an edit in progress, and unaffected by the publish too — their submission scores against the version they were served.
**Rejected:** Immediate-effect edits (no safe intermediate state, and no moment at which an admin confirms what they are about to do to future takers); a free-text "publish notes" field (untyped, and nothing reads it).

## D-072 — Assessment versioning is copy-on-write; a published edit is a new version, and the old bank is kept
**Decision:** Editing the assessment does not mutate the live bank. Publishing an edit creates a **new `Assessment` row** at `version + 1` carrying its own copy of every question, option and weight; the previous row is set `isActive: false` and kept forever, with the questions and options that past responses reference intact. `assessment_results` rows continue to point at the version they were scored against.
**Why:** D-049 says existing results are "frozen as taken", and only this makes that literally true. A result is not just six numbers — it is those numbers *plus the instrument that produced them*, and `assessment_results.assessmentId onDelete: Restrict` (D-035) is a promise that the instrument still exists. Editing in place and bumping an integer would keep the scores frozen but let a wording change rewrite the questions a past response points at, so a row would claim to have been scored under version 3 while resolving to version 7's text. Months later, asked to explain why someone was recommended a path, we could produce the score but not the questionnaire that produced it. For a government system whose certificates and career paths flow from that result, that is not an acceptable gap.
**Also:** it makes "version + effective date" a fact rather than a label — each row carries its own `effectiveFrom`, and the sequence of rows *is* the history.
**Cost, and why it is acceptable:** each published edit copies roughly 30 questions, 150 options and 150 weights — a few hundred small rows. Assessment edits are rare ministry content decisions, not a per-request write path, and the alternative is spending that storage on a history that cannot be reconstructed.
**Rejected:** Edit-in-place plus a version integer (freezes the scores but not the instrument; the `Restrict` reference stops meaning what it says); soft-retiring individual questions inside one assessment row (the bank becomes the union of every question that ever existed, and "which thirty items did version 4 actually ask?" needs a temporal query nobody will write correctly); snapshotting the bank as JSON onto each result (duplicates the bank per *taker* rather than per version, and puts the weights somewhere D-034 says they must not be).
## D-071 — No catalogue before the assessment: the sidebar hides Courses and the URL agrees
**Decision:** for a user in `PRE_ASSESSMENT` the navigation is Dashboard and Profile only; Courses joins it the moment the assessment is done (`ASSESSED_NO_PATH`), My Path, Certificates and the CV once a path is active. A pre-assessment visit to `/courses` or any route under it is redirected to the dashboard by `PortalProvider`, beside the existing 401 and wrong-portal redirects, with the loading state shown in the meantime so the catalogue never flashes. The courses **API stays open**.

**Why:** a brand-new user has exactly one meaningful action — take the assessment — and the dashboard's single card already says so. A browsable catalogue before any recommendation exists competes with that action and invites choosing courses by browsing rather than by fit, which is the failure mode the whole product exists to remove. The nav and the URL must agree: a hidden menu item with a working URL behind it is a nav that lies. The API is left open deliberately: catalogue data is not sensitive, every mutation (adding a course to a path) is already server-gated behind a confirmed path, and closing a read endpoint would buy nothing but a second place for the rule to drift.

**Supersedes:** CLAUDE.md §4.2's "Dashboard, Courses, Profile" and §4.6's "available even pre-assessment", both amended.

**Rejected:** hiding from the nav only (the URL still works — the lie above); a gate page at `/courses` ("finish the assessment first") — a dead end that duplicates the dashboard's card; closing the API (see above).
## D-070 — Auth pages are a centred government template on the Platforms Code form anatomy; axe is a permanent gate
**Decision:** the five authentication pages share `AuthLayout` — a slim header naming the owner (ministry emblem, Tamkeen logo, a visible exit to the landing page), one centred card with the emblem over the form, a footer strip, a decorative lattice behind — and the shared form primitives carry the Platforms Code field anatomy: `Input` (36px, radius 4, neutral-400 edge darkening on hover, primary focus ring), `Field` (semibold label, required mark before the label and kept out of the accessible name, icon + text error row), `PasswordInput`, `Select`, `Alert`. Because the primitives are shared, every form in the portal wears the anatomy too. An axe run (WCAG 2.1 A/AA) over the five pages at three widths is part of the e2e suite.

**Why:** the epic's original design — a two-panel split with a marketing panel — was the reference repo's layout, the very source the project stopped following when it adopted Platforms Code (D-069). Government sign-in pages (Absher, Nafath, the DGA's own examples) are centred and framed by the owner; the reader should recognise the ministry before the form. "Following the DGA" on a form page is mostly its form anatomy, not its colours, so that had to land in the primitives rather than in five page files. §4.1's "single-column, centred" therefore stands unamended.

**Registration** is a two-step wizard (account, then employee) in one client component with local step state; each step validates the shapes the server enforces before advancing, the server stays authoritative, and a server error returns the user to the step that owns the field. The department is a closed list (`DEPARTMENTS`, a placeholder until the ministry supplies the official one; the server still accepts any non-empty string until then).

**Rejected:** the two-panel shell (built, then discarded — see above); a nested tablist for the wizard steps (one level of tabs is enough for a screen reader); applying the field anatomy to auth only (two anatomies in one app); hand-reviewing accessibility per PR instead of gating it.

## D-069 — The visual foundation is the DGA's Platforms Code, adopted in full — superseding the Tamkeen brand palette (D-009, D-025)
**Decision:** the product's design tokens are those of **Platforms Code (كود المنصات)**, the Digital Government Authority's national design system, adopted **in full including the palette**: the Saudi-flag green primary scale, the gold secondary scale, the neutral scale and the semantic status colours, plus its radius scale. The navy/gold/cream brand of D-009 is retired; `--color-navy`, `--color-navy-soft`, `--color-gold-light` and `--color-cream` no longer exist and the contrast test asserts their absence. Typography is unchanged — IBM Plex Sans Arabic is also Platforms Code's typeface (D-023 holds). Source of truth is the official site (`design.dga.gov.sa`) and Figma library; the values were taken from the system's published token export, and must be re-checked against the official foundations by someone with Figma access (open item in progress.md).

**Why:** this is a Ministry of Interior platform. The national design system is what the ministry and its employees already recognise across government services; a private brand — however carefully measured — reads as a vendor product. The decision was forced into the open by the landing page (PR #5), rebuilt faithfully from the reference repo and still looking like a generic template: the problem was never the porting but the absence of an authority on what a government page should look like. Adopting Platforms Code supplies that authority.

**What survives, re-homed:** *gold means recommended* (§3A) survives, now on Platforms Code's own gold secondary — which is the system's intended role for it. The measured-contrast discipline of D-025 survives in full: Platforms Code's "primary gold" (gold-600, `#dba102`) is 2.3:1 on white, so it is **not** valid as text, as a border, or behind white text. Gold edges use gold-700 (3.5:1, non-text only), gold text uses gold-800 (5.5:1), and a gold fill carries display text (neutral-800 on gold-600 is 6.3:1 — the one way gold-600 may carry text, and something the old brand gold never allowed) or uses the gold-100 tint with gold-900. The contrast test enforces all of it; the palette being national does not exempt it from measurement.

**Addendum (same day, user direction):** Platforms Code's **gold secondary is not adopted**. The product uses one accent — the primary — for actions, recommendation and achievement alike; buttons follow the system's state tokens (primary 600/700/900, danger 600/danger/900, neutral, on-color). The gold tokens, the `achievement` button variant and the gold certificate frame are gone; the path certificate is distinguished by the deep-primary frame and filled seal instead. The measured gold restrictions above are therefore moot, and stay only as the record of why a second accent was examined and dropped.

**Scope:** the palette is global by construction — every shadcn semantic role derives from these tokens — so the whole app, the certificate PDF, the emails and the QR code recoloured in one change. Component and pattern alignment (templates, mandatory government header/footer elements, the landing page and auth screens rebuilt on Platforms Code patterns) is staged separately: public surfaces first, the signed-in portal after.

**Rejected:** Platforms Code for structure only with navy/gold kept as a ministry theme (defensible under its theming model, but it keeps the one thing — the colour — that makes a government page recognisable as one, and leaves two palettes to reason about); principles-only adoption (a checklist, not an identity); keeping the reference repo as the design source (it was the source of the template look). Also rejected: aliasing the old token names to new values so nothing had to change — it would have left `bg-navy` painting green, which is a lie the next reader pays for.

## D-068 — Every id the mock LMS hands out derives from a natural key, never from a counter
**Decision:** `MockLmsService` derives user ids from the email and course ids from the shortname, both through the same FNV-1a helper. No id is produced by an in-memory counter. The property — that a fresh port instance does not reissue an id an earlier one gave out — is asserted in the **shared LMS contract**, not in the mock's own tests.

**Why:** the mock's state dies with the process; the rows it seeded do not, and `users.moodle_user_id` and `courses.moodle_course_id` are both UNIQUE. A counter that restarts therefore hands a *new* record an id an *existing* row already holds, and the failure lands on the constraint — far from the mock, and looking nothing like its cause. This has now happened twice: once for user ids in Phase 2 (enrolment died after a restart), and once for course ids in Phase 4, where it surfaced as a 500 in the first test of the entity suite after an earlier run left a course behind. Fixing the second one the same way the first was fixed is the point of writing it down as a rule rather than as another patch.

A real Moodle has this invariant for free, because its ids live in a database. That is precisely why the assertion belongs in the contract: it is a property of *the port*, which the real adapter satisfies without trying, and the mock only satisfies deliberately. Keeping it in the mock's own spec would let a future implementation quietly drop it.

**Consequence:** ids are no longer sequential, so nothing may assume "the next created course is the previous id plus one". Nothing did. Two different natural keys could in principle hash into the same id; the space is a million wide against a handful of courses, and the caller already randomises the shortname per course, so this is not worth defending against in a mock.

**Rejected:** seeding the counter from the database at construction (the mock would need Prisma, and an in-memory fake that reads the real database is no longer a fake); a random base per process (fixes the collision but makes the mock unreproducible run to run, which the contract suite depends on); cleaning the database before every run instead (treats the symptom, and the third occurrence would land on whoever forgot).

## D-067 — Both providers correct a mis-routed account, and 403 is why the second one was missing
**Decision:** `PortalProvider` redirects a signed-in non-`EMPLOYEE` to `/entity`, mirroring `EntityProvider`'s existing redirect of an `EMPLOYEE` to `/`. This makes real the claim D-065 already made — "each provider redirects a caller who does not belong to it" — which was only half true when it was written.

**Why:** the learner provider treated *401* as "not signed in" and everything else as a data failure. That was correct until this phase applied `@Roles`, after which the journey dashboard answers **403** to an entity — signed in, just not entitled. Nothing above read that as a routing problem, so the page settled on the generic error card with a retry button that could never succeed: the one state §2B says no data view may rest in. The asymmetry was invisible because the entity side was written first and the learner side was never asked the question.

The redirect stays a **courtesy, not a control**, exactly as D-065 says: the API refuses cross-portal reads regardless of what the browser renders (D-062). Nothing here loosens authorisation; it only replaces a dead end with a destination.

**Consequence:** the check reads `session.data.role`, which exists only once someone is signed in, so the signed-out visitor is untouched and `/` still renders the public landing page for them. Both directions are asserted in the browser, and the root is asserted explicitly because it is also the landing page.

**Rejected:** treating 403 like 401 and bouncing to `/login` (a signed-in user sent to a sign-in form they do not need, who signs in again and arrives back at the same page); rendering an "wrong portal" explanation with a link (a screen whose only content is a link is a redirect with extra steps, and §3 forbids the redundant UI); a server-side redirect (the session cookie belongs to the API origin — the same reason D-037 and D-065 rejected middleware).

## D-066 — A course's RIASEC letter is derived from its paths, never authored beside them
**Decision:** §4B.3 asks an entity to set "path(s) the course belongs to, its RIASEC letter (consistent with the path)". The entity sets **only the path membership**; the course's RIASEC letters are **derived** from the paths it belongs to and shown read-only. There is no `riasec_letter` column on `courses`, and the metadata endpoint rejects the field outright.

**Why:** §3A makes the *path* the owner of the letter — "every path is tagged with exactly one primary RIASEC letter", and the gold recommendation compares a path's letter against the learner's Holland Code. A separately authored letter on the course would be a second source for the same fact, and the two can disagree: a course tagged `S` sitting inside an `E` path is a state the product has no rule for resolving, and nothing downstream would even notice, because the recommendation never reads a course's letter. The parenthetical "consistent with the path" is precisely the constraint that deriving satisfies **by construction** rather than by a validation someone has to write, remember and keep correct as paths change.

It also survives change correctly. If an admin re-tags a path in Phase 5 (§4C.4), every course in it follows automatically; a stored copy would silently keep asserting the old letter until somebody noticed and rewrote it course by course.

**Consequence:** a course in several paths carries several letters, which is the honest answer — D-003 already allows a course to belong to more than one path, and the learner-facing card has shown a list of paths since Phase 1. A course in no path has none, and cannot be published at all (`NO_PATH`), so the empty case never reaches a learner.

**Rejected:** a `riasec_letter` column on `courses` validated against the path's on save (two sources of truth, kept in step by a check that only runs on one of the two edit paths — nothing re-validates when the *path* is re-tagged); asking the entity to pick a letter and inferring the path from it (backwards — a path is a curriculum, not a letter, and several paths share a letter).

## D-065 — The entity portal is its own route group, and sign-in routes by role
**Decision:** Entity pages live under `apps/web/src/app/(entity)/`, a sibling of `(portal)` with its own `EntityProvider`. Sign-in reads the role off the session and sends an `ENTITY` to `/entity`, everyone else to `/`. Each provider redirects a caller who does not belong to it.
**Why:** `PortalProvider` loads `dashboardApi.get()` — the *learner journey* dashboard — for every page beneath it, and `navForState()` derives the navigation from that journey. An entity has no journey: no assessment, no path, no certificates. Reusing the group would mean an entity account fetching a dashboard that describes a product they do not use, to render a nav computed from a state they can never be in. Two groups keeps each provider loading exactly what its portal needs, which is the same reasoning D-037 used to justify loading the session once.
**Also:** the redirect is *belt and braces* — the API is the authority (D-062) and refuses cross-portal reads regardless of what the browser renders. A client-side redirect is a courtesy to a mis-routed user, never a control.
**Rejected:** one route group branching on role inside the provider (every page then pays for both portals' data, and the nav logic grows a second axis); a middleware redirect (the session cookie belongs to the API origin, so the check would have to be duplicated server-side — the same reason D-037 rejected it).

## D-064 — What an entity may see about a learner
**Decision:** The Learners/Review screens expose a learner's **full name, department, per-course progress, grade and completion state** — and nothing else. Not email, not employee ID, not their Holland Code, not their path, not their certificates, and no course of theirs this entity does not own.
**Why:** §4B.5 asks for "no PII beyond what review requires", and review requires identifying the person and seeing how they did on *this entity's course*. Email and employee ID are the two identifiers that make a leaked export directly actionable elsewhere in the ministry, and neither helps a reviewer — name and department already identify a colleague unambiguously enough to raise a concern about. The Holland Code and the chosen path are the learner's career intentions; an outside organisation supplying one course has no claim on them, and exposing them would let an entity reconstruct a ministry-wide picture of who is trying to move where.
**Consequence:** the review query selects columns explicitly and never spreads a `user` row, so a later `select: { user: true }` cannot quietly widen it. A test asserts the response shape carries no `email` and no `employeeId`.
**Rejected:** showing the employee ID "so the entity can raise an issue with HR" (an entity does not talk to ministry HR; the ministry does, and it holds the id); anonymising the learner entirely (a reviewer who cannot name the person cannot act on the review, which is the screen's purpose).

## D-063 — `entities` is a first-class model, and course ownership is nullable
**Decision:** A new `Entity` model (organisation name, contact name, contact email, status) with `users.entity_id` linking an `ENTITY`-role account to it, and `courses.owner_entity_id` recording which entity supplies a course. **`owner_entity_id` is nullable.**
**Why nullable, which is the part that matters:** the catalogue already holds 48 seeded courses and, in real mode, whatever the LMS returns — none of which any entity authored. Making ownership mandatory would force a fiction: either inventing an entity to own them, or refusing to sync a course the LMS legitimately has. D-040 already established that a course the LMS has and we have never seen "arrives with no product metadata… a legitimate state, not an error". Ownership is product metadata, so it inherits that. An ownerless course is simply one no entity may see or manage; the super-admin manages it in Phase 5.
**Why an entity is not just a `User` with a role:** several people may work for one supplier, and the courses belong to the *organisation*, not to whoever created them. Hanging ownership off a user id would orphan a catalogue the day that person leaves — the exact failure a government system cannot absorb.
**Rejected:** a required owner with a synthetic "ministry" entity (a real row standing for nobody, which every query then special-cases); ownership as many-to-many (nothing in §4B describes co-owned courses, and a join table would make "only your own courses" a subquery rather than an equality).

## D-062 — `@Roles` on every endpoint, and scoping is a query filter rather than a guard
**Decision:** Two separate mechanisms, deliberately not conflated.
1. **Role**, declared with `@Roles(...)` on every controller: the Phase 1–3 learner endpoints become `@Roles('EMPLOYEE')`, the new entity endpoints `@Roles('ENTITY', 'SUPER_ADMIN')`. `RolesGuard` has existed since Phase 0 and, until now, **guarded nothing** — no endpoint declared a role, so an `ENTITY` account could take the assessment and confirm a path.
2. **Scope**, enforced inside each entity service as a `where` clause derived from the caller's `entity_id`: `EntityScopeService` resolves it once and every query filters on it.
**Why the two are separate:** a role answers "may this kind of account call this endpoint"; a scope answers "which rows may *this* account see through it". Expressing the second as a guard would mean the guard had to run the query to know whether to allow it. Keeping it in the service also means it cannot be bypassed by a second caller of the same logic — the rule the audit log already follows (`audit.actions.ts`: log from the service, never the controller).
**Why the scope fails closed:** `resolveScope` throws `ENTITY_SCOPE_MISSING` when an `ENTITY` account has no `entity_id`, rather than falling through to an unfiltered query. A half-provisioned account must see nothing, not everything — the inverse is how a scoping bug becomes a data breach.
**Consequence for Phase 5:** `SUPER_ADMIN` is allowed onto entity endpoints and is deliberately **unscoped**, which is what §4C.5's global course oversight needs. That is the one place `resolveScope` legitimately returns null, and it is written as an explicit branch rather than an absent filter, so an admin's unscoped read is a visible decision in the code rather than the default.
**Rejected:** granting `SUPER_ADMIN` every role implicitly (D-027's decorator comment already rejected it: implicit inheritance is how an admin acquires a write path nobody designed for them); leaving the learner endpoints unroled "because only employees have accounts" (they do not — this phase creates entity accounts); Prisma middleware applying the filter globally (invisible at the call site, and it would have to guess which models are entity-owned).

## D-061 — The content read-back exists to stop an uncompletable course being published
**Decision:** §4B.4's read-back is not a summary for its own sake. It reports, for a course in the LMS: how many activities it holds, whether any of them is a quiz, and **whether course completion is configured at all**. Publishing is refused — not warned about, refused — when the LMS reports no completion criteria.
**Why:** D-042 named this failure and Phase 2 could only detect it *after the fact*: `isGradedButNotComplete` spots a learner who scored above the threshold on a course the LMS will never call complete, because nobody configured completion criteria. Such a course reports `completed: false` forever, so **no learner on it can ever pass and no certificate can ever be issued**, with nothing in any log to say why. Phase 2 could log it; only Phase 4 can prevent it, because Phase 4 is where a human decides the course is ready. Catching it at the publish gate turns a silent product failure — discovered weeks later by a confused learner — into a sentence on the screen of the person who can fix it.
**Why refuse rather than warn:** a warning on a publish button is dismissed. The cost of a wrong refusal is that an entity configures completion in Moodle and clicks publish again; the cost of a dismissed warning is a cohort of learners who cannot finish. Those are not comparable.
**Rejected:** inferring completability from the presence of a quiz (a quiz is neither necessary nor sufficient — completion criteria are configured separately and may key on anything); blocking on grade setup too (we do not know the entity's intent for an ungraded course, and D-007 keeps the threshold ours, so this stays the one structural check).

## D-060 — The course shell is created in Moodle, and entities author it as `editingteacher`
**Decision:** Creating a course creates it **in the LMS first**, through a new `LmsPort.createCourse()`; our `courses` row is written from what the LMS returns. The entity is then enrolled into their own course with `MOODLE_TEACHER_ROLE_ID` (`editingteacher`) and reaches it through the **existing, unmodified** `local_tamkeensso` handoff, landing on the course page where Moodle's own Edit mode is available.
**Why the shell cannot be ours alone:** `courses.moodle_course_id` is non-null and unique, and catalogue sync withdraws any row the LMS stops returning. A course row created without an LMS counterpart would be withdrawn on the very next sync run, minutes after the entity created it. A DB-only shell is not a lighter version of this; it is a row that self-destructs.
**Why the plugin is not touched:** the obvious change is a `target` claim so the handoff can land on `/course/edit.php`. It is not worth it. `local_tamkeensso` is **the open governance blocker** (D-044) — ministry approval of custom PHP on their Moodle is still unconfirmed — and every byte added to it enlarges what has to be approved and re-reviewed. Landing on the course page costs the entity one click on Moodle's Edit toggle and costs the project nothing. The security argument also holds *only because the token is unchanged*: it still binds one user and one course, so an authoring launch grants exactly what a learner launch grants, to someone who additionally holds the editing capability. Widening the token to carry a target is the kind of change that quietly turns a reviewed credential into an unreviewed one.
**Why the role is configuration:** D-039 already made `MOODLE_STUDENT_ROLE_ID` configuration for this reason — role ids are per-instance and we do not control the ministry's Moodle. A hardcoded `3` meaning something else there would hand an outside organisation the wrong capabilities, which is worse for a teacher role than for a student one.
**Also:** `MOODLE_COURSE_CATEGORY_ID` is required in real mode, because `core_course_create_courses` demands a category and guessing one puts ministry courses wherever happens to be first.
**Rejected:** a DB-only draft promoted to a real course at publish time (moves the failure to the worst moment — the entity has authored nothing, because there was nowhere to author it); adding a `target` claim to the handoff (reopens D-044 to save a click); enrolling the entity as `manager` (site-wide capabilities where course-scoped ones suffice).

## D-059 — Publication is ours, visibility is the LMS's, and `status` is derived from both
**This is the central Phase 4 decision, and it corrects a real defect rather than adding a feature.**

**The defect.** `fieldsForPublishedCourse` recomputes `courses.status` from the LMS's `visible` flag on every sync run, protecting only `RETIRED` from being overwritten. So an entity that hid a course would have it flipped back to `AVAILABLE` by the next scheduled sync — silently, minutes later, with the entity's decision nowhere in the database to appeal to. D-040 rule 3 already says "sync writes only what the LMS owns"; `status` was quietly violating it, because `status` was two facts wearing one column: *what the LMS says about this course* and *what we have decided about it*.

**Decision:** split them.
- **`courses.publication`** — `DRAFT | PUBLISHED | UNPUBLISHED`. **Ours.** Written only by an entity or an admin. Catalogue sync never writes it, reads it only as an input, and cannot change it under any circumstances.
- **`courses.lms_visible` and `courses.lms_present`** — the LMS's two facts: whether it shows the course, and whether it still returns it at all. **Theirs.** Written only by sync.
- **`courses.status`** — no longer authored by anyone. It is **derived** from the three above plus whether any learner holds the course, by one pure function, `effectiveCourseStatus`, in `catalog-mapping.ts`. Every writer — sync, publish, unpublish, hide — calls it. Nothing sets `status` directly.

**The full derivation, total by construction:**

| publication | lms_present | lms_visible | held by a learner | → status |
|---|---|---|---|---|
| `DRAFT` | any | any | any | `DRAFT` |
| `UNPUBLISHED` | any | any | yes | `HIDDEN_BUT_COMPLETABLE` |
| `UNPUBLISHED` | any | any | no | `RETIRED` |
| `PUBLISHED` | no | any | yes | `HIDDEN_BUT_COMPLETABLE` |
| `PUBLISHED` | no | any | no | `RETIRED` |
| `PUBLISHED` | yes | no | any | `HIDDEN_BUT_COMPLETABLE` |
| `PUBLISHED` | yes | yes | any | `AVAILABLE` |

`DRAFT` joins `CourseStatus` as a fourth value, invisible to learners exactly as `RETIRED` is. It is needed because a course whose shell exists in Moodle but whose path, RIASEC letter and metadata are not yet set must not appear in the catalogue — and it must be *reversibly* absent, which `RETIRED`, being an end state, is not.

**Why this satisfies §2/D-015 more strongly than the old code did.** Course-edit protection is now a property of the derivation rather than a check someone has to remember: **there is no combination of inputs in which a course a learner holds becomes invisible to them.** Unpublishing a held course degrades it to `HIDDEN_BUT_COMPLETABLE` — gone from new selections, still completable — and the forbidden state is *impossible to express*, rather than merely guarded against. Deletion is not offered anywhere in the entity portal at all.

**A deliberate revision of D-040.** D-040 held that "a `RETIRED` course is not resurrected by the LMS making it visible again — reinstating is a human action." Under this model a `PUBLISHED` course that vanished and came back does return to `AVAILABLE` automatically. That sub-rule existed only to stop the LMS overriding a human decision, and it worked by making `status` sticky because there was nowhere else to record the decision. Now there is: the decision lives in `publication`, where the LMS cannot reach it. An entity that genuinely wants a course gone sets `UNPUBLISHED`, and no sync run will ever undo that. Stickiness on a derived column would now do the opposite of its purpose — it would freeze a stale *LMS* fact and require a human to clear something no human decided.

**The entity is told what will happen, not surprised by it.** Because unpublishing a held course yields `HIDDEN_BUT_COMPLETABLE` rather than `RETIRED`, the API returns the resulting status and the number of learners still holding it, and the confirmation says so. Silently degrading the request would leave an entity believing a course was withdrawn when learners can still take it.

**Rejected:** deriving `status` at query time instead of storing it (`visibleCourseFilter` builds a Prisma `where` on `status`; deriving would mean writing the rule a second time in SQL — the two-implementations failure D-034 exists to prevent); a single `publication` column with no `status` at all (every learner-facing query would then join `user_path_courses` to know whether a course is completable); extending the "existing value wins" rule to `status` (that is what `durationMinutes` does, and it works there because nothing *derives* duration — for `status` it would preserve stale LMS facts as readily as real decisions); keeping `DRAFT` out of `CourseStatus` by inferring it from a null `published_at` (a fourth state only some code paths know about is how `visibleCourseFilter` acquires a bug).

## D-058 — The in-app notification is a dot, cleared by arriving
**Decision:** The certificate indicator is a **dot, not a count**, on exactly one nav item, paired with visually-hidden text. There is no inbox, no feed and no list endpoint; the whole API surface is "how many are unseen" and "mark them seen". Opening the gallery **is** the acknowledgement — there is no dismiss control. Notification rows are written where the thing they announce happens, never by anything a browser can call.
**Why:** §2 permits "a light indicator when a new certificate is issued. Nothing more." A number invites checking, which is the engagement nagging §2 rules out; a dismiss button would be a second thing to do about a dot; and a list endpoint would duplicate the gallery, which already renders the actual content. Keeping writes out of the browser's reach means the indicator can only ever reflect something the system really did. `updateMany` filters on `readAt: null` so re-opening the gallery does not overwrite when each certificate was first seen — the only thing that column records.
**Rejected:** a badge count (invites checking); a notification centre (an engagement surface §2 forecloses); marking read via a button (a second action for a dot); blocking the portal's render on the indicator request (trading the product for a dot).

## D-057 — The CV stores what the learner authored and never what the system knows
**Decision:** `cv_profiles` holds only authored content. Certifications, the account name/department, the path and the Holland Code are **recomputed on every load** and never written to the row. The repeating sections (experience, education, skills, external certifications) are stored as **JSON**.
**Why (the split):** copying system-known values in would let a CV outlive the record it was drawn from — claiming a certificate its holder no longer has, or a department they left. The certifications section is trustworthy precisely because it is a *read of `certificates`* at load time rather than a field with a default. The same boundary holds at the HTTP edge: the DTO does not declare those fields, so `forbidNonWhitelisted` turns "post yourself a certification" into a 400 rather than something silently dropped.
**Why JSON, when D-035 argued the opposite:** because of what the data is *for*. Option weights are an enum-column table so a mistyped letter cannot fail silently; nothing, by contrast, queries across a learner's job history. It is written whole, read whole and rendered whole into one document, so a normalised table would buy joins nobody makes and cost the reordering and partial edits a CV form does constantly. §6 sanctions it explicitly ("structured JSON sections ok"); the shapes are validated at the API boundary against the shared types, with bounds enforced server-side as well as in the form.
**Rejected:** persisting a snapshot of certifications (goes stale, and invites forgery); normalised tables per section (joins nobody makes, reordering pain); unbounded JSON (a storage problem, and a rendering one once a browser lays it out into a PDF).

## D-056 — One CV renderer, shared by the preview and the PDF; `en` joins LOCALES
**Decision:** The CV document — its markup and its stylesheet — is a pure function in `@tamkeen/types`, used by both the live preview in the browser and the PDF rendered in the API. The two differ only in how the typeface is loaded. Separately, `'en'` is added to `LOCALES` with a fixed `CV_FORMAT_CONTEXT`.
**Why:** §4.11 asks for a live preview *and* a PDF export. A preview that differs from the export is worse than no preview, because it promises the learner something the file will not deliver, and two implementations of one layout drift on the first change either side. This is D-024's reasoning — "a certificate PDF disagreeing with the screen that announced it is a real failure mode" — applied to the whole document rather than just its dates. It stays inside the package's charter: no runtime dependencies, no framework code, one pure function from data to a string.
**Why `en`:** the CV is an English document (D-050), so its dates must read "March 2021", and they must still come from the formatting layer rather than a stray `Intl` call in a template (D-018). This does **not** make the app bilingual: `DEFAULT_LOCALE` is unchanged, `<html lang>` is still Arabic, the API config still accepts only `ar`, and there is no English catalogue. `CV_FORMAT_CONTEXT` is deliberately fixed rather than switchable — the CV's language is a product decision, and letting the D-018 digit switch reach it would put Arabic-Indic numerals on an English CV.
**Rejected:** a React preview beside a string template in the API (guaranteed drift); fetching rendered HTML per keystroke (a round trip for a "live" preview); an approximate preview (the thing §4.11 asked for, made untrue).

## D-055 — Node 24, and Puppeteer loaded lazily
**Decision:** `.nvmrc` moves from Node 20 to **Node 24 LTS**, and `PdfRendererService` imports Puppeteer with a lazy `await import()` rather than at module load. CI caches the Chromium download.
**Why:** Puppeteer 25 ships **ESM only** while the API compiles to CommonJS, so loading it needs Node's `require(esm)` support. That forced the version question, and the answer was overdue independently: **Node 20 is past end of life**, which is not a runtime to launch a government system on. Node 24 is current LTS and already what the development machine runs, so dev and CI now agree — the same reasoning as D-026, which chose Prisma 7 rather than start on a superseded major.
**Why lazy:** a static import made every unit suite that transitively reached `CompletionSyncService` parse an ESM bundle under Jest's CommonJS runtime and fail. Nothing in a unit test renders a PDF, so nothing in a unit test should be loading a browser automation library. The cost is also paid once, on first issuance, rather than on every API boot.
**Consequence, stated plainly:** Jest cannot exercise the real renderer at all. Real rendering is proven where it can be — by the spike scripts against a real Chromium, and by the CV export in the browser end-to-end suite, which runs the built API.

## D-054 — Path completion requires courses **passed**, not merely completed
**Decision:** A path reaches `COMPLETED`, and its certificate is issued, only when every chosen course has `completions.passed = true`. `MyPathView.pathCertificateUnlocked` reads the path's own status rather than recounting course statuses.
**Why:** this corrects a defect Phase 2 left behind. `UserPathCourse.status` becomes `COMPLETED` from the LMS's completion signal **alone**, and D-042 §4 is explicit that passing needs the signal *and* the grade. A learner could therefore finish all five courses in Moodle, score below the threshold on every one, and have the path marked complete — and Phase 3 would then have certified it. §4.9 is unambiguous that the path certificate unlocks on "complete **and** passed". Verified against a real database: the path was refused while 5/5 chosen courses read `COMPLETED` and one sat at 45% against a threshold of 70, then issued once that course passed.
**Not changed:** Phase 2's status semantics. "Completed in the LMS" is a legitimate thing for My Path to show beside the grade; the fix belongs at the certification gate, not in the status field.

## D-053 — The verification id is public and stored in the clear; files are named by the row id
**Decision:** `certificates.verification_id` is 256 bits of CSPRNG stored **unhashed**, unlike session and auth tokens. The stored PDF is named after the certificate's **row id**, never its verification id. An unknown id returns 404, never a payload saying "invalid", and a malformed id is answered identically.
**Why:** the two token kinds are not the same thing. A session token authenticates someone and must be useless if the database leaks — hence the hashing rule in `common/secure-token.ts`. A verification id is the *name of a public record*: the QR on the paper has to resolve to it, so it cannot be hashed. Its safety comes from being unguessable and non-enumerable instead.
**Why the filename differs:** the verification id travels on paper. Naming stored files after it would hand anyone holding a certificate the whole PDF if the storage root were ever served by a misconfigured static mount. The public handle and the storage path are deliberately unrelated.
**Why 404 rather than "invalid":** we cannot know a certificate is fake — only that we do not hold that id, which is far more often a mistyped or half-scanned link. Answering "not found" says only what is true, and makes a wrong id indistinguishable from one that never existed, which is what makes guessing pointless rather than merely slow.

## D-052 — Certificates are rendered once and stored; the CV is rendered on demand
**Decision:** A certificate's PDF bytes are produced **once at issue time** and written to a configured storage root, referenced from the row and never re-rendered. The CV PDF is rendered **on every export** and never stored. Certificate reads verify the stored digest before serving, and refuse on a mismatch.
**Why the difference:** a certificate is a credential — the artefact a third party checks must be the artefact that was issued. Rendering on demand would make it a *view* of current data, so a template tweak, a re-synced course title or a corrected name would silently change a document someone had already downloaded, printed and filed. That immutability is also why Phase 5's certificate-template editor can only affect future issuances. A CV is the opposite: a living document the learner edits and re-exports, where storing bytes would mean either a stale file or an invalidation rule for something nobody verifies.
**Why the digest is checked:** handing someone a credential that has been truncated, corrupted or altered is worse than telling them it is unavailable, because a silently wrong certificate is the failure nobody notices.
**Operational note (Phase 7):** `CERT_STORAGE_DIR` defaults to a **relative** path, which resolves against the process's working directory — and `npm run --workspace` starts the API with its own directory as cwd. This was caught when the browser suite's downloads 500'd on files written somewhere else. Deployment must set an absolute path: a relative storage root for credentials means the bytes move if anything ever changes the working directory. Object storage remains a Phase 7 concern.
**Rejected:** render-on-demand for certificates (a credential that can change under its holder); storing CV renders (stale, or an invalidation problem for nothing).

## D-051 — The certificate face: austere, both calendars, no grade
**Decision:** One template serves both certificate types, Arabic-first and RTL, in navy and gold. The **path** certificate is the larger award and says so — gold frame and filled seal against the course certificate's navy, a larger heading, and the count of courses it took. The face carries a **logo slot with a neutral placeholder mark** until the ministry supplies its seal, the line "الجهة المصدرة: وزارة الداخلية", a signature block slot (name + title), **both the Hijri and Gregorian issue dates**, and a QR code. It carries **no grade**.
**Why:** the ministry's logo and seal are not available yet, and a slot sized and positioned now means adding them later is not a layout change. Both calendars because this is a formal ministry credential and both are in use; they come from `format.ts` via a calendar context, so nothing about dates is hardcoded (D-018). No grade because a certificate states that a standard was met, not by how much — it is a credential, not a transcript, and the grade stays in My Path where it can be read in context.
**Mechanically:** the typeface is inlined as base64 rather than linked. PDFs render in the API, which has no `next/font` and, in a container, no Arabic system font at all — an unembedded face does not degrade gracefully, it degrades to tofu or to unshaped letters. `document.fonts.ready` is awaited before `page.pdf()`, without which the render is a race that usually looks right.

## D-050 — CV is an English document with pass-through Arabic proper nouns
**Decision:** The CV builder produces an ENGLISH (LTR) document; the builder UI chrome stays Arabic-first. System-injected proper nouns (name, department, path name, RIASEC type names, certificate/course titles) pass through in whatever language they were authored (likely Arabic), untranslated. The PDF renders English body with correctly-shaped inline Arabic runs. A fully-localized CV is deferred.
**Why:** The user specified the CV should be in English — CVs are commonly expected in English even in an Arabic-first system, since they are used externally/professionally. Names and credential titles staying in their original language on an English CV is normal and correct, and it avoids forcing bilingual authoring of every field across the assessment, catalog and certificates for little benefit.
**Supersedes:** the earlier "Arabic CV" phrasing in §4.11 and the Phase 3 deliverable. The PDF pipeline (Phase 3) must therefore prove the English-body-with-inline-Arabic case, not only pure-Arabic RTL.
**Rejected:** Arabic CV (contradicts the requirement); requiring maintained English versions of all names/titles (large authoring burden for little value).

## D-049 — Assessment edits freeze existing results (versioning)
**Decision:** Editing assessment questions/options/weightings in the Phase 5 admin portal does NOT retroactively change results of employees who already completed it. Existing `assessment_results` are frozen as taken; edits apply to future takers. Surface version + effective date.
**Why:** A person's Holland result is a record of what they answered under a specific instrument, and certificates/paths flow from it — silently mutating past results would be wrong and corrupting. This is already structurally supported: results are append-only (D-033), all six scores are stored as columns with `maxScore` so a historical result renders correctly even after the bank changes size (D-035), and `assessment_responses` references the bank `onDelete: Restrict` so editing a question cannot delete the answers people already gave (D-035). D-049 states the product rule those mechanisms exist to serve.
**Rejected:** Recomputing old results on edit (changes history under people's feet); blocking edits entirely (admin must be able to improve the assessment).

## D-048 — Admins edit assessment questions + weightings, NOT the core scoring algorithm
**Decision:** The super-admin can edit questions, answer options, and each option's RIASEC dimension weightings. The core scoring logic — tally per dimension → rank (canonical-order tie-break, D-031) → top-three Holland Code, and the gold recommendation sort — stays fixed in code (D-034) and is NOT admin-editable.
**Why:** Editing weightings is powerful enough to tune the assessment without risking a broken or nonsensical scoring engine that an editable algorithm would invite; it keeps the correctness tests (D-031/D-032/D-034) meaningful. The weighting editor gets referential integrity for free because option weights are an enum-column table, not JSON (D-035).
**Rejected:** Exposing the raw algorithm to admins (high blast radius, untestable, easy to break); locking questions too (admin must be able to improve content — the bank is seeded data precisely so Phase 5 can edit it without a deploy, D-032).

## D-047 — Each course is single-language as authored
**Decision:** A course exists in ONE language (Arabic or English) as the entity authored it. The catalog shows each course's title/description in that language; we do not require or maintain both languages per course. App chrome stays Arabic-first.
**Why:** The user said courses may be in Arabic and English and content passes through as authored. Per-course single language matches how entities actually create content in Moodle (Model 1, D-046) and avoids a large bilingual-authoring burden for v1.
**Rejected:** Mandatory bilingual title/description per course (authoring overhead, little value now).

## D-046 — Course authoring uses Model 1 (author in Moodle; portals wrap the product layer)
**Decision:** Entities author course CONTENT (lectures, videos, materials, quiz questions) inside a themed Moodle via the seamless-login handoff (D-044/D-045). The entity/admin portals own only the product layer Moodle lacks: path membership, RIASEC letter, duration, objectives, prerequisites (D-035), publish/unpublish, and learner review. We do NOT rebuild Moodle's authoring UI in our app.
**Why:** Moodle is already a full authoring system; rebuilding it in-app would be the single largest build in the project, would duplicate Moodle, and would fight Moodle's weak content-creation API. Model 1 matches the "app = experience layer, Moodle = engine" principle (D-000) and mirrors the learner-side handoff already chosen (D-045). It also fits what §6/D-040 already do — our `courses` row is a thin mirror carrying product metadata over an LMS-owned course.
**Rejected:** Model 2 (full authoring UI in our own portal pushing content to Moodle) — largest single build, duplicates Moodle, fights a limited API, for a mostly-cosmetic unified-authoring benefit. Revisit only if the ministry later insists entities never see Moodle even for authoring.

## D-045 — The course player is a handoff page, and the raw LMS link is removed from the API
**Decision:** §4.8's course view is a thin page that provides path context, the outcome of the last attempt, and **one** action that launches into Moodle. It does not embed Moodle, and it is now the only route into a course.

**Launching is a POST, minted per click.** The URL carries a short-lived single-use credential (D-044), so it must not be prefetched by a browser, cached, or arrived at by following a link — and as a POST it inherits the CSRF protection every mutating endpoint has. Rendering it into the page would mean a live credential sat in the DOM, in view-source and in any cached copy, from the moment the page loaded and for as long as anyone left the tab open. A component test and a browser test both assert the markup does not contain it.

**`courseUrl` is removed from `CourseDetail` and `MyPathCourseView`.** Both screens previously linked straight at the Moodle deep link, which **carries no session** — a learner following it would land on a Moodle page that does not know who they are. Now that a working handoff exists, leaving the unauthenticated link in the API contract would leave the wrong thing available and equally easy to use. The method stays on the port, because the plugin redirects to exactly that URL after establishing the session; it just no longer reaches a browser.

**Enrolment happens on demand at launch, not only on the sync schedule.** A learner who confirmed their path while the LMS was unreachable has a committed path with no enrolments (D-036), and clicking a course would drop them onto a Moodle page refusing access. `ensureEnrolledForLaunch` closes that window: it enrols right then, idempotently, and turns "wait up to a sync interval and hope" into "it works". Reconciliation still runs on the schedule for learners who never click.

**Refusals are deliberately indistinguishable.** A course not in a confirmed path and a course the LMS refused both answer `COURSE_NOT_ENROLLED`. Distinguishing them would tell a caller which courses exist in someone else's path. Launch is audited either way, success and failure — it is the one place the product issues a credential that logs someone in somewhere else.

**Passing is re-derived, not stored on the chosen course.** The threshold is a product setting (D-007); a frozen boolean would keep asserting the old policy on screen after it changed, while `completions` recorded the new one.

**A mock made stricter, again.** `MockLmsService.courseLaunchUrl` originally returned a stable URL, and an integration test asserting freshness failed against it. The mock now varies per call and the **contract** requires it. A handoff is single-use, so returning the same URL twice means returning an already-spent token — the mock being easier to satisfy than reality is exactly the failure D-036 already recorded once, with the user-id counter.

## D-044 — Seamless login is a small custom Moodle plugin, pending ministry approval of custom PHP
**Decision:** the course handoff uses **`local_tamkeensso`** (Option A) — a small Moodle plugin that accepts a short-lived, single-use, HMAC-signed token from our app and logs the learner straight into the course. OAuth2-IdP (Option B) remains the hardening target per §5.3.

> **⚠ OPEN BLOCKER — not yet resolved.** Whether the ministry will accept **custom PHP on their production Moodle** is a governance question that has not been confirmed. `local_tamkeensso` is approved **for the pilot**. **Ministry approval of custom Moodle plugins MUST be confirmed before production; if refused, switch to Option B (OAuth2) during hardening.** The user is raising this in parallel. Nothing else in Phase 2 depends on the answer, so the work proceeds — but the answer changes which mechanism ships.

**Why core Moodle cannot do this, established empirically rather than assumed:** every core mechanism that mints a session mints one for **the token's own user**, and our web-services token belongs to `tamkeen-integration`, not to the learner. `tool_mobile_get_autologin_key` is core's only candidate and fails three times over — it is not on our external service, it issues a key only for the token owner, it needs a `privatetoken` that manually created tokens do not carry, and it is rate-limited per user. Issuing per-learner tokens does not rescue it: creating tokens is not exposed as a web-service function, so a plugin would be needed anyway, and the rate limit still breaks "click a course, land in it".

**Why the plugin over OAuth2 for v1:** the security surface is small enough to review properly — an HMAC signature, a short expiry, single use, and binding to **one user and one course** — and it is exactly what §5.4's MVP handoff and D-004 describe. OAuth2 would be the single largest piece of work in Phase 2, and two frictions make it worse as a *first* step rather than a hardening step: `auth_oauth2` links accounts by **email**, whereas we deliberately key on a derived username (D-038) and provision accounts as `manual`; and Moodle's first OAuth2 login normally shows an account-linking confirmation, which breaks "no second login" on the very first course entry unless auto-linking is configured.

**A correction worth recording, because it nearly became a false finding:** the first probe inferred from HTTP 404s that `auth_oauth2` and `tool_mobile` were absent from the instance. That inference was wrong — `/course/view.php`, which certainly exists, also answers 404 without parameters, because Moodle renders its own 404 for a missing course id. On this instance a 404 means "PHP declined", not "file absent", and unauthenticated probing cannot enumerate plugins. The spike script now demonstrates that calibration instead of asserting the conclusion. The verdict rests only on the token-identity finding, which is structural.

**Re-verification owed (D-039):** the mechanism is being built against 5.2.2 and **must be re-verified on a real 4.5** before production, since that is the version production will run.

## D-043 — The `deepmerge-ts` advisory is accepted and deferred, not fixed by downgrading Prisma
**Decision:** `npm audit` reports **3 high** advisories for `deepmerge-ts` (stack exhaustion on recursive object graphs), reached through `prisma` → `@prisma/config`. We **accept it for now** and hand it to the **Phase 6 dependency review**, which already owns the D-022 `postcss`/`sharp` pins. Prisma is **not** downgraded.
**Why not fix it:** npm's own remedy installs `prisma@6.12.0`, which is a major downgrade and directly contradicts D-026 — Prisma 7 was chosen deliberately so a system intended to run for years does not start on an already-superseded major with an earlier end of support. Trading a live framework decision for a low-exposure advisory is the wrong way round.
**Why the D-022 trick does not work here:** an npm `overrides` pin on `deepmerge-ts` **has no effect** — verified, including a full lockfile regeneration. `@prisma/config` pins the version exactly and the override does not displace it. (Regenerating the lockfile also produced a 6,476-line diff, which was reverted rather than folded into a feature commit; the only lockfile change in that commit is BullMQ.)
**Exposure, stated plainly:** `deepmerge-ts` is reached by Prisma's **config loader** — CLI and boot-time configuration, not the request path. Triggering it needs an attacker-controlled recursive object graph in a Prisma config file, and ours is repo-authored. This is an argument for not panicking, not for ignoring it.
**Not introduced by Phase 2.** Traced through the dependency tree: it comes from `prisma`, not from the newly added `bullmq`. It is a newly published advisory against a dependency the project already had, which is why the Phase 0 audit was clean.
**What Phase 6 must do:** re-check whether Prisma has bumped `@prisma/config`'s `deepmerge-ts` pin (the fix is theirs to ship), and if not, decide between an upstream fix, a patch-package approach, or accepting it explicitly for launch. Recorded in `progress.md`'s open-blocker list so it stays visible across sessions rather than living only here.

## D-042 — Completion sync: one writer, one constraint, and one email
The polled sync (D-005) writes completion state. Everything below exists because this code runs every few minutes forever, so anything not idempotent becomes a duplicate row, a repeated email, or — in Phase 3 — a certificate issued twice.

**1. `completions` is unique on `(user_id, moodle_course_id)`, and that one constraint carries three rules.** Re-running the sync cannot create a second row, so polling is safe. A course reachable through more than one route reuses the single completion rather than being re-taken (D-003, §2). And Phase 3's issuance gets a stable key to be idempotent against. It is keyed on the **LMS** course id rather than our `courses.id` deliberately: the LMS course is the thing actually completed, and the record must survive our catalogue row being retired or re-created.

**2. The verdict is stored with the threshold it was judged against.** `passed` is *our* evaluation, not the LMS's (D-007) — but a stored boolean whose meaning depends on a setting that can change is unexplainable a year later, exactly when someone asks why a certificate was issued. `passThresholdUsed` makes each historical verdict self-describing.

**3. The grade is rounded once, and the decision uses the rounded value.** The alternative — deciding on the precise grade while displaying a rounded one — produces a learner shown "70%" and told they failed, because the true figure was 69.6. For a government system the grade on the screen must be the grade decided on. The cost is that the effective boundary sits half a point below the nominal one; that is deliberate and explainable rather than hidden.

**4. Passing requires the LMS's completion signal *and* the grade.** A high quiz score in an unfinished course is not a finished course, and a certificate saying otherwise would be false (§5.5). This creates one operational hazard worth naming: a Moodle course with **no completion criteria configured** reports `completed:false` forever, so nobody on it can ever pass however well they score — and the symptom is "certificates never arrive" with nothing to explain it. `isGradedButNotComplete` detects exactly that shape and logs it against the course. The spike hit this very failure on the test course, which is why it is guarded rather than theorised.

**5. The email fires only on the transition into passing.** It is the single irreversible side effect in a job that re-reads the same completions indefinitely; without the check a learner would be emailed about the same course every few minutes. The previous `passed` value is therefore read *before* the upsert. A failed send never fails the sync — the completion is true regardless, and the next run must not re-process it because SMTP was down. **Phase 3 issues the course certificate at this same seam (`onCoursePassed`) and must still do its own idempotency check**: this guard is about not spamming, not about uniqueness, and a re-run after a partial failure can legitimately arrive here twice.

**6. My Path's live-progress overlay is gone, closing D-036.** Phase 1 read progress from the LMS on every render because nothing persisted it; this job is the missing writer, so the stored status is now the whole truth. That is not tidying: the overlay made an N+1 LMS call on every page load, so the page's latency — and its ability to render at all — depended on the LMS being up. It no longer does, and there is exactly one writer of those rows.

**Scheduling.** The cycle runs **catalogue → enrolment reconciliation → completions**, and the order is load-bearing: the catalogue first so a new or vanished course is known before anything reasons about it, and enrolments before completions so a learner whose enrolment never landed is enrolled before we ask about their progress rather than waiting a whole interval for nothing. Each stage is isolated — they fail for unrelated reasons, and a catalogue problem must not freeze every learner's progress. The cycle never throws, because a failed BullMQ job would retry stages that already succeeded. Worker concurrency is **1**: two overlapping cycles would put two writers on `completions` and could double-send an email in the window between reading the previous verdict and writing the new one.

**The schedule and the work are separate on purpose.** `SyncSchedulerService` only calls three services in order; all the logic lives in them, testable without Redis, a queue or a clock. Scheduling is fire-and-forget at bootstrap and its failure is logged, not thrown — the product works without sync running, just with staler data, and refusing to start would turn a background-job outage into a total one. It never schedules under `NODE_ENV=test` whatever the flag says, because a repeatable job firing mid-suite would write underneath assertions and read as flakiness.

**Deferred, deliberately:** the sync processes every eligible learner in one pass, with no batching or rotation. A silent cap would starve whoever fell outside it, which is worse than a long run; **Phase 6** (sync reliability and load testing) owns making this scale.

## D-041 — Enrolment: verify before believing an error, and fail one course at a time
Two changes to how enrolment behaves, both invisible under the mock and both load-bearing against a real Moodle.

**1. `enrol` verifies before believing its own error.**
The spike caught Moodle throwing `Message was not sent.` — the course-welcome email failing with no mail transport — **after the enrolment had already committed**. Reading the enrolments back showed it present, both times. So on any failure the adapter re-reads `core_enrol_get_users_courses` and only a genuine absence counts as a failure.
**Why this is not just about one instance's broken mail:** the same reasoning covers a **timeout**, which is the genuinely ambiguous case — the request may well have landed. Assuming failure there would make the reconciliation job re-enrol forever, and under D-036 (enrolment is best-effort, the audit log is its only trace) it would record successful enrolments as `FAILURE`, sending an operator to fix something already correct. The verification is itself allowed to fail: if Moodle is unreachable we learn nothing and the original error stands.

**2. Each course is enrolled independently, and the audit carries counts.**
Enrolment previously wrapped the whole 5–10 course loop in one `try`. Under the mock nothing failed, so this never mattered; against a real Moodle a single refused course would abandon **every course after it** and audit the batch as failed — leaving a learner half-enrolled in a path they cannot switch out of (D-002), with no record of which half. Now each course is attempted on its own, the audit records `{requested, enrolled, failed}`, and the outcome is `FAILURE` only if something actually failed. Provisioning failure remains a whole-batch failure, correctly: with no LMS account there is nothing to enrol into.

**3. `retryPendingEnrolments` closes D-036's loop.**
Best-effort enrolment is only defensible if something comes back for the leftovers; otherwise it means "sometimes silently not enrolled". The reconciler picks up confirmed paths with `enrolledAt IS NULL`, is bounded per run so one bad batch cannot monopolise the scheduler, and is safe to run at any time. It is attributed to **no IP address** — it is a background job, and inventing one would make the audit trail claim a person acted. The scheduler that calls it arrives with the completion-sync job.

**On the `enrollments` table (§6):** still not built, and deliberately. §6 marks it optional ("debugging syncs"), and `user_path_courses.enrolledAt` already answers the only question anything currently asks — *is this course enrolled yet?* — which is what both the retry query and idempotency need. A table whose only consumer would be a hypothetical future debugger is speculative schema. It earns its place when completion sync needs to record something `enrolledAt` cannot express.

**Also:** `MOODLE_STUDENT_ROLE_ID` is passed into the adapter rather than read as a constant, and the enrolment count is summed from what each attempt actually did rather than derived from a global "pending" tally — with more rows outstanding than the batch limit, the derived figure reports zero enrolled on a run that enrolled plenty.

## D-040 — Catalogue sync: never delete, refuse an empty catalogue, and product metadata is untouchable
Three rules govern what a sync run may do to `courses`. Each exists because the obvious implementation is quietly destructive.

**1. A course that vanishes from the LMS is never deleted, and is only retired if nobody holds it.**
Our `RETIRED` status is invisible to *everyone* — `CoursesService.visibleCourseFilter` excludes it even for a user who already selected the course, and `resolveCourseAction` returns `UNAVAILABLE`. So retiring an in-use course does precisely what §2/D-015 forbids: it pulls content out from under a learner mid-path. Sync therefore reads `user_path_courses` and demotes a vanished course to **`HIDDEN_BUT_COMPLETABLE`** when any learner holds it — gone from new selections, still completable by those already on it — and only to `RETIRED` when none does. Rows are never deleted at all.

**2. An empty catalogue is a fault, not an instruction.**
If `listCourses()` returns nothing, the run writes nothing and audits a FAILURE. Acting on it would withdraw the entire catalogue in a single pass, and every likely cause — a capability lost from the integration role, an instance mid-upgrade, a token rotated — is transient and recoverable. The seed runner already refuses an empty catalogue for the same reason. The asymmetry is deliberate: wrongly keeping a stale course costs a confusing catalogue entry, wrongly withdrawing every course costs every learner their path.

**3. Sync writes only what the LMS owns.**
Moodle owns a course *existing*, plus its title, summary and visibility. `objectives`, `prerequisites`, `durationMinutes`, path membership and ordering are ours (D-035, D-039), and sync never writes them — `path_courses` is not referenced by the service at all. The duration rule needed care: letting the LMS's `null` overwrite an authored value would erase every duration in the catalogue on the first run **without erroring**, because the column is nullable. An existing value therefore always wins, and the LMS's is accepted only where we hold none.

**Two smaller choices:**
- **A `RETIRED` course is not resurrected by the LMS making it visible again.** Retirement is our decision (Phase 4/5 unpublishing, or a course that vanished); an LMS visibility flag must not silently undo it. Reinstating is a human action.
- **An absent `visible` field fails closed** — the course does not enter the catalogue as available. Its absence would signal a capability regression on the token; defaulting to visible would publish courses Moodle deliberately hides, silently, whereas defaulting to hidden is loud, recoverable and leaks nothing.

**When it runs:** once at application startup in real mode, so a fresh deployment never serves a stale catalogue while waiting for the first tick, and on the scheduled interval thereafter (the scheduler arrives with the completion-sync job). It is fire-and-forget and **cannot fail boot** — the catalogue is cached in our own database, so an LMS down at deploy time is a degraded state, not a reason for the API to refuse to start. Every write is an upsert keyed on the unique `moodle_course_id`, so calling it at any other time is safe.

**Also:** the seed runner and the sync now share `fieldsForPublishedCourse`. They both mirror an LMS catalogue, and if they disagreed about what "hidden" means or who owns duration, a seeded database and a synced one would describe the same course differently.

## D-039 — Phase 2 build decisions: version split, duration as our metadata, handoff for v1
Resolves what D-038 left open, plus the shape choices the real client forced.

**1. Version split: Moodle 4.5 LTS in production, 5.2 in development.**
The spike ran against 5.2.2 because that is what the local Docker image pulled. Production stays on **4.5 LTS** — D-019's reasoning still governs: security support to Oct 2027 is the property a government system is buying, and 5.2 is not an LTS. Running two versions is acceptable only because **the adapter is version-agnostic**: nothing branches on a version, and `release` is read for reporting alone. The two behaviours the spike found to be surprising were both **capability**-gated rather than version-gated, which is why they are expected to carry across — but *expected* is not *verified*, so **the seamless-login mechanism must be re-verified against a real 4.5** rather than assumed from 5.2. A dev/prod version skew is a real risk and is accepted with that mitigation, not waved away.

**2. `durationMinutes` is our product metadata, not Moodle's.**
Moodle has no nominal-effort field: the spike confirmed `customfields` empty and only `startdate`/`enddate` (calendar dates, not effort) available. This is exactly the situation D-035 already ruled on for objectives and prerequisites — making the adapter responsible for data Moodle does not hold means it must infer, and it will infer wrongly. So duration is authored as our metadata and becomes entity-editable in Phase 4, alongside the fields it now keeps company with.
`LmsCourse.durationMinutes` **stays on the port** (nullable), because a Moodle instance *could* supply one through a course custom field and removing the field would foreclose that. Catalogue sync prefers our own value and treats the LMS's as a fallback, so the port stays honest without our catalogue depending on it.
**Rejected:** a Moodle course custom field (per-instance configuration the ministry must create and maintain correctly, to supply data we already own a better home for); deriving it from `enddate - startdate` (that is how long a course *runs*, not how long it *takes* — a year-long course is not a year of effort).

**3. Course delivery for v1 is handoff, and seamless login is spiked before the player is built.**
§5.4's MVP stands: hand off to an Arabic/RTL-themed Moodle, app remains the hub, no embedding. The open question is how the learner arrives **already signed in**. Core Moodle's only stock mechanism is `tool_mobile_get_autologin_key`, which is not on our token, needs the mobile web service enabled, and is understood to be rate-limited per user — plausibly too restrictive for "click a course, land in it". The alternatives are a small custom `local_` Moodle plugin or standing our app up as an OAuth2 IdP.
**Decision: spike this specifically, early, before any course-player UI exists.** Building a player around a handoff that turns out to be unworkable would mean rebuilding the screen *and* renegotiating Moodle-side installation late. It is also the Phase 2 item most likely to need something installed on the ministry's Moodle, which is the longest-lead dependency we have.

**Also decided, from building the client:**
- **`MoodleWsError` carries the errorcode and nothing else.** It originally kept Moodle's human-readable `message` too; a test asserting no credential appears in any thrown error is what removed it. Moodle can echo the request it received in a debug response, and nothing branches on the prose — so keeping it out makes the property structural rather than a hope about Moodle's phrasing. Non-JSON bodies are likewise never parsed into an error; only their length is reported.
- **`LmsOperationError` distinguishes a refusal from an outage.** `LmsUnavailableError` means "retry"; `LmsOperationError` means "a human must look". Folding both into one type would have made the hand-created-account case (D-038's accepted cost) indistinguishable from a network blip, and it is the one that needs an operator. Neither carries an LMS error code — that stays in the log, inside the module.
- **The Moodle password is generated and immediately discarded.** We are the identity owner, so the account is reachable only through our handoff — and making that true *by construction* beats making it true by a setting someone can later change. There is also then no second credential to store, rotate or leak.
- **`MOODLE_STUDENT_ROLE_ID` and `MOODLE_TIMEOUT_MS` are configuration.** Role ids are per-instance and we do not control the ministry's Moodle; a hardcoded `5` that meant something else there would enrol every learner with the wrong permissions.
- **`MOODLE_MODE=real` now also requires `MOODLE_WS_TOKEN`**, not just a base URL. Booting without it yields an integration that starts cleanly and fails every call with `invalidtoken` — a slow, confusing failure in place of an immediate one.

## D-038 — Moodle accounts are keyed on a username we derive, and four other rules the Phase 2 spike forced
**Context:** the spike (branch `phase-2-moodle-spike`, `spike/moodle-spike.mjs`) proved the loop end to end against a real Moodle **5.2.2** — provision → enrol → learner takes the quiz → we detect `completed: true`, `gradePercent: 100`, PASS at `PASS_THRESHOLD=70`. Five things it found are design decisions, not implementation trivia, and each was a defect waiting to happen.

**1. Moodle accounts are keyed on a deterministic username we derive from the email — NOT on an email lookup.**
`core_user_get_users_by_field` with `field=email` returns an **empty list** for an address that certainly exists, and the returned user object carries no `email` key at all. Both are the missing `moodle/site:viewuseridentity` capability. Critically it is **silent**: no exception, no warning. An adapter trusting it would find no existing user on every retry and create a duplicate account each time — and `users.moodle_user_id` is unique, so the failure would surface far from its cause.
**Decision:** do **not** grant `moodle/site:viewuseridentity`. We are the identity owner (D-000), so the username is ours to choose, and a key we control is stronger than an index we cannot query. `provisionUser` is lookup-by-username-then-create.
**Cost, accepted:** if an admin hand-creates a Moodle account with a learner's email under a different username, we cannot detect it; provisioning fails with a Moodle error we surface rather than auto-resolve. A `viewuseridentity`-gated reconciliation path is documented as a future option should auto-linking of admin-created accounts ever be wanted.
**Also:** a *blind* re-create is rejected with `invalidparameter`, so provisioning must be lookup-then-create, never create-then-catch.

**2. `enrol` must verify before believing its own error.**
`enrol_manual_enrol_users` threw `Message was not sent.` — Moodle failing to send the course-welcome email — **after the enrolment had already committed**. Reading the enrolments back showed it present, both times. Under D-036 enrolment is best-effort and the audit log is its only trace, so an adapter that trusted the exception would record a *successful* enrolment as `FAILURE`: a silently wrong operational record, undebuggable later. **On error, re-read enrolments; only genuine absence is failure.** This is a property of the call, not of one instance's broken mail.

**3. Catalogue sync uses `core_course_get_courses_by_field`, not `core_course_get_courses`.**
`core_course_get_courses` omits `visible` and `enablecompletion` — Moodle gates them behind `moodle/course:update` on the caller, which a least-privilege integration user must not have. `visible` drives our `courses.status` → `HIDDEN_BUT_COMPLETABLE` rule (D-015/D-035), so sync is impossible without it. `..._by_field` returns both, plus hidden courses, under the same token. The gating is capability-based rather than version-based, so this should hold on 4.5 too — to be re-verified, not assumed, if the version decision changes. Sync must also skip the site course (`format: "site"`, id 1), which is not a course.

**4. The pass threshold is evaluated against the `itemtype: "course"` total, always.**
`gradereport_user_get_grade_items` returned **only** the course total — no `mod/quiz` item — even though the grade came from a quiz. Preferring a quiz item "when present" would make the grade source differ between this instance and the ministry's, which is a latent inconsistency bug. The course total is also the correct product semantics: D-007 and §5.5 speak of a *course* being passed. `gradePercent = (graderaw - grademin) / (grademax - grademin) * 100`, and `graderaw: null` stays `null` — never 0 (an unattempted course must not read as a failed one).

**5. `completedAt` is derived from the criteria, because the obvious field does not exist.**
There is no `completionstatus.timecompleted`. The timestamps live on `completionstatus.completions[]`, so the course completion time is the latest satisfied criterion. Reading the obvious-looking path returns `null` on a course that is demonstrably complete — which would have written a null timestamp for every learner. (`gradedategraded` on the course total is a usable secondary source.)

**Also confirmed:** core REST answers **HTTP 200 on failure**, with `{errorcode, message, exception}` in the body — the Catalyst RESTful plugin is not installed, so the status line proves nothing and the body must be inspected on every call. The student role id is **configurable** (`MOODLE_STUDENT_ROLE_ID`, default 5): hardcoding a role id against a Moodle we do not control is a latent production bug. Arabic names round-trip through `core_user_create_users` intact. Latency 60–256 ms per call locally.

**Left open at the end of the spike** — the production Moodle version and the absent `durationMinutes` source — **both resolved in D-039.**

**Addendum (§4.12, TAM-111) — an email change moves the LMS's email, never the username.** Confirming an email change (`AuthService.confirmEmailChange`) calls `LmsPort.updateUser({ lmsUserId, email })` for a user with a `moodle_user_id`, best-effort and after the change already committed — the same D-036 pattern `ProfileService` uses for a name change, and reusing `PROFILE_LMS_SYNC_FAILED` (now carrying `detail.field: 'email' | 'fullName'`) rather than a second action code.
**Why the username is untouched:** rule 1 above is not just how the account was *found* at provisioning — it is what the account *is*, for the account's whole lifetime. `deriveMoodleUsername` runs once, against whatever address was current at `provisionUser`, and `users.moodle_user_id` is the only durable link from then on. Re-deriving it from a new email on every change would mean an account's identity moves whenever a person changes their address, which is exactly the silent-duplicate failure rule 1 exists to prevent, just triggered by an update instead of a retry.
**The consequence, made explicit:** after an email change, `findUserByEmail` on the *new* address returns `null` — no account was ever given a username derived from it — while the *original* address still resolves to the same account. This is not a bug to fix; it is the same "email lookups do not work under this token" constraint rule 1 already accepted, now visible on write as well as on read. The contract suite (`updateUser` → "moves the email without re-deriving the username") asserts exactly this shape, against both the mock and, when Phase 2's real-Moodle contract run is exercised, the real adapter.
**A user with no `moodle_user_id` yet:** untouched by this. They provision later, through the normal path, with whatever email is current at that time — there is no stale Moodle record to leave behind, because none exists yet.

## D-037 — Frontend shape: a `(portal)` route group, one session load, and no query library
**Decision:** Authenticated pages live under `apps/web/src/app/(portal)/`, whose layout renders `PortalProvider`. That provider loads `authApi.me()` and `dashboardApi.get()` **once**, exposes both through context, and owns the redirect to `/login` on a 401. Data fetching is a ~110-line in-house `useApiQuery`/`useApiMutation` pair shaped to feed the existing `DataView`, not TanStack Query.
**Why the single load:** the navigation itself depends on journey state — §4.2 hides My Path until a path exists — so a page that fetched its own copy would render a nav disagreeing with its own content for a frame. Centralising the 401 matters for the same reason a global guard does on the API: with per-page handling, every page repeats three lines and one is eventually missed, leaving a signed-out user staring at a permanent error state instead of the sign-in form. Sign-in and the password pages sit *outside* the group, so they never pay for the session lookup and cannot be caught by a redirect from `/login` to `/login`.
**Why no query library:** what §2B actually requires is that every data view has loading, error and empty states, and `DataView` already enforces that by construction; the missing piece was a hook whose return value plugs into it. Caching, background refetching and invalidation are capabilities Phase 1 has no use for, and an unused dependency in a government system is one more thing to review, patch and justify at every audit. The hook does handle the two things that cause real bugs — a stale response overwriting a newer one, and a resolved promise setting state on an unmounted component. Swapping in TanStack Query later is a change behind this signature.
**Two related choices:**
- **Certificates and CV are absent from the navigation entirely** until Phase 3 builds them, rather than appearing disabled or linking to a placeholder. A nav item that leads nowhere advertises something the product cannot do and costs the user a click to discover it. Profile *is* built (read-only) precisely because §4.2 puts it in the pre-assessment nav, so that link must lead somewhere real.
- **The confirmation gate uses the native `<dialog>`.** `showModal()` supplies focus trapping, the inert background, Escape-to-close and `aria-modal` from the platform; hand-rolled overlays routinely get one of those wrong, and this is the one dialog a user must genuinely understand before agreeing. jsdom does not implement `showModal`, so `vitest.setup.ts` shims the missing method — explicitly a stand-in for the API, not for the behaviour, which the Playwright suite exercises for real in Chromium.
**Rejected:** protecting pages individually (the forgotten-guard problem, in the browser this time); a middleware redirect (the session cookie belongs to the API origin, so the check would have to be duplicated server-side); TanStack Query (unused capability, real supply-chain cost); a div-based modal (trades a genuine accessibility property for a more convenient test).

## D-036 — LMS identity and enrolment in Phase 1: lazy provisioning, best-effort enrolment, read-only progress
**Decision:** Confirming a path calls `LmsPort.provisionUser()` if `users.moodle_user_id` is null, stores the returned id, then enrols each chosen course — **all through the port**, and **all best-effort after the commitment is already recorded**. My Path *reads* live progress via `listProgressForUser()` and overlays it on the stored status without writing it back.
**Why provisioning happens here, though Phase 2 nominally owns it:** without an LMS user there is no enrolment, and without enrolment the mock can report no progress at all — so Phase 1's "My Path statuses fed by the mock" would be unreachable. Doing it at the first moment an account is genuinely needed, through the port's contractually-idempotent `provisionUser`, means Phase 2 changes the implementation and nothing else. This is a scope call, recorded so it is not mistaken for scope creep.
**Why enrolment must not fail the request:** the commitment is irreversible and already written to our database, which is the source of truth for it. Rejecting the request because the LMS was unreachable would tell the user their irreversible decision did not take, when it did. Failures are logged and audited as `PATH_ENROLMENT_REQUESTED / FAILURE`, and Phase 2's sync job is where reconciliation belongs. The trade is explicit: a confirmed path can exist without its LMS enrolments until sync catches up.
**Why the progress overlay is not persisted:** writing completions is the Phase 2 sync job's responsibility. Having a read path also write the same rows would put two writers on them, which is a race waiting for a deadline.
**Revision to D-030's mock:** `MockLmsService` numbered users from a per-process counter. The end-to-end run exposed the consequence — after an API restart the counter began again at 5001 and handed a *new* user an id an existing `users` row already held, so enrolment died on the unique index that exists precisely to stop two people sharing one LMS account. Ids are now derived from the email (FNV-1a), reproducing the invariant a real Moodle has: an account keeps its id forever. The contract suite gained a case asserting the same email yields the same id across two instances, so the real Phase 2 adapter is held to it too.
**Rejected:** deferring provisioning to Phase 2 (leaves Phase 1's run view untestable); failing the confirm on an LMS error (misreports an irreversible decision); persisting the overlay now (two writers); handling the unique-constraint violation by ignoring it (hides a genuine integrity problem instead of fixing its cause).

## D-035 — Phase 1 schema: constraints carry the product rules
**Decision:** Four schema choices encode rules rather than merely storing data.
1. **`user_paths.user_id` is `@unique`.** "One path per user" (D-002) is a database constraint, not an application convention. An application-level check loses the race between two concurrent confirm requests; a unique index does not. The confirm transaction additionally guards on `confirmedAt IS NULL` in the `UPDATE … WHERE`, so a second concurrent confirm matches zero rows rather than overwriting the first one's timestamp.
2. **Option weights are a table with a `RiasecDimension` enum column, not JSON on the option.** A mistyped letter inside a JSON blob contributes nothing and fails *silently*, producing a subtly wrong Holland Code that no error surfaces. An enum column makes the database reject it, and Phase 5's weighting editor gets referential integrity without anyone writing validation for it.
3. **`assessment_responses` references the bank with `onDelete: Restrict`.** Editing a question in Phase 5 must not silently delete the answers people already gave and change historical results. (The result → responses relation stays `Cascade`: removing an attempt as a whole is coherent.)
4. **`assessment_results` stores all six scores as columns plus `maxScore`.** §3A requires all six; columns rather than JSON keeps them typed and queryable for Phase 5's dashboards, and carrying `maxScore` means a historical result can still be rendered as a percentage after the bank changes size.
**Also decided:** **course objectives and prerequisites are our product metadata, not the LMS's.** Moodle has no first-class field for either, so adding them to `LmsPort` would make the Phase 2 adapter responsible for data Moodle does not hold — it would have to parse them out of a summary and would get it wrong. They are seeded now and become editable by entities in Phase 4. The LMS's `visible` flag maps to our `courses.status`: not visible → `HIDDEN_BUT_COMPLETABLE`, which is D-015's "leaves the catalogue for new selections, stays completable for those enrolled".
**Also:** the API `tsconfig` now includes `prisma/`, so the seed script is typechecked — it builds the entire catalogue and question bank, and an untyped seed for a government system is a real gap. `tsconfig.build.json` excludes it again so the emitted layout stays `dist/main.js`.
**Rejected:** enforcing single-path in application code only (loses the concurrency race); JSON weights (silent failure); `Cascade` from the bank to responses (rewrites history); a `passed` column on `user_path_courses` (freezes a policy decision that D-007 makes a setting).

## D-034 — The RIASEC rules live in `packages/types`; the tally does not
**Decision:** Ranking, tie-breaking, Holland Code derivation and the gold recommendation sort (`rankDimensions`, `buildRiasecProfile`, `rankPathsByRecommendation`) live in `packages/types`, shared by both apps. The **tally** — turning chosen options into points — lives server-side in `apps/api/src/assessment/scoring.ts`, and **no view type in the API contract carries a dimension weighting**.
**Why the rules are shared:** the API is authoritative and computes the profile, but the web app sorts and highlights path cards. If "gold" meant something subtly different on each side, the recommendation a user *sees* would not be the one the system *recorded*. One implementation removes that failure mode, exactly as `format.ts` does for D-018. For the same reason the API sorts with the shared function rather than an `ORDER BY`: sorting in SQL would put §3A's rule in two places, in TypeScript and in a query.
**Why the tally is not shared:** it needs the option weights, and an assessment whose scoring key is visible in a network response is one a user can steer toward whichever result they already wanted — which would make every downstream recommendation theatre. `getActive` selects questions and options without their weights, and an integration test greps the whole response for `weight`, `dimension`, `points` and `riasec`. The e2e suite has to read the weights *out of the database* to produce a chosen code, which is the property made visible.
**Also decided:** the single context-dependent course action (§3, §4.7) is computed by a pure server-side function returning **exactly one** value. "Never all three" is then enforced by the shape of the response rather than trusted to each screen. A sixth value, `IN_PATH`, was added for a course already selected but not yet confirmed — "start" would be a button that cannot do what it says, because nothing is enrolled before the commitment gate. §4.9's quiet add means the selection may **grow** after commitment but never shrink; letting courses leave a confirmed path would be switching by instalments.
**Rejected:** computing the recommendation only on the server and shipping a pre-sorted list with no shared vocabulary (works until the web needs to re-sort or re-explain, then diverges); exposing weights to let the client show a live score (destroys the instrument); returning a list of permitted actions (invites a screen to render two).

## D-033 — Retakes append; a result is never overwritten
**Decision:** Each completed attempt inserts a new `assessment_results` row with its own responses. "The user's result" is the newest row by `completedAt`. Nothing is updated in place, and nothing is deleted.
**Why:** a career recommendation is a record of what the system told someone and when. Overwriting it would make the earlier advice unreconstructable, which matters both for explaining a decision months later and for any audit of how a path came to be chosen. It also keeps the retake rule honest: D-015 permits retaking only before commitment, and history makes it visible whether that was respected.
**Cost:** the table grows with retakes. Bounded in practice — retakes stop at commitment — and the Phase 6 retention pass owns anything further.
**Rejected:** updating the existing row (loses history for no real saving); soft-deleting superseded results (a second state to keep correct, for the same outcome).

## D-032 — The question bank: thirty Likert items, weighted 0-4, balanced by construction
**Decision:** The assessment is **30 five-point Likert statements, five per dimension**, seeded as data in `apps/api/src/seed-data/assessment.ts` and read from the database at runtime. Agreement levels weigh **0-4**, and the bank must be **balanced** — every dimension attaining exactly 20 — with `isBalancedBank` asserting it in CI.
**Why balance is not a nicety:** ranking compares **raw scores across dimensions**. If one dimension had more items than another it would rank higher on volume rather than on the user's interests, and the resulting Holland Code would be an artefact of how the bank happened to be authored. The test exists so that a Phase 5 edit which unbalances the bank fails loudly and forces a deliberate decision (either rebalance, or switch ranking to normalised percentages) rather than silently skewing every result.
**Why 0-4 rather than 1-5:** on a 1-5 scale a user who rejected every Realistic item would still accumulate Realistic points purely for having answered, so the floor would track the number of items rather than any interest.
**Why items are interleaved (R,I,A,S,E,C,R,…):** five consecutive statements on one dimension read as a labelled section, and a user who has decided how they wish to be categorised can answer the block uniformly. A test asserts no two consecutive items share a dimension.
**Why it is seeded data:** Phase 5 must be able to edit questions and weightings without a deployment, and the ministry must be able to revise the Arabic wording without touching a component. Question keys are stable, so revising wording does not orphan stored responses. The content sits under `src/` rather than beside `prisma/seed.ts` so it is typechecked and reachable by the test runner — the balance property must fail CI, not be noticed later.
**Status of the wording:** the Arabic text is a reviewed first draft and is expected to change; the asserted *properties* are not.
**Rejected:** scenario-style multiple choice (more engaging, but more authoring and more tie-prone; the schema still supports it, since options carry weights across one or more dimensions); hardcoding questions in components (defeats Phase 5); grouping items by dimension (invites block answering).

## D-031 — Ties break on canonical R-I-A-S-E-C order
**Decision:** When two dimensions score equally, they are ordered by the canonical Holland hexagon order R, I, A, S, E, C. The ordering is therefore **total**: ranks are 1-6 with no shared or skipped positions, and the Holland Code always has exactly three letters.
**Why:** CLAUDE.md §3A does not specify a tie rule, and ties are common — six dimensions over thirty items produce them routinely. Left to `Array.sort`'s handling of equal elements, a user's code would depend on the order rows came back from the database, so **the same answers could yield a different career recommendation on a different day**. A recommendation that is not reproducible is not defensible, which matters more here than in most products. Canonical order is the conventional presentation of the framework, so it is at least a principled arbitrary choice rather than an accidental one.
**Consequence worth knowing:** a user who answers every item identically gets `RIA`. That is correct behaviour — no dimension was preferred — and the e2e suite asserts it precisely because it is the case that would otherwise be nondeterministic.
**Rejected:** leaving ties to sort stability (nondeterministic across drivers and query plans); breaking ties randomly (irreproducible by construction); returning a shorter code on a tie (downstream recommendation logic assumes three letters); asking the user to break the tie (a question about an artefact of scoring, not about them).

## D-030 — The LMS boundary is a port in *our* vocabulary, with the contract expressed as an executable test suite
**Decision:** All LMS access goes through one interface, `LmsPort` (`apps/api/src/moodle/lms.port.ts`), injected by the DI token `LMS_PORT`. Three things make it a real anti-corruption layer rather than a proxy:
1. **The types are ours.** `LmsCourse`, `LmsCourseProgress`, `LmsUserRef` — nothing mirrors a Moodle payload. No `fullname`, no `completionstatus`, no `enrolledusercount`. Translating Moodle's shapes is the Phase 2 adapter's job, confined to `real/moodle-http.service.ts`. A contract test asserts Moodle's native field names never appear on a returned object, so a leak fails CI rather than quietly coupling every caller to Moodle's schema.
2. **The contract is executable, not just an interface.** `lms.contract.ts` exports `describeLmsContract(name, factory)` — a suite asserting the *behaviours* callers depend on: `provisionUser` and `enrol` are idempotent, an unenrolled user yields `null` (not an empty object), an enrolled-but-unattempted course reports a **null** grade rather than 0, `listCourses` returns copies rather than shared mutable state, and `courseUrl` embeds no token. A shared interface only proves method names line up; these are what actually break when an implementation is swapped. Phase 2 runs the same suite against the real adapter — if it passes, no caller changes.
3. **No product logic crosses the boundary.** `LmsCourseProgress` carries `gradePercent` and deliberately has **no `passed` field**; a contract test asserts its absence. The pass threshold is a product setting (D-007), so if the LMS decided pass/fail, changing certification policy would mean editing Moodle quizzes.
**Two supporting choices:**
- **`MOODLE_MODE=real` fails loudly.** The Phase 2 adapter exists now, declared `implements LmsPort`, with every data method throwing `NotImplementedException`. Two benefits: the compiler breaks it the moment the port gains a method, so the interface cannot drift ahead of the real adapter unnoticed; and flipping config early produces an explicit refusal rather than an integration that appears to work while reporting every course as empty. `checkHealth()` is the one exception — it reports `reachable: false`, because a health endpoint exists to report bad states, not to crash a dashboard.
- **Mock-only helpers stay off the port.** `simulateCompletion`, `simulateAttempt` and `reset` live on `MockLmsService`, never on `LmsPort` — a real Moodle adapter could not implement them, so putting them on the interface would break the swap. The contract suite touches only port methods.
**Verified:** 40 tests across the contract and wiring suites; `/api/health` reaches the mock through `LMS_PORT` and reports `{"lms":"up","lmsSiteName":"Tamkeen Mock LMS"}`; `MOODLE_MODE=real` boots, reports `"lms":"down"` and throws `Phase 2` on any data call; `MOODLE_MODE=real` without a base URL refuses to boot at all. A wiring test resolves the *same* consumer class under both modes, which is the Checkpoint F claim made checkable.
**Also fixed while here:** `MoodleModule` now imports `AppConfigModule` explicitly instead of relying on its `@Global` registration. Implicit reliance on globalness means a module cannot be compiled in isolation, which turns a unit test into a whole-application boot.
**Rejected:** exposing Moodle's REST shapes directly (couples every caller to the LMS; an LMS change would touch the whole codebase); a port named after Moodle (invites callers to assume Moodle-specific behaviour); returning `passed: boolean` (moves certification policy into the LMS); leaving the real adapter unwritten until Phase 2 (nothing would keep the interface and the future implementation in step); mock methods on the port (makes the swap impossible).

## D-029 — Configuration is read from a validated object, never from `process.env` (security defect fixed)
**Decision:** `@nestjs/config` was removed. `AppConfigService` now holds the object returned by the zod validator and reads directly from it.
**Why — this was a live authentication bypass, not a style preference.** `ConfigService.get()` consults `process.env` *in preference to* the object returned by `validate`, so every setting arrived as the raw environment string rather than its parsed type. The consequences, in order of severity:
1. **`ALLOWED_EMAIL_DOMAINS` came back as the string `"ministry.gov.example"` instead of `["ministry.gov.example"]`.** The registration gate then called `.includes(domain)` on a *string*, which is substring matching — so **`attacker@ministry.gov` would have satisfied a gate configured for `ministry.gov.example`**, and self-registration was open to any domain that happened to be a substring of an allowed one. This defeats D-017, the rule that keeps the system from being an open sign-up.
2. `RATE_LIMIT_ENABLED=false` came back as the string `"false"`, which is truthy — a boolean switch that silently did nothing.
3. Numeric settings came back as strings, so arithmetic on them would concatenate rather than add.
**How it surfaced:** the integration tests could not disable rate limiting and kept returning 429. Chasing *that* symptom is what exposed the type problem underneath. The domain bypass had no failing test of its own — the existing domain test used `gmail.com`, which fails a substring check too, so it passed for the wrong reason. It is worth noting plainly that a green test suite did not catch this.
**Guards added:** `app-config.spec.ts` asserts the *types* coming out of configuration (arrays are arrays, numbers are numbers, `"false"` is `false`), and `registration-policy.spec.ts` gained explicit tests that a domain which is merely a **prefix** or **substring** of an allowed one is rejected.
**Rejected:** keeping `@nestjs/config` with `skipProcessEnv` (relies on remembering an opt-out flag whose absence is silently insecure); casting at each call site (spreads the problem instead of removing it).

## D-028 — Opaque server-side sessions in Postgres; in-process rate limiting for now
**Decision:** Authentication uses **opaque 256-bit random session tokens stored as SHA-256 hashes in a `sessions` table**, delivered in an `httpOnly; SameSite=Strict; Secure` cookie. Not JWTs. Per-account brute-force lockout lives in the database; per-IP rate limiting is `@nestjs/throttler` with **in-process** storage. CSRF is a double-submit cookie/header pair on top of `SameSite=Strict`.
**Why opaque, not JWT:** revocation. A stateless token stays valid until it expires, so suspending an account or signing out cannot take effect immediately. Here both do — an integration test suspends an account and the very next request is rejected. For a government system where "disable this employee's access now" is a real operational requirement, that is worth a database lookup per request.
**Why Postgres, not Redis:** signing in should not depend on a second datastore being healthy. Redis remains in the stack for BullMQ (Phase 2). Keeping sessions in Postgres also lets Phase 5 show an administrator the active sessions on an account, which an opaque Redis key cannot.
**Why only the hash is stored:** the same reasoning as `auth_tokens` — a database dump must not yield presentable sessions. SHA-256 rather than argon2 because these are CSPRNG tokens with no guessable structure; a slow hash protects nothing here and would add latency to every request.
**Rate limiting — the honest limitation:** in-process storage is correct for a single API instance, which is the Phase 0 target, but **counters are per-instance, so horizontal scaling multiplies the effective limit**. Phase 7 must swap in a shared store when it decides the deployment topology. Per-account lockout is unaffected by instance count, and it is the protection that matters against a targeted attack; per-IP throttling mainly blunts broad spraying. `RATE_LIMIT_ENABLED` exists so integration tests can make hundreds of requests, and `validateEnv` **refuses to start with it disabled in production** — a switch that could be flipped in production would defeat the point.
**Also decided:** no `JWT_SECRET` or `SESSION_SECRET` in configuration. There is nothing to sign, and dead config invites someone to "use" it later in a way nobody designed.
**Rejected:** JWTs (no immediate revocation); Redis sessions (extra hard dependency in the sign-in path); signing the session cookie (a 256-bit random value already cannot be forged); relying on `SameSite` alone for CSRF (leaves older browsers and a compromised same-site subdomain uncovered).

## D-027 — RBAC is role-based and code-defined, not a database permission table
**Decision:** Authorization is driven by the `UserRole` enum on `users` (`EMPLOYEE` / `ENTITY` / `SUPER_ADMIN`) plus guards in code. There is **no `permissions` table and no role–permission join table.**
**Why:** The system has exactly three fixed portals, and §6 describes roles, not a configurable permission matrix. Putting permissions in the database implies they are editable at runtime, which creates a privilege-escalation surface — anyone with a single UPDATE on that table becomes a super-admin, and the change leaves no trace in code review. Code-defined roles are versioned in git, reviewable in a PR, and diffable during a security audit, which is what a government system needs. A DB-backed permission matrix is the right answer when customers define their own roles; nobody here does.
**Also considered and deferred:** inventing a fine-grained permission taxonomy now (`assessment:take`, `admin:manage-paths`, …). Rejected as speculation: those strings would describe features that do not exist yet, and Phase 4/5 are the phases that will actually know what an entity or admin may do. Introducing a permission layer later is a contained change *behind the guard*, whereas a wrong taxonomy baked in now would spread through every controller.
**Consequence:** Phase 4 must add entity *scoping* (which courses/learners an entity may see). That is data-scoped filtering, not a new role, and belongs with the entity model in Phase 4. A test asserts the Prisma `UserRole` enum and `USER_ROLES` in `@tamkeen/types` never diverge, since a silent mismatch would make RBAC checks stop matching without failing loudly.

## D-026 — Prisma 7 with the pg driver adapter (schema no longer holds the URL)
**Decision:** Adopt **Prisma 7** rather than pinning Prisma 6. Prisma 7 removed `url` from the `datasource` block, so the connection is configured in two places by design: `apps/api/prisma.config.ts` for CLI/migration commands, and the **`@prisma/adapter-pg` driver adapter** passed to `PrismaClient` for the runtime. The generated client is emitted to `apps/api/generated/prisma` (gitignored) and regenerated by a `postinstall` hook.
**Why:** Prisma 7 is the current major. Starting a system intended to run for years on an already-superseded major buys short-term familiarity and pays for it with an earlier end-of-support and a migration later, during hardening or after launch — exactly when a government system should not be taking framework upgrades. The adapter change is contained: one config file and one constructor.
**Details worth knowing:**
- Prisma 7 also stopped auto-loading `.env`, so `prisma.config.ts` loads the root `.env` explicitly, matching the `envFilePath` the Nest config module uses.
- The datasource URL deliberately does **not** use Prisma's `env()` helper, which throws when the variable is absent. `prisma generate` needs no database and runs on postinstall, so a fresh clone with no `.env` must still install. The fallback is the literal string `postgresql://DATABASE_URL-is-not-set`, so if a command that genuinely needs the database runs unconfigured, the connection error names the missing variable rather than being cryptic.
- CI generates the client and applies migrations before typecheck, because the client is generated rather than committed.
- `npm ls` style caveat: ESLint had to be told to ignore `generated/**` — the machine-written client is not ours to lint.
**Rejected:** Prisma 6 (familiar `url = env(...)`, no adapter, but a shorter support horizon for a long-lived system); committing the generated client (bloats diffs and goes stale against the schema); Prisma Accelerate (a managed proxy is inappropriate for an internal ministry deployment).

## D-025 — Gold cannot carry body text at AA; two functional colours added
**Decision:** Measured contrast forced two adjustments to how the §3 palette is applied. Neither changes a brand value; both constrain or extend usage.
**(a) Gold is a non-text and large-text colour only.** `--color-gold` `#A8863C` measures **3.42:1 on white, 3.08:1 on cream, 3.99:1 on navy** — all below the 4.5:1 AA floor for body text (WCAG 1.4.3). Worse, a *gold fill* fails in both directions: white-on-gold is 3.42:1 and navy-on-gold 3.99:1, so there is no legible body-size label for a solid gold button. Gold is therefore restricted to **borders, focus rings, icons, accent edges, and large/bold text**, where the 3:1 threshold (WCAG 1.4.11) applies and it passes. Where a gold *fill* is needed behind body text — the achievement button, and the "موصى به" recommended badge in Phase 1 — the fill is **`--color-gold-light` `#C9A85C` with navy text, which measures 6.01:1** and passes comfortably.
This turns out to reinforce §3's own instruction rather than fight it: gold was always meant to be scarce and signal-carrying. A palette that physically cannot support gold as a body-text colour is a palette that keeps gold meaning "recommended".
**(b) Two functional status colours added, outside the brand palette:** `--color-danger` `#A32015` and `--color-success` `#1E6F4E`. §2B DoD 4 makes error states mandatory on every data view, and the brand seven contain no signal colour — an error rendered in navy is not an error. Both clear 4.5:1 in *either* direction on white and cream (danger 7.57/6.82, success 6.11/5.51). They are declared in a separate, commented block in `globals.css` so they cannot be mistaken for brand accents and so gold stays scarce.
**Why enforce it in tests:** `src/lib/contrast.test.ts` computes every pairing the design system uses and asserts its required ratio — 24 assertions, including deliberate *negative* tests proving gold body text fails, which document why the restriction exists. WCAG 2.1 AA is a government obligation; "the gold looks fine" is exactly the judgement that fails an audit. A test also means a future palette tweak that breaks AA fails CI instead of shipping. `src/lib/tokens.ts` mirrors the palette for the tests and a test asserts the mirror matches `globals.css`, so the two cannot drift.
**Rejected:** darkening `#A8863C` until it passes for text (changes a locked brand value — not mine to make); using gold body text anyway and accepting the AA failure (a government accessibility obligation is not optional); reusing navy for errors (removes the distinction between "failed" and "normal"); pulling in a full third-party palette for status colours (two values are enough, and more colour weakens gold's signal).

## D-024 — next-intl without locale routing; one formatting layer shared by both apps
**Decision:** `next-intl` is configured **without i18n routing** — no `/ar` URL prefix, no `[locale]` route segment, no middleware. Arabic is the sole locale; `<html lang="ar" dir="rtl">` is fixed, not negotiated. All UI copy lives in `apps/web/messages/ar.json`; no user-visible string is hardcoded in a component, including the document title.
The locale handed to next-intl is the **extended** tag from `formatLocaleTag()` (e.g. `ar-u-nu-latn-ca-gregory`), not bare `ar`, because next-intl passes it straight to `Intl` — so numbers and dates inside ICU messages honour the D-018 digit/calendar switch automatically. The bare `ar` is used for `<html lang>` via `HTML_LANG`, since an extension subtag there would be invalid HTML.
Client components reach the same formatters through `FormatProvider` / `useFormat()`, seeded from the server-resolved context. This exists because `NUMBER_FORMAT` is a server-only variable: without it, client components would have no access to the setting and would drift into calling `Intl` directly — the exact fragmentation D-018 forbids.
**Why no locale routing:** adding `/ar` to every URL of a single-language internal system is permanent noise for a hypothetical future. `next-intl` supports both modes, and the migration path is understood: introducing English means adding a `[locale]` segment and middleware, which is a contained change to routing, not to the message catalogs or the formatting layer.
**Verified:** the same page, rebuilt with only environment variables changed and **zero code edits**, renders `1,248 / 85% / 17 أغسطس 2026` under the defaults and `١٬٢٤٨ / ٨٥٪ / ٤ ربيع الأول ١٤٤٨ هـ` under `NUMBER_FORMAT=arabic-indic DATE_CALENDAR=islamic-umalqura`. A catalog test additionally fails the build on any empty string, unbalanced ICU braces, or stray English copy, so the Arabic-first rule is enforced mechanically rather than by review discipline.
**Caveat:** for statically prerendered pages the setting is baked in at build time, so flipping it on an existing deployment requires a rebuild. Acceptable — it is a one-time deployment choice, and the authenticated pages that dominate this product render per request.
**Rejected:** locale-prefixed routing now (URL noise, no current benefit); letting next-intl own number/date formatting while `packages/types` owns it for the API (two implementations would drift, and a certificate PDF disagreeing with the screen that announced it is a real failure mode); reading `process.env` directly in components (defeats the single switch point).

## D-023 — Self-host the Arabic typeface instead of fetching it from Google Fonts
**Decision:** IBM Plex Sans Arabic is committed to `apps/web/src/fonts` as four "complete" woff2 files (400/500/600/700, ~74 KB each) and loaded with `next/font/local`. `next/font/google` is not used. The OFL 1.1 licence text ships alongside the fonts, since the repo now redistributes them.
**Why:** Three reasons, in order of weight. (1) **Build reliability** — `next/font/google` fetches at build time; the first build here retried the fetch five times before succeeding, and a ministry environment behind a proxy or air-gapped would fail outright. A production build must not depend on reaching a third party. (2) **Privacy** — a Google-hosted font means every employee's browser makes a request to Google carrying its IP and user agent on every visit to an internal government system. That is a needless third-party disclosure of who is using the platform and when, and it is exactly the kind of thing §2's PII-minimisation stance exists to prevent. (3) **Correctness** — the "complete" files cover Arabic glyphs *and* Latin digits in one file per weight, so the Western Arabic numerals that D-018 makes the default render in the same typeface as the Arabic text instead of falling back to a system font. Google's API splits by subset, which cannot express that cleanly through `next/font/local`.
**Verified:** production build succeeds with no network retries; the served page references `/_next/static/media/*.woff2` and contains **no `fonts.googleapis.com` or `fonts.gstatic.com`** reference at all.
**Cost:** ~298 KB of binary in the repo, and the fonts must be refreshed manually if IBM ships an update — a deliberate trade for a build that cannot fail on someone else's uptime.
**Rejected:** `next/font/google` (build-time network dependency + third-party disclosure); depending on the `@ibm/plex-sans-arabic` npm package and pointing `next/font/local` into `node_modules` (avoids committing binaries, but the path is fragile under workspace hoisting); hand-written `@font-face` rules with `unicode-range` (more control, but loses `next/font`'s automatic preloading and layout-shift compensation).

## D-022 — Clear transitive CVEs with npm `overrides` rather than moving off the locked Next.js 15
**Decision:** The first install carried **3 high-severity transitive advisories** through Next 15.5.23 — four `postcss` issues (XSS via unescaped `</style>` in stringify output; arbitrary `.map` file read via attacker-controlled `sourceMappingURL`) and the `sharp`/libvips set (CVE-2026-33327/33328/35590/35591). `npm audit fix --force` resolves them only by installing **Next 16**, which is a breaking change and contradicts D-013. Instead, root `overrides` pin `postcss@^8.5.26` and `sharp@^0.35.3` for the whole tree, including inside `next` (which pins `postcss` exactly at `8.4.31` and `sharp` at `^0.34.3`). Result: **`npm audit` reports 0 vulnerabilities** and Next 15.5.23 still builds, serves, and passes tests.
**Why:** A government system should not begin Phase 0 with known highs baked into its lockfile, and it should not silently defer them to Phase 6 either. Overriding a patch/minor within the same major is low-risk (stable public APIs), and it was verified end-to-end rather than assumed: full production build, the Tailwind v4 CSS pipeline still emitting the brand tokens to the served stylesheet, both apps booting, all tests green. `npm ls` labels the overridden packages `invalid` because they fall outside Next's declared ranges — that is the expected, cosmetic signal of a deliberate override, not a broken tree.
**Why not just accept them:** real exposure here is genuinely low (the postcss issues need attacker-controlled CSS at build time, and ours is repo-authored; the sharp issues need attacker-supplied images through `next/image`). But "low exposure" is an argument for not panicking, not for shipping a red audit — and the override cost nothing.
**Consequence / revisit:** overrides are a standing maintenance obligation — each Next upgrade must re-check that the pins are still needed and still compatible. Phase 6's dependency review owns that check, and should also decide whether to drop the `sharp` pin by disabling `next/image` optimisation entirely (the app has no need to process untrusted images).
**Rejected:** Next 16 now (breaks the locked stack mid-Phase-0, and 15.x is the version the rest of the plan assumes); accepting 3 highs and deferring to Phase 6 (leaves the baseline red for six phases); `npm audit fix --force` (same as adopting Next 16, but without the decision being explicit).

## D-021 — Local dev dependencies run in Docker; Mailpit is the dev mail sink
**Decision:** A root `docker-compose.yml` provides PostgreSQL 16, Redis 7 and **Mailpit** for local development (`npm run db:up` / `db:down`). Development `SMTP_HOST/PORT` point at Mailpit (`localhost:1025`, inbox at `http://localhost:8025`). Postgres/Redis image versions match the CI service containers. This file is a **development convenience only** — real environments, secrets management and deployment topology are Phase 7.
**Why:** No local PostgreSQL was installed (Docker was), so Docker is the lowest-friction path to a working DB and gives dev/CI parity on image versions. Email verification and password reset (0.5) are unusable without somewhere for mail to land; Mailpit makes the verification link readable with **no real SMTP credentials and no risk of mailing a real inbox from a dev box** — which matters because these are ministry-employee addresses.
**Rejected:** Requiring a hand-installed local Postgres (per-machine drift, no CI parity); logging verification links to the console only (works, but hides the actual rendered Arabic email, so RTL email bugs would go unnoticed until late); pointing dev at a real SMTP relay (risks sending mail to real employees during development).

## D-020 — npm workspaces as the monorepo tool
**Decision:** Use **npm workspaces** (`apps/web`, `apps/api`, `packages/types`) rather than pnpm or yarn. `packages/types` is compiled to `dist` and consumed via its `main`/`types` entry points, built by an explicit `build:types` step that runs before typecheck/build.
**Why:** §2A left the workspace tool open ("pnpm/npm/yarn"). npm ships with Node so there is no bootstrap step for a new developer or for CI, and the provided CI workflow already assumed `npm ci`. Compiling the shared package (instead of importing raw source) keeps NestJS's `tsc` build and Next's bundler both working without special-casing, and means the published type surface is exactly what consumers see.
**Rejected:** pnpm (fastest and best at monorepos, but not installed locally and adds an install-pnpm step to CI for no benefit at this repo's size); yarn (same bootstrap cost, no advantage here); a single package with folders (loses the enforced boundary that stops the frontend importing backend internals).

## D-019 — Auth is email/password only (no AD/LDAP); Moodle target = latest 4.5.x LTS
**Decision:** (a) The ministry does not require AD/LDAP integration; the system uses **email/password authentication only** (app is the identity owner, provisioning Moodle accounts behind the scenes). The AD/LDAP hardening path in D-004 is dropped unless the ministry later requests it. (b) Deploy the **latest Moodle 4.5.x LTS** patch (from github.com/moodle/moodle, newest `v4.5.x` tag / download.moodle.org). Requires PHP ≥ 8.1 (8.3 supported), sodium extension, `max_input_vars ≥ 5000`.
**Why:** (a) User confirmed email login is the intended, sole mechanism — removes the biggest Phase 2 auth unknown. (b) 4.5 is the current LTS with security support to 4 Oct 2027; the next LTS (5.3) isn't out yet, so 4.5.x is the stable choice for a government system. General bug-fix support for 4.5.x ended Oct 2025, so always run the newest 4.5 patch for security.
**Rejected:** AD/LDAP/OAuth2 SSO (not wanted); Moodle 5.x non-LTS (shorter support, less stable for gov); pinning an old 4.5.x patch (misses security fixes).

## D-015 — Assessment retake locked to pre-commitment; course-edit protection

## D-013 — Tech stack & architecture
**Decision:**
- **Frontend:** Next.js 15 (React + TypeScript), Tailwind CSS, shadcn/ui, `next-intl` (Arabic-first RTL).
- **Backend:** NestJS (Node.js + TypeScript) as a **dedicated API**, not Next.js route handlers.
- **DB:** PostgreSQL + Prisma ORM.
- **Async/jobs:** Redis + BullMQ (scheduled Moodle completion sync, certificate generation).
- **PDF:** headless-Chromium (Puppeteer) HTML→PDF for Arabic-correct certificates + CVs.
- **Moodle:** v4.5 LTS, Web Services (REST) + Catalyst RESTful plugin; access isolated behind one NestJS "Moodle integration" module (anti-corruption layer). Least-privilege token, stored server-side only.
- **Auth:** app is IdP (email/password, verified); JWT/session for the app; token-mapped Moodle handoff for MVP, OAuth2/AD-LDAP as hardening target.
**Why:** The system is integration-heavy and long-lived with background jobs, RIASEC scoring, certificate generation, three role-based portals, and government-grade audit/security needs. A dedicated opinionated backend (NestJS) keeps that maintainable and scalable far better than packing logic into Next.js handlers (industry consensus: Next.js-only backends accrue refactor debt past ~18 months for team-scale, logic-heavy systems). Shared TypeScript lets front/back share the RIASEC + path types. Postgres/Prisma is the safe system-of-record choice. Chromium-based PDF is the most reliable route to correct Arabic RTL shaping. Moodle 4.5 LTS is supported to late 2027; the RESTful plugin gives real HTTP status codes instead of always-200. Isolating Moodle behind one module means an LMS change touches one place.
**Rejected:** Next.js-only full-stack (logic/jobs/roles outgrow route handlers); Express (less structure than NestJS for a multi-portal system); Django/Laravel (loses shared-TypeScript benefit); non-LTS Moodle (shorter support window); common PDF libs without robust Arabic shaping (RTL/ligature bugs).

## D-011 — Assessment is Holland (RIASEC); paths tagged by letter; gold = letter in top-three code
**Decision:** Use the Holland Codes / RIASEC framework. Scoring tallies points per dimension → ranked profile → top-three **Holland Code**. Every path is tagged with one **primary RIASEC letter**. A path is recommended (gold) if its letter is in the user's top-three code, ranked by the user's letter order. Non-matching paths remain selectable. Store all six dimension scores, not just the code.
**Why:** User specified a Holland-based assessment with each path linked to a Holland category. Top-three code is the standard Holland output and richer than a single letter; storing all six enables ranking and later re-explanation. Matching by "letter ∈ top-three code" preserves the single-path rule while using the real framework and keeps gold meaningful without caging the user.
**Alternatives considered:** Match only the single #1 letter (too narrow — most careers are blends, and few paths would be gold); reduce the result to one opaque letter (loses the framework's value). If stricter/looser matching is wanted later, revise this entry.
