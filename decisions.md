## D-045 — The landing page's assets and motion are migrated; the rest of the reference is not
**Decision:** A traced migration rather than a copy. Starting from the reference's landing entry point, every import was followed to its source; the result was 44 missing asset files, one keyframe, and one dependency. Those came across. Nothing else did.

**What the trace found, and it is worth recording:** the seven landing sections import **nothing** from `hooks/`, `lib/` or `utils/` — only `lucide-react`, `react-router-dom`, the i18n context, and one local `shared.tsx`. Those three directories looked like migration candidates and were not. Equally, only ONE animation class appears anywhere in the landing tree (`animate-marquee-x`); the float, shimmer and pulse-glow keyframes in the reference stylesheet belong to a different branch's hero and were left behind.

**Assets — the actual gap.** Two of forty-six files had been copied in earlier sessions; the page was rendering forty-four references to files that did not exist. Now migrated: forty-one institution marks, the technology and training partner marks, and the university emblem. Path shape changes with the platform — the reference imports them as bundler modules (`@/assets/...`), Next serves them from `public/`, so they are addressed by URL and named in one table beside the component that draws them. Verified by walking the rendered page in Chromium: 87 images, none broken, no failed requests.

**Motion.** `framer-motion` was taken on deliberately, for the reference's scroll-reveal on the roadmap cards and its numbered milestones. It is wrapped once at the root in `MotionConfig reducedMotion="user"` rather than checked per component: the global CSS reduced-motion block cannot reach transforms driven from JavaScript, and the guard that gets forgotten is the one in the component added next.

**Two things deliberately NOT migrated, each for a specific reason:**
- **`components.json`.** The reference declares `rsc: false` and `rtl: false`. Copying it would misconfigure every future shadcn addition in an App Router project that is RTL by default.
- **The Latin typeface.** The reference sets Geist ahead of IBM Plex Sans Arabic. IBM Plex Sans Arabic is a complete family with Latin glyphs, so keeping it costs the English view some fidelity and saves every visitor a second font download — and D-023's reasoning about self-hosting one face still holds. The user was asked and chose this.

**One test-environment consequence:** jsdom implements no `IntersectionObserver`, and framer-motion's `whileInView` throws without it — eleven landing tests died on the first run after the dependency landed. `vitest.setup.ts` now shims it, reporting observed elements as intersecting so assertions see the settled state rather than the pre-animation frame. Like the `showModal` shim beside it, it stands in for the missing API and not for the behaviour; intersection itself is exercised in Chromium.

**Rejected:** copying `hooks/`, `lib/`, `utils/` (traced: nothing in them is reachable from the landing page); migrating the unused keyframes (they belong to another branch's hero); `react-router-dom`, `@supabase/supabase-js`, `recharts`, `driver.js`, `zod`, `@base-ui/react` (none touches this page); the two IMSIU logo variants in the reference's public folder (the landing page references only the emblem).

## D-044 — Stakeholders become tabs, the partner list ships as names, and the footer links only where a page exists
**Decision:** Four regions were rebuilt to the content the user supplied from the reference site: the stakeholder section now carries **six** actors (the graduate track was missing) as a tabbed selector, partnerships lists the academic partner and the participating institutions by name, the closing CTA gains a dashboard mock, and the footer is the full four-column version.

**Why the stakeholders are tabs and not six stacked cards:** six actors times three capabilities is eighteen lines, of which exactly one actor describes any given reader. Shown at once it is a wall; chosen, it is three lines. It is a real WAI-ARIA tablist — roving tabindex so Tab steps past the group instead of through all six, arrows to move, Home/End to jump, and a focusable panel so the keyboard lands in the content it just revealed. **The arrow keys are mirrored in Arabic**: "next" is the key pointing at the end of the line, which is ArrowLeft in RTL, and hardcoding ArrowRight-as-next walks an Arabic reader backwards through the list.

**Why the partner list is names and not a logo wall:** the reference renders each partner's mark. Those are three dozen third-party trademarks; copying the image files in attaches a licensing question to every one of them and says nothing the names do not. The names ship in full, each `dir="ltr"` so Latin strings keep their internal order inside the Arabic page.

**Why it is a wrapped list and not the reference's marquee:** which partners a reader can see should not depend on when they happened to look. A scrolling row cannot be scanned, cannot be found with the browser's own in-page search, and has to stop under `prefers-reduced-motion` anyway — at which point it is this list, only clipped.

**Why most footer items are text, not links:** the reference footer links to opportunities, a skills record, four role dashboards, about, contact, privacy and terms. **Only sign-in exists in this application.** A link that 404s advertises a page, costs a click to discover it is not there, and reaches a screen-reader user announced as a link to nowhere. Each item renders as its label and carries an optional `href` in `FOOTER_GROUPS`: fill one in and it becomes a link, with nothing else to change.

**Two smaller calls:** the dashboard mock is a *picture of a screen*, so its Latin field names live in the component rather than the catalogs and the whole frame is `aria-hidden` behind one accessible description — read aloud, a list of disconnected numbers tells a screen-reader user nothing the heading beside it has not. And the ministry classification line was dropped from the footer: it read "internal — for government use" under a page about university students.

**One addition to the shared formatting layer:** `formatYear`. A year is the one number that looks like a quantity and is not, so `formatNumber` renders 2026 as "2,026". It still goes through the layer rather than `String(year)`, so the D-018 digit switch reaches the copyright line like everything else.

**The layouts match the reference too, not just the words.** Read from its source rather than inferred from screenshots: the stakeholder selector is a six-across row of icon-topped cards with the active one filled and underlined in gold, above a white panel of three icon-and-text columns, all on a warm gold wash; partnerships is a single card with a filled gold band for the academic partner and the institution list beneath it; the closing section is a centred column on near-black with the browser mock below it; the footer is four columns on navy under a gold hairline, headed in light gold.

**That needed two more tokens from the reference palette**, both used and both measured: `--color-gold-pale` (#f5f0e3), the warm wash behind the selector, and `--color-ink` (#1a1409), the near-black olive the closing section sits on — not a second navy, it reads as unlit gold, which is what makes the gold on top of it look lit. Seven new pairings are asserted in `contrast.test.ts`, including the two that unlock these layouts: white on gold-deep is 5.25:1, so the academic-partner band can carry text, and light gold on navy is 5.67:1, so the footer headings can be gold rather than white.

**Rejected:** six always-open cards (the eighteen-line wall); copying the partner logo files (licensing question per file, no gain over names); a marquee (unscannable, unsearchable, and it stops under reduced motion regardless); footer links to routes that do not exist (a 404 is worse than a label); hardcoding the year (someone has to remember it every January).

## D-042 — The reference frontend's brand palette and hero artwork are adopted wholesale
**Supersedes the values D-009 locked and CLAUDE.md §3's colour table.** The product *rules* about colour survive unchanged — gold still means "recommended/achievement" and stays scarce; only which colours carry those roles has changed.

**Decision:** The palette comes from the reference frontend's `master` branch: navy `#0a2e42`, brand blue `#045d84`, sky `#b3ddf5`, page background `#dfe7f4`, gold `#99823f`, warm gold `#b7a362`, plus `#806b30` as a deeper gold. Our token *names* are unchanged, so every screen in the app — portal, auth, assessment — inherits the new brand without a component edit. The hero's hand-drawn SVG sky is replaced by the reference's own background image, and the hand-drawn wordmark by the brand's real logo lockup.

**Why the branch matters:** the design in the screenshots is on `master`, not on the branch named `Tamkeen` — that one is a dark navy/gold treatment with a 3D dashboard mockup and is a different design entirely. Anyone comparing against the wrong branch will conclude this implementation is wrong.

**Why the artwork is copied rather than redrawn:** the SVG sky was an approximation built from screenshots. Artwork owned by the brand is not something to reproduce shape by shape — an approximation has to be re-tuned every time the real one changes, and it is never quite right in between.

**Four places the reference is deliberately NOT followed, each for a measured reason** (all asserted in `src/lib/contrast.test.ts`, so none can be quietly undone):
1. **`--muted-foreground`.** Its `#7a8b95` is 3.53:1 on white and 3.21:1 on its own page background — it cannot carry secondary text at AA, and secondary text is everywhere. The hue is kept and the value darkened to `#566577`, the lightest that clears 4.5:1 on both (6.09:1 and 4.89:1).
2. **Form-field borders.** The reference uses its pale sky line for both cards and inputs. On a card that is decorative and 1.16:1 is the intent; on a text input the border is the only thing that says where the control is, so WCAG 1.4.11 asks for 3:1 and 1.44:1 does not meet it. Inputs use muted instead.
3. **Its `--secondary` pairing**, white text on gold, is 3.74:1. A test asserts that failure so it cannot be re-introduced from the reference by hand.
4. **The functional colours.** Its `#c0392b` is 4.35:1 on the new background and its `#2d9f6f` is 3.33:1 on white — both below the floor for the error and success text they exist to carry. Ours are kept.

**What the swap buys, beyond matching:** `gold-deep` is the first gold in this project that can carry body-size text (5.25:1 on white, though only 4.26:1 on the page background — white surfaces only). The hero eyebrow is now gold text, which is what the reference does and what D-025's old palette made impossible. The tracked-uppercase treatment the reference applies to it is scoped to `ltr:` — Arabic is cursive, so letter-spacing pulls joined letters apart, and there is no uppercase to set it in.

**Blast radius, stated plainly:** this repaints every authenticated screen too. Those screens pass the contrast suite but have not been looked at.

**Rejected:** keeping the ministry palette and matching only layout (the user was asked and chose the reference's colours); adopting the reference palette on the landing page alone (a visitor would meet two different brands one click apart); redrawing the hero as SVG (approximation with a permanent maintenance tail); adopting `#7a8b95` and `#b3ddf5` for text and inputs as-is (fails AA in a system with a government obligation and an enforcing test).

## D-041 — A real language switch: cookie-scoped locale, full English catalog, direction derived from the locale
**Supersedes the single-locale half of D-024.** RTL is no longer unconditional; Arabic remains the default, the fallback, and the first entry in `LOCALES`.

**Decision:** The reader's language lives in a `tamkeen.locale` cookie. `getRequestLocale()` reads it server-side, `request.ts` loads `ar.json` or `en.json` from it, and the root layout derives `<html lang>` and `<html dir>` from the same value. The header's placeholder (D-039) is now a working control that writes the cookie and calls `router.refresh()`. **The entire catalog is translated — all 370 strings, not the landing page's share of them.**

**Why the whole catalog and not just the landing page:** it was offered as the cheaper option and it is a trap. A visitor switches to English on the landing page, clicks "Sign in", and lands in Arabic — the switch would advertise a capability the product does not have. Two catalogs also drift silently, because next-intl renders a missing key as the key itself: an English page shows `landing.gap3Body` where a sentence belongs, and nothing fails. `messages.test.ts` therefore asserts identical key sets, identical ICU placeholders per key, no leftover Arabic script in `en.json`, and no hardcoded digits in either. The placeholder check is the one that earns its keep — a dropped `{count}` still reads like a fluent sentence.

**Why a cookie, not `/[locale]` routing:** the app has one canonical URL per page, and §2 requires certificate verification URLs to be stable and shareable with third parties. Prefixing every route rewrites the whole link graph to encode a preference that is not part of a page's identity. The price is real and worth naming: reading a cookie opts routes into dynamic rendering, so the landing page can no longer be statically cached at build time.

**Why direction is derived, never stored:** `directionFor(locale)` is a function, so there is no second switch to forget. A page cannot end up Arabic-but-LTR. Two consequences in the components: the hero artwork is drawn once for RTL and flipped with `ltr:-scale-x-100` rather than re-drawn, and the directional glyphs (`ArrowLeft`, `ChevronLeft`) rotate under `ltr:` instead of being swapped for their mirror twins — one icon that follows the reading direction beats two that must agree on which way "forward" is.

**Scope held deliberately:** the API stays `DEFAULT_LOCALE: z.literal('ar')`. Certificates, the CV and transactional email remain Arabic — §2 makes Arabic PDF rendering a product requirement, and an English certificate is a document decision for the ministry, not a side effect of a UI toggle. 189 API tests still pass.

**Owed:** the English copy is a **first draft by the implementer, not a reviewed translation** — the same standing as D-032's Arabic question wording. It needs a native review before launch, and the ministry has to confirm it wants an English surface at all.

**Rejected:** the visual-only placeholder (D-039 — the user asked for the real thing instead); translating only the landing namespace (dead end on the first click, and the parity test could not exist); `next-intl` locale routing (rewrites every URL, including ones §2 wants stable); `localStorage` plus a client-side swap (the server renders the messages, so the choice has to reach it on the request); a second webfont for Latin (IBM Plex Sans Arabic is a complete family — D-023's reasoning about third-party requests still applies).

## D-040 — The landing page grew to the seven-link bar, and each link had to earn a section
**Decision:** The public bar carries the seven links of the supplied reference — الرئيسية / التحديات / المزايا / كيف تعمل / المنظومة / الشراكات / العرض التوضيحي — and the page grew three new sections (features, ecosystem, partnerships, demo) so that every one of them scrolls to something real. The current section is marked with a gold-outlined pill driven by an `IntersectionObserver`.
**Why sections rather than links alone:** the user first chose the three real anchors, then asked for the full seven. Adding four links to sections that do not exist is the one thing §3 flatly forbids, so the only way to honour the request was to build what they point at. `landing.test.tsx` now resolves every `href` against the rendered DOM, asserts each target carries `scroll-mt` (or the sticky header lands on the heading) and `tabIndex={-1}` (or focus stays behind in the bar) — the bar and the page can no longer drift apart silently.
**Where the content came from:** every claim traces to this repo's own brief — the assessment length and RIASEC shape (§3A, D-032), the 5–10 commitment (§2), the one-directional completion sync (D-000), the two certificate levels and their verification (§2), the three portals (§1, Phases 4–5). Two things were deliberately *not* copied from the reference: its adoption metrics (78% employment rate and friends — invented numbers for a platform that has not launched) and any named or badged partner. The partnerships section therefore describes the *shape* of a partnership and ends with an explicit note that the list is published at launch; `demoNote` likewise states in the page that the example profile is not a real result.
**Two structural calls inside that:**
- **The challenges section is organised by audience, not by symptom.** Four cards — employees, the training directorate, supplying entities, and whoever must trust a certificate — each with three bullets. Naming who feels a gap is what makes the gap checkable; the previous three abstract problems could not be traced to anyone.
- **`GapPanel` answers those four cards and is NOT a second journey diagram.** The steps section is what a user *does*, in order. The panel is what each audience *gets*. That boundary is the reason the page does not end up with two navy zig-zags that look interchangeable — if the panel ever starts listing steps, one of the two should be deleted rather than both kept.
**The active-pill rule that matters:** ties go to the LAST section in document order, and the observation root is a thin strip under the header rather than the viewport. The first attempt used the whole viewport and the earliest match, and the pill sat a full section behind on every click — because `scroll-mt-20` parks the arriving section *below* the strip while the previous section's bottom edge is still inside it. Both intersect; taking the earlier one is always wrong.
**Rejected:** seven links against three sections (a link that scrolls nowhere is a broken page); inventing metrics or partner logos to match the reference pixel-for-pixel (fabrication, and this page's trust section is built on not doing that); a scroll listener instead of an observer (same result, more work per frame); `findLast` (ES2023, outside this project's `lib`).

## D-039 — The landing header carries a language placeholder that is not a control, and its own CTA label
**Decision:** The public header shows a globe + "English" affordance matching the supplied reference design, rendered as a **`<span>`** — visually identical, but not focusable, not announced as a button, and wired to nothing. Its primary action also reads **"ابدأ الآن"** rather than the auth pages' "إنشاء حساب".
**Why the placeholder exists at all:** the user asked for it after being shown the conflict with D-024 (Arabic/RTL only, no locale switcher) and the three alternatives — build real English, translate only the landing page, or omit it — and chose to show it now without function. That is their call to make; this entry records that it was made knowingly, not overlooked.
**Why it is a span and not a disabled button:** "visual only" still has an accessible shape, and the two options are not equally honest. A `<button>` — disabled or inert — occupies a tab stop and is announced as an action, so a keyboard user pays for it and a screen-reader user is told a language switch exists when none does. A span costs neither and looks the same. The rule the codebase should keep is: *an element is a control when it does something*. Making this real means adding an `onClick` and a full `en.json`, in that order — and the landing test asserts the current state so the button cannot appear without the behaviour.
**Why the CTA label diverges from the auth pages:** D-037's reuse rule exists so the header and the form never disagree about *what an action does*. "ابدأ الآن" and "إنشاء حساب" do not disagree — both go to `/register`; one names the journey, the other the form. On a marketing header the journey is the better label, and this is the only place that exception applies.
**Nav links stay at three.** The reference shows seven; this page has three sections. §3 forbids a link that leads nowhere, and the user chose the three real anchors over inventing sections to fill the row.
**Owed:** if the ministry wants English, this placeholder is the first thing to either implement or delete — it should not survive as decoration indefinitely.
**Rejected:** a disabled or inert `<button>` (buys the same pixels with a false affordance); omitting it (the user was asked and chose otherwise); a toggle that switches only the landing page (one click and the visitor is back in Arabic, which is worse than no toggle).

## D-038 — The landing hero is an illustration, and three decorative tints exist outside the brand palette to draw it
**Decision:** The hero at `/landing` is a full-bleed illustrated scene — a graded sky, a white cloud bank, a frond and cream dunes — rendered as one inline `HeroBackdrop` SVG, with the hero's copy set **start-aligned** against it rather than centred. Drawing it required three tints the seven brand colours cannot produce (`--color-sky-pale`, `--color-sky`, `--color-sky-deep`); they are declared in `globals.css` alongside the palette but are **decorative-only** — never a text, button, or UI-surface colour.
**Why new tokens at all:** the brand seven are flat and high-contrast by design (§3), which is right for cards and navigation and useless for atmosphere. Mixing a sky out of navy or muted blue yields grey, not sky. The alternative — hardcoding hexes inside the component — is exactly what the palette comment forbids, and would put the values out of reach of the contrast test. Declaring them as tokens keeps globals.css the single source of truth and, more importantly, makes them *testable*.
**Why the accessibility constraint has a particular shape:** an illustrated background means any band can end up behind any word once the layout reflows, so per-region reasoning is not a guarantee. The invariant instead is: (a) only `sky-pale` and `sky` are painted across the full width, and they are capped light enough that even the **gold headline** clears the 3:1 large-text threshold — this is the binding limit, and it is why the sky cannot simply be made bluer; (b) `sky-deep` is darker than gold can sit on, so it appears only in shapes on the far side of the hero from the text column; (c) hero text is navy / navy-soft / large gold only, never `--color-muted`, which fails on `sky-deep`. All three are asserted in `src/lib/contrast.test.ts`, including the deliberate *failures* that document (b) and (c), in the same style as D-025's gold restrictions.
**Two consequences worth knowing before changing this:**
- **The artwork is authored mirrored.** Cloud mass and frond sit on the *left* because the text column reads from the *right* (D-024, RTL only). This is the same composition as the LTR reference, mirrored — not a different one.
- **Arabic gets no letterspaced eyebrow.** The reference's small-caps tracked label has no Arabic equivalent: the script is cursive, so tracking pulls joined letters apart, and there is no uppercase. The eyebrow is a short gold rule plus a navy-soft label instead — which also keeps gold in a non-text role at a size where it could not carry text.
**Rejected:** deriving the tints with `color-mix()` from muted blue (produces grey, and an unparseable value the contrast test cannot assert on); hardcoding hexes in the component (unreviewable, untestable); keeping the sky pale enough for `--color-muted` body text (would have forced an even weaker sky than the gold cap already forces, for no gain once the text colour changed); a raster image (a background nobody can recolour, plus a network request on the first paint of the only page an unauthenticated visitor sees).

## D-037 — Frontend shape: a `(portal)` route group, one session load, and no query library
**Decision:** Authenticated pages live under `apps/web/src/app/(portal)/`, whose layout renders `PortalProvider`. That provider loads `authApi.me()` and `dashboardApi.get()` **once**, exposes both through context, and owns the redirect to `/login` on a 401. Data fetching is a ~110-line in-house `useApiQuery`/`useApiMutation` pair shaped to feed the existing `DataView`, not TanStack Query.
**Why the single load:** the navigation itself depends on journey state — §4.2 hides My Path until a path exists — so a page that fetched its own copy would render a nav disagreeing with its own content for a frame. Centralising the 401 matters for the same reason a global guard does on the API: with per-page handling, every page repeats three lines and one is eventually missed, leaving a signed-out user staring at a permanent error state instead of the sign-in form. Sign-in and the password pages sit *outside* the group, so they never pay for the session lookup and cannot be caught by a redirect from `/login` to `/login`.
**Why no query library:** what §2B actually requires is that every data view has loading, error and empty states, and `DataView` already enforces that by construction; the missing piece was a hook whose return value plugs into it. Caching, background refetching and invalidation are capabilities Phase 1 has no use for, and an unused dependency in a government system is one more thing to review, patch and justify at every audit. The hook does handle the two things that cause real bugs — a stale response overwriting a newer one, and a resolved promise setting state on an unmounted component. Swapping in TanStack Query later is a change behind this signature.
**Two related choices:**
- **Certificates and CV are absent from the navigation entirely** until Phase 3 builds them, rather than appearing disabled or linking to a placeholder. A nav item that leads nowhere advertises something the product cannot do and costs the user a click to discover it. Profile *is* built (read-only) precisely because §4.2 puts it in the pre-assessment nav, so that link must lead somewhere real.
- **The confirmation gate uses the native `<dialog>`.** `showModal()` supplies focus trapping, the inert background, Escape-to-close and `aria-modal` from the platform; hand-rolled overlays routinely get one of those wrong, and this is the one dialog a user must genuinely understand before agreeing. jsdom does not implement `showModal`, so `vitest.setup.ts` shims the missing method — explicitly a stand-in for the API, not for the behaviour, which the Playwright suite exercises for real in Chromium.
**Rejected:** protecting pages individually (the forgotten-guard problem, in the browser this time); a middleware redirect (the session cookie belongs to the API origin, so the check would have to be duplicated server-side); TanStack Query (unused capability, real supply-chain cost); a div-based modal (trades a genuine accessibility property for a more convenient test).

## D-036 — LMS identity and enrolment in Phase 1: lazy provisioning, best-effort enrolment, read-only progress
**Decision:** Confirming a path calls `LmsPort.provisionUser()` if `users.moodle_user_id` is null, stores the returned id, then enrols each chosen course — **all through the port**, and **all best-effort after the commitment is already recorded**. My Path *reads* live progress via `listProgressForUser()` and overlays it on the stored status without writing it back.
**Why provisioning happens here, though Phase 2 nominally owns it:** without an LMS user there is no enrolment, and without enrolment the mock can report no progress at all — so Phase 1's "My Path statuses fed by the mock" would be unreachable. Doing it at the first moment an account is genuinely needed, through the port's contractually-idempotent `provisionUser`, means Phase 2 changes the implementation and nothing else. This is a scope call, recorded so it is not mistaken for scope creep.
**Why enrolment must not fail the request:** the commitment is irreversible and already written to our database, which is the source of truth for it. Rejecting the request because the LMS was unreachable would tell the user their irreversible decision did not take, when it did. Failures are logged and audited as `PATH_ENROLMENT_REQUESTED / FAILURE`, and Phase 2's sync job is where reconciliation belongs. The trade is explicit: a confirmed path can exist without its LMS enrolments until sync catches up.
**Why the progress overlay is not persisted:** writing completions is the Phase 2 sync job's responsibility. Having a read path also write the same rows would put two writers on them, which is a race waiting for a deadline.
**Revision to D-030's mock:** `MockLmsService` numbered users from a per-process counter. The end-to-end run exposed the consequence — after an API restart the counter began again at 5001 and handed a *new* user an id an existing `users` row already held, so enrolment died on the unique index that exists precisely to stop two people sharing one LMS account. Ids are now derived from the email (FNV-1a), reproducing the invariant a real Moodle has: an account keeps its id forever. The contract suite gained a case asserting the same email yields the same id across two instances, so the real Phase 2 adapter is held to it too.
**Rejected:** deferring provisioning to Phase 2 (leaves Phase 1's run view untestable); failing the confirm on an LMS error (misreports an irreversible decision); persisting the overlay now (two writers); handling the unique-constraint violation by ignoring it (hides a genuine integrity problem instead of fixing its cause).

## D-035 — Phase 1 schema: constraints carry the product rules
**Decision:** Four schema choices encode rules rather than merely storing data.
1. **`user_paths.user_id` is `@unique`.** "One path per user" (D-002) is a database constraint, not an application convention. An application-level check loses the race between two concurrent confirm requests; a unique index does not. The confirm transaction additionally guards on `confirmedAt IS NULL` in the `UPDATE … WHERE`, so a second concurrent confirm matches zero rows rather than overwriting the first one's timestamp.
2. **Option weights are a table with a `RiasecDimension` enum column, not JSON on the option.** A mistyped letter inside a JSON blob contributes nothing and fails *silently*, producing a subtly wrong Holland Code that no error surfaces. An enum column makes the database reject it, and Phase 5's weighting editor gets referential integrity without anyone writing validation for it.
3. **`assessment_responses` references the bank with `onDelete: Restrict`.** Editing a question in Phase 5 must not silently delete the answers people already gave and change historical results. (The result → responses relation stays `Cascade`: removing an attempt as a whole is coherent.)
4. **`assessment_results` stores all six scores as columns plus `maxScore`.** §3A requires all six; columns rather than JSON keeps them typed and queryable for Phase 5's dashboards, and carrying `maxScore` means a historical result can still be rendered as a percentage after the bank changes size.
**Also decided:** **course objectives and prerequisites are our product metadata, not the LMS's.** Moodle has no first-class field for either, so adding them to `LmsPort` would make the Phase 2 adapter responsible for data Moodle does not hold — it would have to parse them out of a summary and would get it wrong. They are seeded now and become editable by entities in Phase 4. The LMS's `visible` flag maps to our `courses.status`: not visible → `HIDDEN_BUT_COMPLETABLE`, which is D-015's "leaves the catalogue for new selections, stays completable for those enrolled".
**Also:** the API `tsconfig` now includes `prisma/`, so the seed script is typechecked — it builds the entire catalogue and question bank, and an untyped seed for a government system is a real gap. `tsconfig.build.json` excludes it again so the emitted layout stays `dist/main.js`.
**Rejected:** enforcing single-path in application code only (loses the concurrency race); JSON weights (silent failure); `Cascade` from the bank to responses (rewrites history); a `passed` column on `user_path_courses` (freezes a policy decision that D-007 makes a setting).

## D-034 — The RIASEC rules live in `packages/types`; the tally does not
**Decision:** Ranking, tie-breaking, Holland Code derivation and the gold recommendation sort (`rankDimensions`, `buildRiasecProfile`, `rankPathsByRecommendation`) live in `packages/types`, shared by both apps. The **tally** — turning chosen options into points — lives server-side in `apps/api/src/assessment/scoring.ts`, and **no view type in the API contract carries a dimension weighting**.
**Why the rules are shared:** the API is authoritative and computes the profile, but the web app sorts and highlights path cards. If "gold" meant something subtly different on each side, the recommendation a user *sees* would not be the one the system *recorded*. One implementation removes that failure mode, exactly as `format.ts` does for D-018. For the same reason the API sorts with the shared function rather than an `ORDER BY`: sorting in SQL would put §3A's rule in two places, in TypeScript and in a query.
**Why the tally is not shared:** it needs the option weights, and an assessment whose scoring key is visible in a network response is one a user can steer toward whichever result they already wanted — which would make every downstream recommendation theatre. `getActive` selects questions and options without their weights, and an integration test greps the whole response for `weight`, `dimension`, `points` and `riasec`. The e2e suite has to read the weights *out of the database* to produce a chosen code, which is the property made visible.
**Also decided:** the single context-dependent course action (§3, §4.7) is computed by a pure server-side function returning **exactly one** value. "Never all three" is then enforced by the shape of the response rather than trusted to each screen. A sixth value, `IN_PATH`, was added for a course already selected but not yet confirmed — "start" would be a button that cannot do what it says, because nothing is enrolled before the commitment gate. §4.9's quiet add means the selection may **grow** after commitment but never shrink; letting courses leave a confirmed path would be switching by instalments.
**Rejected:** computing the recommendation only on the server and shipping a pre-sorted list with no shared vocabulary (works until the web needs to re-sort or re-explain, then diverges); exposing weights to let the client show a live score (destroys the instrument); returning a list of permitted actions (invites a screen to render two).

## D-033 — Retakes append; a result is never overwritten
**Decision:** Each completed attempt inserts a new `assessment_results` row with its own responses. "The user's result" is the newest row by `completedAt`. Nothing is updated in place, and nothing is deleted.
**Why:** a career recommendation is a record of what the system told someone and when. Overwriting it would make the earlier advice unreconstructable, which matters both for explaining a decision months later and for any audit of how a path came to be chosen. It also keeps the retake rule honest: D-015 permits retaking only before commitment, and history makes it visible whether that was respected.
**Cost:** the table grows with retakes. Bounded in practice — retakes stop at commitment — and the Phase 6 retention pass owns anything further.
**Rejected:** updating the existing row (loses history for no real saving); soft-deleting superseded results (a second state to keep correct, for the same outcome).

## D-032 — The question bank: thirty Likert items, weighted 0-4, balanced by construction
**Decision:** The assessment is **30 five-point Likert statements, five per dimension**, seeded as data in `apps/api/src/seed-data/assessment.ts` and read from the database at runtime. Agreement levels weigh **0-4**, and the bank must be **balanced** — every dimension attaining exactly 20 — with `isBalancedBank` asserting it in CI.
**Why balance is not a nicety:** ranking compares **raw scores across dimensions**. If one dimension had more items than another it would rank higher on volume rather than on the user's interests, and the resulting Holland Code would be an artefact of how the bank happened to be authored. The test exists so that a Phase 5 edit which unbalances the bank fails loudly and forces a deliberate decision (either rebalance, or switch ranking to normalised percentages) rather than silently skewing every result.
**Why 0-4 rather than 1-5:** on a 1-5 scale a user who rejected every Realistic item would still accumulate Realistic points purely for having answered, so the floor would track the number of items rather than any interest.
**Why items are interleaved (R,I,A,S,E,C,R,…):** five consecutive statements on one dimension read as a labelled section, and a user who has decided how they wish to be categorised can answer the block uniformly. A test asserts no two consecutive items share a dimension.
**Why it is seeded data:** Phase 5 must be able to edit questions and weightings without a deployment, and the ministry must be able to revise the Arabic wording without touching a component. Question keys are stable, so revising wording does not orphan stored responses. The content sits under `src/` rather than beside `prisma/seed.ts` so it is typechecked and reachable by the test runner — the balance property must fail CI, not be noticed later.
**Status of the wording:** the Arabic text is a reviewed first draft and is expected to change; the asserted *properties* are not.
**Rejected:** scenario-style multiple choice (more engaging, but more authoring and more tie-prone; the schema still supports it, since options carry weights across one or more dimensions); hardcoding questions in components (defeats Phase 5); grouping items by dimension (invites block answering).

## D-031 — Ties break on canonical R-I-A-S-E-C order
**Decision:** When two dimensions score equally, they are ordered by the canonical Holland hexagon order R, I, A, S, E, C. The ordering is therefore **total**: ranks are 1-6 with no shared or skipped positions, and the Holland Code always has exactly three letters.
**Why:** CLAUDE.md §3A does not specify a tie rule, and ties are common — six dimensions over thirty items produce them routinely. Left to `Array.sort`'s handling of equal elements, a user's code would depend on the order rows came back from the database, so **the same answers could yield a different career recommendation on a different day**. A recommendation that is not reproducible is not defensible, which matters more here than in most products. Canonical order is the conventional presentation of the framework, so it is at least a principled arbitrary choice rather than an accidental one.
**Consequence worth knowing:** a user who answers every item identically gets `RIA`. That is correct behaviour — no dimension was preferred — and the e2e suite asserts it precisely because it is the case that would otherwise be nondeterministic.
**Rejected:** leaving ties to sort stability (nondeterministic across drivers and query plans); breaking ties randomly (irreproducible by construction); returning a shorter code on a tie (downstream recommendation logic assumes three letters); asking the user to break the tie (a question about an artefact of scoring, not about them).

## D-030 — The LMS boundary is a port in *our* vocabulary, with the contract expressed as an executable test suite
**Decision:** All LMS access goes through one interface, `LmsPort` (`apps/api/src/moodle/lms.port.ts`), injected by the DI token `LMS_PORT`. Three things make it a real anti-corruption layer rather than a proxy:
1. **The types are ours.** `LmsCourse`, `LmsCourseProgress`, `LmsUserRef` — nothing mirrors a Moodle payload. No `fullname`, no `completionstatus`, no `enrolledusercount`. Translating Moodle's shapes is the Phase 2 adapter's job, confined to `real/moodle-http.service.ts`. A contract test asserts Moodle's native field names never appear on a returned object, so a leak fails CI rather than quietly coupling every caller to Moodle's schema.
2. **The contract is executable, not just an interface.** `lms.contract.ts` exports `describeLmsContract(name, factory)` — a suite asserting the *behaviours* callers depend on: `provisionUser` and `enrol` are idempotent, an unenrolled user yields `null` (not an empty object), an enrolled-but-unattempted course reports a **null** grade rather than 0, `listCourses` returns copies rather than shared mutable state, and `courseUrl` embeds no token. A shared interface only proves method names line up; these are what actually break when an implementation is swapped. Phase 2 runs the same suite against the real adapter — if it passes, no caller changes.
3. **No product logic crosses the boundary.** `LmsCourseProgress` carries `gradePercent` and deliberately has **no `passed` field**; a contract test asserts its absence. The pass threshold is a product setting (D-007), so if the LMS decided pass/fail, changing certification policy would mean editing Moodle quizzes.
**Two supporting choices:**
- **`MOODLE_MODE=real` fails loudly.** The Phase 2 adapter exists now, declared `implements LmsPort`, with every data method throwing `NotImplementedException`. Two benefits: the compiler breaks it the moment the port gains a method, so the interface cannot drift ahead of the real adapter unnoticed; and flipping config early produces an explicit refusal rather than an integration that appears to work while reporting every course as empty. `checkHealth()` is the one exception — it reports `reachable: false`, because a health endpoint exists to report bad states, not to crash a dashboard.
- **Mock-only helpers stay off the port.** `simulateCompletion`, `simulateAttempt` and `reset` live on `MockLmsService`, never on `LmsPort` — a real Moodle adapter could not implement them, so putting them on the interface would break the swap. The contract suite touches only port methods.
**Verified:** 40 tests across the contract and wiring suites; `/api/health` reaches the mock through `LMS_PORT` and reports `{"lms":"up","lmsSiteName":"Tamkeen Mock LMS"}`; `MOODLE_MODE=real` boots, reports `"lms":"down"` and throws `Phase 2` on any data call; `MOODLE_MODE=real` without a base URL refuses to boot at all. A wiring test resolves the *same* consumer class under both modes, which is the Checkpoint F claim made checkable.
**Also fixed while here:** `MoodleModule` now imports `AppConfigModule` explicitly instead of relying on its `@Global` registration. Implicit reliance on globalness means a module cannot be compiled in isolation, which turns a unit test into a whole-application boot.
**Rejected:** exposing Moodle's REST shapes directly (couples every caller to the LMS; an LMS change would touch the whole codebase); a port named after Moodle (invites callers to assume Moodle-specific behaviour); returning `passed: boolean` (moves certification policy into the LMS); leaving the real adapter unwritten until Phase 2 (nothing would keep the interface and the future implementation in step); mock methods on the port (makes the swap impossible).

## D-029 — Configuration is read from a validated object, never from `process.env` (security defect fixed)
**Decision:** `@nestjs/config` was removed. `AppConfigService` now holds the object returned by the zod validator and reads directly from it.
**Why — this was a live authentication bypass, not a style preference.** `ConfigService.get()` consults `process.env` *in preference to* the object returned by `validate`, so every setting arrived as the raw environment string rather than its parsed type. The consequences, in order of severity:
1. **`ALLOWED_EMAIL_DOMAINS` came back as the string `"ministry.gov.example"` instead of `["ministry.gov.example"]`.** The registration gate then called `.includes(domain)` on a *string*, which is substring matching — so **`attacker@ministry.gov` would have satisfied a gate configured for `ministry.gov.example`**, and self-registration was open to any domain that happened to be a substring of an allowed one. This defeats D-017, the rule that keeps the system from being an open sign-up.
2. `RATE_LIMIT_ENABLED=false` came back as the string `"false"`, which is truthy — a boolean switch that silently did nothing.
3. Numeric settings came back as strings, so arithmetic on them would concatenate rather than add.
**How it surfaced:** the integration tests could not disable rate limiting and kept returning 429. Chasing *that* symptom is what exposed the type problem underneath. The domain bypass had no failing test of its own — the existing domain test used `gmail.com`, which fails a substring check too, so it passed for the wrong reason. It is worth noting plainly that a green test suite did not catch this.
**Guards added:** `app-config.spec.ts` asserts the *types* coming out of configuration (arrays are arrays, numbers are numbers, `"false"` is `false`), and `registration-policy.spec.ts` gained explicit tests that a domain which is merely a **prefix** or **substring** of an allowed one is rejected.
**Rejected:** keeping `@nestjs/config` with `skipProcessEnv` (relies on remembering an opt-out flag whose absence is silently insecure); casting at each call site (spreads the problem instead of removing it).

## D-028 — Opaque server-side sessions in Postgres; in-process rate limiting for now
**Decision:** Authentication uses **opaque 256-bit random session tokens stored as SHA-256 hashes in a `sessions` table**, delivered in an `httpOnly; SameSite=Strict; Secure` cookie. Not JWTs. Per-account brute-force lockout lives in the database; per-IP rate limiting is `@nestjs/throttler` with **in-process** storage. CSRF is a double-submit cookie/header pair on top of `SameSite=Strict`.
**Why opaque, not JWT:** revocation. A stateless token stays valid until it expires, so suspending an account or signing out cannot take effect immediately. Here both do — an integration test suspends an account and the very next request is rejected. For a government system where "disable this employee's access now" is a real operational requirement, that is worth a database lookup per request.
**Why Postgres, not Redis:** signing in should not depend on a second datastore being healthy. Redis remains in the stack for BullMQ (Phase 2). Keeping sessions in Postgres also lets Phase 5 show an administrator the active sessions on an account, which an opaque Redis key cannot.
**Why only the hash is stored:** the same reasoning as `auth_tokens` — a database dump must not yield presentable sessions. SHA-256 rather than argon2 because these are CSPRNG tokens with no guessable structure; a slow hash protects nothing here and would add latency to every request.
**Rate limiting — the honest limitation:** in-process storage is correct for a single API instance, which is the Phase 0 target, but **counters are per-instance, so horizontal scaling multiplies the effective limit**. Phase 7 must swap in a shared store when it decides the deployment topology. Per-account lockout is unaffected by instance count, and it is the protection that matters against a targeted attack; per-IP throttling mainly blunts broad spraying. `RATE_LIMIT_ENABLED` exists so integration tests can make hundreds of requests, and `validateEnv` **refuses to start with it disabled in production** — a switch that could be flipped in production would defeat the point.
**Also decided:** no `JWT_SECRET` or `SESSION_SECRET` in configuration. There is nothing to sign, and dead config invites someone to "use" it later in a way nobody designed.
**Rejected:** JWTs (no immediate revocation); Redis sessions (extra hard dependency in the sign-in path); signing the session cookie (a 256-bit random value already cannot be forged); relying on `SameSite` alone for CSRF (leaves older browsers and a compromised same-site subdomain uncovered).

## D-027 — RBAC is role-based and code-defined, not a database permission table
**Decision:** Authorization is driven by the `UserRole` enum on `users` (`EMPLOYEE` / `ENTITY` / `SUPER_ADMIN`) plus guards in code. There is **no `permissions` table and no role–permission join table.**
**Why:** The system has exactly three fixed portals, and §6 describes roles, not a configurable permission matrix. Putting permissions in the database implies they are editable at runtime, which creates a privilege-escalation surface — anyone with a single UPDATE on that table becomes a super-admin, and the change leaves no trace in code review. Code-defined roles are versioned in git, reviewable in a PR, and diffable during a security audit, which is what a government system needs. A DB-backed permission matrix is the right answer when customers define their own roles; nobody here does.
**Also considered and deferred:** inventing a fine-grained permission taxonomy now (`assessment:take`, `admin:manage-paths`, …). Rejected as speculation: those strings would describe features that do not exist yet, and Phase 4/5 are the phases that will actually know what an entity or admin may do. Introducing a permission layer later is a contained change *behind the guard*, whereas a wrong taxonomy baked in now would spread through every controller.
**Consequence:** Phase 4 must add entity *scoping* (which courses/learners an entity may see). That is data-scoped filtering, not a new role, and belongs with the entity model in Phase 4. A test asserts the Prisma `UserRole` enum and `USER_ROLES` in `@tamkeen/types` never diverge, since a silent mismatch would make RBAC checks stop matching without failing loudly.

## D-026 — Prisma 7 with the pg driver adapter (schema no longer holds the URL)
**Decision:** Adopt **Prisma 7** rather than pinning Prisma 6. Prisma 7 removed `url` from the `datasource` block, so the connection is configured in two places by design: `apps/api/prisma.config.ts` for CLI/migration commands, and the **`@prisma/adapter-pg` driver adapter** passed to `PrismaClient` for the runtime. The generated client is emitted to `apps/api/generated/prisma` (gitignored) and regenerated by a `postinstall` hook.
**Why:** Prisma 7 is the current major. Starting a system intended to run for years on an already-superseded major buys short-term familiarity and pays for it with an earlier end-of-support and a migration later, during hardening or after launch — exactly when a government system should not be taking framework upgrades. The adapter change is contained: one config file and one constructor.
**Details worth knowing:**
- Prisma 7 also stopped auto-loading `.env`, so `prisma.config.ts` loads the root `.env` explicitly, matching the `envFilePath` the Nest config module uses.
- The datasource URL deliberately does **not** use Prisma's `env()` helper, which throws when the variable is absent. `prisma generate` needs no database and runs on postinstall, so a fresh clone with no `.env` must still install. The fallback is the literal string `postgresql://DATABASE_URL-is-not-set`, so if a command that genuinely needs the database runs unconfigured, the connection error names the missing variable rather than being cryptic.
- CI generates the client and applies migrations before typecheck, because the client is generated rather than committed.
- `npm ls` style caveat: ESLint had to be told to ignore `generated/**` — the machine-written client is not ours to lint.
**Rejected:** Prisma 6 (familiar `url = env(...)`, no adapter, but a shorter support horizon for a long-lived system); committing the generated client (bloats diffs and goes stale against the schema); Prisma Accelerate (a managed proxy is inappropriate for an internal ministry deployment).

## D-025 — Gold cannot carry body text at AA; two functional colours added
**Decision:** Measured contrast forced two adjustments to how the §3 palette is applied. Neither changes a brand value; both constrain or extend usage.
**(a) Gold is a non-text and large-text colour only.** `--color-gold` `#A8863C` measures **3.42:1 on white, 3.08:1 on cream, 3.99:1 on navy** — all below the 4.5:1 AA floor for body text (WCAG 1.4.3). Worse, a *gold fill* fails in both directions: white-on-gold is 3.42:1 and navy-on-gold 3.99:1, so there is no legible body-size label for a solid gold button. Gold is therefore restricted to **borders, focus rings, icons, accent edges, and large/bold text**, where the 3:1 threshold (WCAG 1.4.11) applies and it passes. Where a gold *fill* is needed behind body text — the achievement button, and the "موصى به" recommended badge in Phase 1 — the fill is **`--color-gold-light` `#C9A85C` with navy text, which measures 6.01:1** and passes comfortably.
This turns out to reinforce §3's own instruction rather than fight it: gold was always meant to be scarce and signal-carrying. A palette that physically cannot support gold as a body-text colour is a palette that keeps gold meaning "recommended".
**(b) Two functional status colours added, outside the brand palette:** `--color-danger` `#A32015` and `--color-success` `#1E6F4E`. §2B DoD 4 makes error states mandatory on every data view, and the brand seven contain no signal colour — an error rendered in navy is not an error. Both clear 4.5:1 in *either* direction on white and cream (danger 7.57/6.82, success 6.11/5.51). They are declared in a separate, commented block in `globals.css` so they cannot be mistaken for brand accents and so gold stays scarce.
**Why enforce it in tests:** `src/lib/contrast.test.ts` computes every pairing the design system uses and asserts its required ratio — 24 assertions, including deliberate *negative* tests proving gold body text fails, which document why the restriction exists. WCAG 2.1 AA is a government obligation; "the gold looks fine" is exactly the judgement that fails an audit. A test also means a future palette tweak that breaks AA fails CI instead of shipping. `src/lib/tokens.ts` mirrors the palette for the tests and a test asserts the mirror matches `globals.css`, so the two cannot drift.
**Rejected:** darkening `#A8863C` until it passes for text (changes a locked brand value — not mine to make); using gold body text anyway and accepting the AA failure (a government accessibility obligation is not optional); reusing navy for errors (removes the distinction between "failed" and "normal"); pulling in a full third-party palette for status colours (two values are enough, and more colour weakens gold's signal).

## D-024 — next-intl without locale routing; one formatting layer shared by both apps
**Decision:** `next-intl` is configured **without i18n routing** — no `/ar` URL prefix, no `[locale]` route segment, no middleware. Arabic is the sole locale; `<html lang="ar" dir="rtl">` is fixed, not negotiated. All UI copy lives in `apps/web/messages/ar.json`; no user-visible string is hardcoded in a component, including the document title.
The locale handed to next-intl is the **extended** tag from `formatLocaleTag()` (e.g. `ar-u-nu-latn-ca-gregory`), not bare `ar`, because next-intl passes it straight to `Intl` — so numbers and dates inside ICU messages honour the D-018 digit/calendar switch automatically. The bare `ar` is used for `<html lang>` via `HTML_LANG`, since an extension subtag there would be invalid HTML.
Client components reach the same formatters through `FormatProvider` / `useFormat()`, seeded from the server-resolved context. This exists because `NUMBER_FORMAT` is a server-only variable: without it, client components would have no access to the setting and would drift into calling `Intl` directly — the exact fragmentation D-018 forbids.
**Why no locale routing:** adding `/ar` to every URL of a single-language internal system is permanent noise for a hypothetical future. `next-intl` supports both modes, and the migration path is understood: introducing English means adding a `[locale]` segment and middleware, which is a contained change to routing, not to the message catalogs or the formatting layer.
**Verified:** the same page, rebuilt with only environment variables changed and **zero code edits**, renders `1,248 / 85% / 17 أغسطس 2026` under the defaults and `١٬٢٤٨ / ٨٥٪ / ٤ ربيع الأول ١٤٤٨ هـ` under `NUMBER_FORMAT=arabic-indic DATE_CALENDAR=islamic-umalqura`. A catalog test additionally fails the build on any empty string, unbalanced ICU braces, or stray English copy, so the Arabic-first rule is enforced mechanically rather than by review discipline.
**Caveat:** for statically prerendered pages the setting is baked in at build time, so flipping it on an existing deployment requires a rebuild. Acceptable — it is a one-time deployment choice, and the authenticated pages that dominate this product render per request.
**Rejected:** locale-prefixed routing now (URL noise, no current benefit); letting next-intl own number/date formatting while `packages/types` owns it for the API (two implementations would drift, and a certificate PDF disagreeing with the screen that announced it is a real failure mode); reading `process.env` directly in components (defeats the single switch point).

## D-023 — Self-host the Arabic typeface instead of fetching it from Google Fonts
**Decision:** IBM Plex Sans Arabic is committed to `apps/web/src/fonts` as four "complete" woff2 files (400/500/600/700, ~74 KB each) and loaded with `next/font/local`. `next/font/google` is not used. The OFL 1.1 licence text ships alongside the fonts, since the repo now redistributes them.
**Why:** Three reasons, in order of weight. (1) **Build reliability** — `next/font/google` fetches at build time; the first build here retried the fetch five times before succeeding, and a ministry environment behind a proxy or air-gapped would fail outright. A production build must not depend on reaching a third party. (2) **Privacy** — a Google-hosted font means every employee's browser makes a request to Google carrying its IP and user agent on every visit to an internal government system. That is a needless third-party disclosure of who is using the platform and when, and it is exactly the kind of thing §2's PII-minimisation stance exists to prevent. (3) **Correctness** — the "complete" files cover Arabic glyphs *and* Latin digits in one file per weight, so the Western Arabic numerals that D-018 makes the default render in the same typeface as the Arabic text instead of falling back to a system font. Google's API splits by subset, which cannot express that cleanly through `next/font/local`.
**Verified:** production build succeeds with no network retries; the served page references `/_next/static/media/*.woff2` and contains **no `fonts.googleapis.com` or `fonts.gstatic.com`** reference at all.
**Cost:** ~298 KB of binary in the repo, and the fonts must be refreshed manually if IBM ships an update — a deliberate trade for a build that cannot fail on someone else's uptime.
**Rejected:** `next/font/google` (build-time network dependency + third-party disclosure); depending on the `@ibm/plex-sans-arabic` npm package and pointing `next/font/local` into `node_modules` (avoids committing binaries, but the path is fragile under workspace hoisting); hand-written `@font-face` rules with `unicode-range` (more control, but loses `next/font`'s automatic preloading and layout-shift compensation).

## D-022 — Clear transitive CVEs with npm `overrides` rather than moving off the locked Next.js 15
**Decision:** The first install carried **3 high-severity transitive advisories** through Next 15.5.23 — four `postcss` issues (XSS via unescaped `</style>` in stringify output; arbitrary `.map` file read via attacker-controlled `sourceMappingURL`) and the `sharp`/libvips set (CVE-2026-33327/33328/35590/35591). `npm audit fix --force` resolves them only by installing **Next 16**, which is a breaking change and contradicts D-013. Instead, root `overrides` pin `postcss@^8.5.26` and `sharp@^0.35.3` for the whole tree, including inside `next` (which pins `postcss` exactly at `8.4.31` and `sharp` at `^0.34.3`). Result: **`npm audit` reports 0 vulnerabilities** and Next 15.5.23 still builds, serves, and passes tests.
**Why:** A government system should not begin Phase 0 with known highs baked into its lockfile, and it should not silently defer them to Phase 6 either. Overriding a patch/minor within the same major is low-risk (stable public APIs), and it was verified end-to-end rather than assumed: full production build, the Tailwind v4 CSS pipeline still emitting the brand tokens to the served stylesheet, both apps booting, all tests green. `npm ls` labels the overridden packages `invalid` because they fall outside Next's declared ranges — that is the expected, cosmetic signal of a deliberate override, not a broken tree.
**Why not just accept them:** real exposure here is genuinely low (the postcss issues need attacker-controlled CSS at build time, and ours is repo-authored; the sharp issues need attacker-supplied images through `next/image`). But "low exposure" is an argument for not panicking, not for shipping a red audit — and the override cost nothing.
**Consequence / revisit:** overrides are a standing maintenance obligation — each Next upgrade must re-check that the pins are still needed and still compatible. Phase 6's dependency review owns that check, and should also decide whether to drop the `sharp` pin by disabling `next/image` optimisation entirely (the app has no need to process untrusted images).
**Rejected:** Next 16 now (breaks the locked stack mid-Phase-0, and 15.x is the version the rest of the plan assumes); accepting 3 highs and deferring to Phase 6 (leaves the baseline red for six phases); `npm audit fix --force` (same as adopting Next 16, but without the decision being explicit).

## D-021 — Local dev dependencies run in Docker; Mailpit is the dev mail sink
**Decision:** A root `docker-compose.yml` provides PostgreSQL 16, Redis 7 and **Mailpit** for local development (`npm run db:up` / `db:down`). Development `SMTP_HOST/PORT` point at Mailpit (`localhost:1025`, inbox at `http://localhost:8025`). Postgres/Redis image versions match the CI service containers. This file is a **development convenience only** — real environments, secrets management and deployment topology are Phase 7.
**Why:** No local PostgreSQL was installed (Docker was), so Docker is the lowest-friction path to a working DB and gives dev/CI parity on image versions. Email verification and password reset (0.5) are unusable without somewhere for mail to land; Mailpit makes the verification link readable with **no real SMTP credentials and no risk of mailing a real inbox from a dev box** — which matters because these are ministry-employee addresses.
**Rejected:** Requiring a hand-installed local Postgres (per-machine drift, no CI parity); logging verification links to the console only (works, but hides the actual rendered Arabic email, so RTL email bugs would go unnoticed until late); pointing dev at a real SMTP relay (risks sending mail to real employees during development).

## D-020 — npm workspaces as the monorepo tool
**Decision:** Use **npm workspaces** (`apps/web`, `apps/api`, `packages/types`) rather than pnpm or yarn. `packages/types` is compiled to `dist` and consumed via its `main`/`types` entry points, built by an explicit `build:types` step that runs before typecheck/build.
**Why:** §2A left the workspace tool open ("pnpm/npm/yarn"). npm ships with Node so there is no bootstrap step for a new developer or for CI, and the provided CI workflow already assumed `npm ci`. Compiling the shared package (instead of importing raw source) keeps NestJS's `tsc` build and Next's bundler both working without special-casing, and means the published type surface is exactly what consumers see.
**Rejected:** pnpm (fastest and best at monorepos, but not installed locally and adds an install-pnpm step to CI for no benefit at this repo's size); yarn (same bootstrap cost, no advantage here); a single package with folders (loses the enforced boundary that stops the frontend importing backend internals).

## D-019 — Auth is email/password only (no AD/LDAP); Moodle target = latest 4.5.x LTS
**Decision:** (a) The ministry does not require AD/LDAP integration; the system uses **email/password authentication only** (app is the identity owner, provisioning Moodle accounts behind the scenes). The AD/LDAP hardening path in D-004 is dropped unless the ministry later requests it. (b) Deploy the **latest Moodle 4.5.x LTS** patch (from github.com/moodle/moodle, newest `v4.5.x` tag / download.moodle.org). Requires PHP ≥ 8.1 (8.3 supported), sodium extension, `max_input_vars ≥ 5000`.
**Why:** (a) User confirmed email login is the intended, sole mechanism — removes the biggest Phase 2 auth unknown. (b) 4.5 is the current LTS with security support to 4 Oct 2027; the next LTS (5.3) isn't out yet, so 4.5.x is the stable choice for a government system. General bug-fix support for 4.5.x ended Oct 2025, so always run the newest 4.5 patch for security.
**Rejected:** AD/LDAP/OAuth2 SSO (not wanted); Moodle 5.x non-LTS (shorter support, less stable for gov); pinning an old 4.5.x patch (misses security fixes).

## D-018 — Digits/dates default with a single locale switch
**Decision:** Default to Western Arabic numerals (0-9) and Arabic date presentation (Hijri optional), routed through one locale/formatting layer so Arabic-Indic numerals (٠-٩) can be switched on without touching feature code. Same choice applied to UI, certificates, CV, and all PDFs.
**Why:** Arabic-Indic vs Western digits is a real, visible choice; centralizing it prevents inconsistent mixes across the app and PDFs.
**Rejected:** Hardcoding digits per component (guarantees inconsistency); deferring the choice (RTL/number formatting is painful to retrofit).

## D-017 — Restricted registration (not open public sign-up)
**Decision:** Registration is ministry-scoped by default: admin-provisioned accounts and/or self-registration gated by allowed email domain + valid employee ID. Open public registration is not shipped. A settings toggle allows pure admin-provisioning.
**Why:** Internal government system for ministry employees; open registration would be a security and data-integrity hole.
**Rejected:** Open self-registration (inappropriate for an internal system). *Confirm exact policy with the ministry.*

## D-016 — Certificate verification (ID + QR/public page)
**Decision:** Every certificate has a unique public `verification_id` and a QR/public verification URL that confirms validity (name, course/path, date) without login and without extra PII.
**Why:** Government-issued credentials are commonly verified by third parties; without this the certificates aren't trustworthy artifacts.
**Rejected:** Certificates with no verification (can't be authenticated); exposing full profile on the verification page (unnecessary PII).

## D-015 — Assessment retake locked to pre-commitment; course-edit protection
**Decision:** (a) Users may retake the assessment and get a new Holland Code only before confirming a path; after commitment, both path and result are locked. (b) A course in any user's confirmed path cannot be deleted/unpublished — only hidden from new selections while enrolled users finish; `courses.status` = available / hidden-but-completable / retired.
**Why:** (a) A new code is meaningless once the path is permanent (one-path rule) and inviting retakes post-commitment contradicts it. (b) Prevents pulling content out from under a mid-path learner — an operational hazard left undefined before.
**Rejected:** Unlimited retakes anytime (conflicts with one-path rule); hard-deleting courses (breaks in-progress learners).

## D-014 — Engineering standards & Definition of Done; "the test" defined
**Decision:** Locked §2B: per-task Definition of Done, required testing (unit + integration + at least one e2e happy path per phase; explicit RIASEC scoring tests; mock Moodle must share the real module's contract), mandatory loading/empty/error states, WCAG 2.1 AA, and conventions (branch naming, Conventional Commits, `.env.example`, CI gates). This defines what "the test" in the git/PR rule means.
**Why:** The PR rule referenced "the test" without defining it; an agent needs concrete, uniform quality gates or testing/coverage will be inconsistent. Government context demands accessibility, security, and reliability baselines.
**Rejected:** Leaving testing/quality implicit (inconsistent, unverifiable "done"); UI without mandated states (dead/blank/error-swallowing screens).

## D-013 — Tech stack & architecture
**Decision:**
- **Frontend:** Next.js 15 (React + TypeScript), Tailwind CSS, shadcn/ui, `next-intl` (Arabic-first RTL).
- **Backend:** NestJS (Node.js + TypeScript) as a **dedicated API**, not Next.js route handlers.
- **DB:** PostgreSQL + Prisma ORM.
- **Async/jobs:** Redis + BullMQ (scheduled Moodle completion sync, certificate generation).
- **PDF:** headless-Chromium (Puppeteer) HTML→PDF for Arabic-correct certificates + CVs.
- **Moodle:** v4.5 LTS, Web Services (REST) + Catalyst RESTful plugin; access isolated behind one NestJS "Moodle integration" module (anti-corruption layer). Least-privilege token, stored server-side only.
- **Auth:** app is IdP (email/password, verified); JWT/session for the app; token-mapped Moodle handoff for MVP, OAuth2/AD-LDAP as hardening target.
**Why:** The system is integration-heavy and long-lived with background jobs, RIASEC scoring, certificate generation, three role-based portals, and government-grade audit/security needs. A dedicated opinionated backend (NestJS) keeps that maintainable and scalable far better than packing logic into Next.js handlers (industry consensus: Next.js-only backends accrue refactor debt past ~18 months for team-scale, logic-heavy systems). Shared TypeScript lets front/back share the RIASEC + path types. Postgres/Prisma is the safe system-of-record choice. Chromium-based PDF is the most reliable route to correct Arabic RTL shaping. Moodle 4.5 LTS is supported to late 2027; the RESTful plugin gives real HTTP status codes instead of always-200. Isolating Moodle behind one module means an LMS change touches one place.
**Rejected:** Next.js-only full-stack (logic/jobs/roles outgrow route handlers); Express (less structure than NestJS for a multi-portal system); Django/Laravel (loses shared-TypeScript benefit); non-LTS Moodle (shorter support window); common PDF libs without robust Arabic shaping (RTL/ligature bugs).

## D-012 — Comprehensive 8-phase plan with done-criteria
**Decision:** Expand the phase plan to 0–7, each with goal/deliverables/"done when"; split entity and super-admin into separate phases; add a dedicated deployment + acceptance phase. Project isn't "done" until Phase 7 acceptance passes.
**Why:** User asked for the phases to make the system comprehensive and fully functional. Explicit done-criteria and a deployment/acceptance phase prevent a "features built but not launchable" outcome.
**Rejected:** The earlier 6-phase sketch (bundled admin portals, no explicit deployment/acceptance, no per-phase done-criteria).

## D-011 — Assessment is Holland (RIASEC); paths tagged by letter; gold = letter in top-three code
**Decision:** Use the Holland Codes / RIASEC framework. Scoring tallies points per dimension → ranked profile → top-three **Holland Code**. Every path is tagged with one **primary RIASEC letter**. A path is recommended (gold) if its letter is in the user's top-three code, ranked by the user's letter order. Non-matching paths remain selectable. Store all six dimension scores, not just the code.
**Why:** User specified a Holland-based assessment with each path linked to a Holland category. Top-three code is the standard Holland output and richer than a single letter; storing all six enables ranking and later re-explanation. Matching by "letter ∈ top-three code" preserves the single-path rule while using the real framework and keeps gold meaningful without caging the user.
**Alternatives considered:** Match only the single #1 letter (too narrow — most careers are blends, and few paths would be gold); reduce the result to one opaque letter (loses the framework's value). If stricter/looser matching is wanted later, revise this entry.

## D-010 — Three-file context engineering (CLAUDE.md / progress.md / decisions.md)
**Decision:** Maintain three files: `CLAUDE.md` (rules Claude Code follows), `progress.md` (running state), `decisions.md` (this file, rationale). Every session reads CLAUDE.md → progress.md → decisions.md as needed, and updates progress.md (and decisions.md on any decision) before ending.
**Why:** Survives cleared chats / new sessions. State and rationale persist outside the conversation so a fresh session can continue coherently.
**Rejected:** Relying on chat memory alone (lost on reset); a single README (mixes stable rules with volatile state).

## D-009 — Color system fixed as design tokens
**Decision:** Navy `#222E42`, Secondary Navy `#2E3A50`, Gold `#A8863C`, Cream `#F4F3F1`, White `#FFFFFF`, Light Gold `#C9A85C`, Muted Blue `#5E6B85`. Gold reserved for recommended-path highlight and achievement accents.

**Rejected:** Ad-hoc coloring; heavy gold usage (dilutes the "recommended" signal).

## D-008 — PR-only workflow, never touch main
**Decision:** All work on feature branches; open a PR to `main` only after the user approves the test; never merge or push to `main` directly.
**Why:** Government system — human review gate is essential; protects main.
**Rejected:** Direct commits to main (unsafe, unreviewable).

## D-007 — Pass threshold is a product setting, evaluated against Moodle grade
**Decision:** The "passed well enough for a certificate" threshold lives in our system config and is checked against the grade Moodle returns.
**Why:** Lets us control certification policy without editing Moodle quizzes; keeps product logic in the product.
**Rejected:** Encoding the threshold inside Moodle (splits product logic into the LMS).

## D-006 — Certificates issued by our app, idempotent
**Decision:** Generate certificates as Arabic PDFs from our own templates; check "already issued?" before creating one.
**Why:** Consistent branding/Arabic template control; polling-based sync would otherwise create duplicates.
**Rejected:** Moodle certificate plugin (less control over Arabic template + product coupling); non-idempotent issuance (duplicate certs).

## D-005 — Completion sync via scheduled job (MVP)
**Decision:** Backend polls Moodle completion/grade functions for enrolled users every few minutes; webhooks are a later optimization.
**Why:** Simpler and more reliable to build first; minutes of latency is fine for training.
**Rejected (for now):** Webhooks/events first (more moving parts before the core loop is proven).

## D-004 — MVP auth = token-mapped handoff; SSO/OAuth2 = hardening target
> **Update (D-019):** the AD/LDAP option is dropped — auth is email/password only. OAuth2 remains only an optional internal convenience for the Moodle handoff, not a ministry SSO requirement.
**Decision:** App is the identity owner (email/password). Create a Moodle user per registrant (`moodle_user_id`), use token-mapped auto-login/handoff for course entry in MVP. Move to OAuth2 IdP (or AD/LDAP if the ministry has it) during hardening.
**Why:** Get a working single-login experience fast; defer the heavier SSO build until the flow is proven. AD/LDAP existence must be confirmed early as it reshapes auth.
**Rejected:** Building full OAuth2 SSO up front (slower MVP); two separate logins (bad UX).

## D-003 — One Moodle course, multiple paths; reuse completion
**Decision:** A single Moodle course can belong to several paths. If a user already completed a shared course, reuse that completion — no retake.
**Why:** Avoids duplicate content and pointless repeat work; one source of truth per course.
**Rejected:** Duplicating courses per path (content maintained twice); forcing retakes (frustrating, wasteful).

## D-002 — One path per user, no switching
**Decision:** A user commits to exactly one path; it cannot be switched after confirmation. Confirm is a hard gate with an Arabic confirmation dialog.
**Why:** Simplifies state (effectively one active `user_paths` record), keeps the experience focused. (User instruction, "for now.")
**Rejected:** Multiple concurrent paths / free switching (more complex state, diluted focus). Revisit only if the user later requests it.

## D-001 — Arabic-first is architecture, not styling
**Decision:** RTL layout, Arabic default locale, Arabic-capable PDF rendering set from Phase 0.
**Why:** Retrofitting RTL and Arabic PDF shaping later is painful and error-prone; it's a primary requirement.
**Rejected:** English-first with later Arabic pass (would compromise the core requirement).

## D-000 — App is the experience layer, Moodle is the learning engine
**Decision:** Our app owns users/auth, assessment, paths, path membership, certificates, CV, UX. Moodle owns course content, quizzes, grading, completion. Bridges are only `moodle_user_id` and `moodle_course_id`; completion flows one direction (Moodle → our DB → certificate logic). Course content is never authored twice.
**Why:** Don't rebuild what Moodle does well; keep product logic in the product and a single source of truth per concern.
**Rejected:** Building our own LMS (huge, redundant); duplicating course content in both systems (sync hell).
